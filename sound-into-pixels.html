Sound Into Pixels

How the loop, the bars, and the particles actually work

The whole job in one sentence: sound comes in as numbers, a picture goes out. Three files split that work up.

Think of a TV

PartJobFile
the contract"every show must be 30 minutes and have credits"renderer.ts
the projectorflips to the next picture 60 times a secondloop.ts
the showwhat is actually on screenbars.ts, particles.ts

The projector does not care what is showing. The show does not know it is being played on a loop. They only agree on the contract.

That is the entire architecture. Everything else is detail.

The contract

Julio does not write this file. It was handed to him finished. It says one thing: anything that draws must have a draw function taking three arguments.

draw(ctx, frame, settings)
ArgumentWhat it isThink of it as
ctxthe drawing toolsyour pencil and the paper
framethe sound as numberswhat the music is doing right now
settingsuser preferencescolours, sensitivity

Because bars and particles both obey this exact shape, the app swaps between them by changing one line. That is the only reason a contract exists.

The flow

main.ts     "here is a canvas, a source of numbers, and the bars renderer"
   |
   v
loop.ts     every 16ms: get numbers -> call draw() -> schedule the next one
   |
   v
bars.ts     one picture: 48 bars, tall where it is loud
   |
   v
canvas      moving bars in the side panel

Change one line in main.ts:

renderer: () => bars,        becomes        renderer: () => particles,

and the same loop now drives dots instead of bars. Neither file changed.

Who wrote what

Given to him

renderer.ts, the canvas helper, the side panel shell, the settings. All finished before he started.

He writes

loop.ts and bars.ts for LOS-12. particles.ts for LOS-24.

Somebody else

The audio engine and the three sources, tab, mic and file. Those are separate tickets.

Before any drawing makes sense, you have to know what the sound actually looks like as data.

frame.bins is the music

frame.bins        // 1024 numbers, each 0 to 255
frame.sampleRate  // 48000
frame.fftSize     // 2048
frame.pulse       // beat detector, always 0 for now

1024 slots. Slot 0 is the deepest bass. Slot 1023 is the highest treble. The value is how loud that pitch is, right now.

Situationbins looks like
silence[0, 0, 0, 0, 0, ...]
a kick drum[220, 195, 140, 30, 5, 0, ...]
a cymbal[5, 8, 12, ... , 150, 180, 170]

And it gets completely refilled 60 times a second. That is the only reason anything on screen moves.

Watch it move

Every bar below is one slice of the 1024 numbers. This is fake audio, but it behaves like the real thing: a moving spectrum with a bass thump on the beat.

bins[0] 0 bins[100] 0 bins[500] 0 bins[1000] 0

Notice the left side is always busier than the right. Real music has far more energy in the bass than the treble. That single fact drives the most confusing part of bars.ts, coming up in tab 4.

Where the numbers come from

Nobody writes any maths. The browser has a thing called an AnalyserNode that does it:

analyser.getByteFrequencyData(bins);   // fills the array, 0 to 255

One function call, and the array is full of fresh numbers. That is a teammate's ticket, not Julio's. Until it lands, a fake generator fills the same array and nothing downstream can tell the difference.

loop.ts is 39 lines and it draws absolutely nothing. It is a timer that tells somebody else to draw.

The setup, runs once

const ctx = options.canvas.getContext('2d');
if (!ctx) throw new Error('render: 2d context unavailable');

let handle = 0;
let running = false;

Grab the drawing tools once. Getting them every frame would be wasteful.

running is an on/off switch. handle is a ticket number the browser hands back so you can cancel later.

tick, the heartbeat

const tick = (): void => {
  if (!running) return;                                    // 1
  resizeToDisplaySize(options.canvas);                     // 2
  options.renderer().draw(ctx, options.nextFrame(), options.settings());  // 3
  handle = requestAnimationFrame(tick);                    // 4
};
  1. Stopped? Quit. The switch check.
  2. Fix the canvas size. If the user dragged the panel wider, match it.
  3. Do the work. Ask who is drawing today, ask for fresh numbers, hand both over.
  4. Book the next one. requestAnimationFrame means "call me again before the next screen refresh", about 16 milliseconds later.

Step 4 is what makes it a loop. Each frame schedules the next one. There is no while anywhere.

Watch the loop run

Nothing fancy is being drawn here. This is just the heartbeat, counting.

frames drawn 0 fps 0 ms per frame 0 state running

Click Simulate hidden panel and the counter freezes. Click again and it resumes. That is exactly what this does:

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') stop();
  else start();
});

The ticket says why: a hidden panel burning a core is a battery bug. No point doing 60 calculations a second for a screen nobody can see.

Start and stop

const start = (): void => {
  if (running) return;      // already going, do not double it
  running = true;
  handle = requestAnimationFrame(tick);
};

const stop = (): void => {
  running = false;
  cancelAnimationFrame(handle);
};

if (running) return matters. Without it, calling start() twice creates two loops racing each other and everything runs at double speed. Easy bug to create, hard to spot.

The 16 millisecond budget

60 frames a second means each frame has about 16 milliseconds to finish everything. Go over and the animation stutters.

That budget is why the ticket says no allocation inside the loop, and why the particle pool has a cap.

bars.ts is 35 lines. It draws 48 vertical bars. Tall bar means that frequency is loud.

Watch it

Step 1: wipe the canvas

ctx.clearRect(0, 0, width, height);

Erase everything. Fresh start every frame. Without this, old bars would pile up on top of new ones.

Step 2: the confusing part, and it is about hearing

The 1024 bins are evenly spaced, about 23 Hz apart. But musical octaves double:

OctaveRangeHow many bins
120 to 40 Hz1 bin
5320 to 640 Hz14 bins
95120 to 10240 Hz218 bins

Split those evenly across 48 bars and everything a human cares about lands in the first three bars. The other 45 show inaudible hiss.

See it for yourself. Same music, same bars, two different mappings:

linear mapping, wrong

log mapping, right

On the left, all the movement is crushed into the far left and the rest is dead. On the right, the whole width is alive. Same numbers, different spacing.

That is what this line does:

const start = Math.round(low * Math.pow(ratio, bar / BAR_COUNT));
const end   = Math.round(low * Math.pow(ratio, (bar + 1) / BAR_COUNT));

Bar 1 covers a couple of bins. Bar 48 covers hundreds. The bars get logarithmically wider.

The ticket says it plainly: linear mapping crams all musical detail into the left edge. Now you can see what that sentence means.

Step 3: average and draw

let total = 0;
for (let i = start; i < last; i++) total += frame.bins[i] ?? 0;

const level = Math.min((total / (last - start) / 255) * settings.gain, 1);
const barHeight = level * height;

ctx.fillStyle = settings.palette[bar % settings.palette.length] ?? '#ffffff';
ctx.fillRect(bar * barWidth, height - barHeight, barWidth - 1, barHeight);
LineWhat it does
total += ...add up the bins in this bar's range
/ (last - start)turn the total into an average
/ 255turn 0-255 into 0-1
* settings.gainthe user's sensitivity knob
Math.min(..., 1)never go above full height
level * height0-1 becomes pixels

Why height - barHeight? Because y counts downward on a canvas. (0,0) is the top left corner. A tall bar has to start near the top, so you subtract its height from the bottom.

barWidth - 1 leaves a one pixel gap so the bars do not merge into a solid block.

Same contract, different picture. Dots instead of bars. But there is one idea here that the whole ticket is graded on.

Watch it

alive 0 / 240 spawned this frame 0 objects created since load 240

Watch that last number. It never goes up. 240 objects were made when the page loaded and not one has been created since, no matter how many dots you see.

The pool, the idea that matters

const pool = Array.from({ length: MAX_PARTICLES }, () => ({
  x: 0, y: 0, vx: 0, vy: 0, age: 0, life: 0, band: 0,
}));

240 dot objects, created once when the file loads. Never again.

Think of a parking lot with 240 painted spots. You never build new spots and you never demolish any. Cars come and go, the spots stay.

A dot is dead when age >= life. Dead does not mean deleted, it means the spot is free. At startup every dot has age: 0, life: 0, and 0 >= 0 is true, so all 240 start empty.

See the parking lot

Each square is one slot in the pool. Green means a dot is alive in it. Grey means free.

Squares flick between grey and green constantly. That is recycling. A square going green did not get created, it got reused.

Why it has to work this way

The obvious version looks like this:

dots.push(newDot());               // makes a new object
dots = dots.filter(d => d.alive);  // makes a new array

That is hundreds of objects a second for the garbage collector to clean up. While it cleans, the animation freezes for a few milliseconds and the user sees a stutter.

That is the entire reason the ticket says fixed-size particle pool, no per-frame allocation.

Bands: chopping the sound into 4

1024 numbers is too many to work with. Squash them:

bins[0   .. 255]  ->  band 0   bass
bins[256 .. 511]  ->  band 1
bins[512 .. 767]  ->  band 2
bins[768 .. 1023] ->  band 3   treble

Average each chunk. Four loudness readings, four spawn sources, four lanes across the canvas.

What draw does, four steps

1. Wash, do not wipe

ctx.fillStyle = 'rgba(12, 12, 16, 0.22)';
ctx.fillRect(0, 0, width, height);

Paint near-black at 22% opacity over everything. Old dots get darker each frame instead of vanishing, which gives motion trails for free. Hit Trails on/off above to see the difference. One line, big change.

2. Spawn from loudness

const energy = Math.min((total / size / 255) * settings.gain, 1);
if (energy < THRESHOLD) continue;

for (let n = 0; n < Math.round(energy * MAX_SPAWN); n++) {
  spawn(band, energy, width, height);
}
energydots spawned

The threshold stops background hiss from spawning dots during silence.

3. spawn revives a dead dot

p.x = ((band + 0.5) / BANDS) * width;   // this band's lane
p.y = height;                            // the bottom
p.vx = (Math.random() - 0.5) * energy * 0.012;
p.vy = -energy * 0.02;                   // negative is up
p.age = 0;
p.life = 60;

On a 400px canvas the lanes land at x = 50, 150, 250, 350. Bass on the left, treble on the right.

Math.random() - 0.5 gives a number from -0.5 to +0.5, so half the dots drift left and half drift right.

vy scales with energy. That is "velocity by magnitude" from the ticket. Loud music launches dots harder.

Nothing was created here. Seven numbers were overwritten in a spot that already existed.

4. Move, fade, draw

p.x += p.vx * width;
p.y += p.vy * height;
p.age += 1;

ctx.globalAlpha = 1 - p.age / p.life;
ctx.beginPath();
ctx.arc(p.x, p.y, height * 0.006, 0, TAU);
ctx.fill();

01.00solid

That is "faded by age" from the ticket.

beginPath then arc then fill is just "draw a filled circle". Those three always travel together.

The three sentences

If you can explain these back without looking, you understand the code.

  1. loop.ts never draws anything. It is a timer that calls somebody else's draw.
  2. The bars are log-spaced because human hearing is log-spaced, not because of anything about code.
  3. "Spawn" does not create a dot. It finds a dead one and overwrites its numbers, which is why the animation never stutters.

Number three is the one the ticket is actually graded on. If it does not feel obvious yet, go back to the parking lot in tab 5 and watch the grid again.
