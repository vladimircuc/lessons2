From Notebook to a Live, Clickable App

A walkthrough for the session where the project stops being a notebook and becomes a real thing on the internet: connect an AI coding assistant to VS Code, push the repo to GitHub, and build an interactive predictor anyone can play with. Ordered so nothing gets tangled.

The session plan

Do these in order. Each step makes the next one safe and easy.

  1. Connect the AI to VS Code. Get to where he can type a request and the assistant edits files in his actual project folder. Everything else depends on this.
  2. Push to GitHub first. Save the current clean project (notebook, README, charts) as a repo before building anything new. Then every UI experiment is a safe, revertible commit.
  3. Polish the README with the AI. A gentle, low-risk first task that improves the most important file.
  4. Build the UI on localhost. The interactive predictor. This is where the session lands.
The one principle to coach the whole time: he uses AI to write code faster, but he reads it, can explain it, and decides what it does. For a college project, "the AI did it" is a bad answer if someone asks how it works. So as the assistant writes each piece, have him pause and understand it. That habit is itself a skill worth teaching this session, and it is what separates using AI well from leaning on it.
Time budget realism: connecting the tooling the first time is fiddly (installs, sign-in, pointing at the folder). Give it room. If you only get through tooling, GitHub, and a first tiny UI, that is a good session.

Connect an AI assistant to VS Code

Three options depending on what he picked. Claude Code is the main path; the other two are fine alternatives.

Heads up on accounts: Claude Code needs a paid Claude plan (Pro or higher), the free plan does not include it. GitHub Copilot is free for students through the GitHub Student Developer Pack, worth applying for since Roman is a student. Cursor has a free tier.

Option A — Claude Code recommended

Anthropic's AI that works right in the terminal and can read and edit the whole project. First make sure VS Code is installed and his project folder is open (File, then Open Folder).

Install (native installer, no Node.js needed)

macOS / Linux

curl -fsSL https://claude.ai/install.sh | bash

Windows (PowerShell)

irm https://claude.ai/install.ps1 | iex

Or on Mac with Homebrew: brew install --cask claude-code.

Start it and sign in

  1. In VS Code, open the built-in terminal: View, then Terminal (or Ctrl + backtick).
  2. Make sure the terminal is in his project folder, then type claude and press Enter.
  3. The first run opens a browser to sign in to his Claude account. Approve it, and he is connected.
  4. Now he can type requests like "explain what this notebook does" or "create a file app.py that...". Claude Code proposes edits he can accept or reject.
Nicer experience: there is also an official Claude Code extension in the VS Code marketplace (search "Claude Code") that gives point-and-click diffs instead of the terminal. Optional, the terminal works fine. Full docs: docs.claude.com/en/docs/claude-code.

Option B — Cursor

An AI-first code editor that looks and feels like VS Code (it is a fork of it). If he would rather have everything built in with no terminal setup, this is the easiest all-in-one.

  1. Download and install Cursor from cursor.com.
  2. Open his project folder in it.
  3. Press Ctrl + L to open the AI chat panel and start asking. It edits files directly, with accept/reject on changes.

Option C — GitHub Copilot (VS Code extension)

  1. In VS Code, open Extensions (the squares icon), search GitHub Copilot, install it.
  2. Sign in with his GitHub account when prompted.
  3. Open the Copilot Chat panel to ask for code, or get inline suggestions as he types.
Student tip: the GitHub Student Developer Pack gives free Copilot and other tools to verified students.

Push the project to GitHub

Do this before the UI work, so the working project is safely saved. Two ways: the easy VS Code button, or the command line.

What GitHub is, in one line: a website that stores his code and its full history. "Pushing" uploads his project to it. Once it is there, the repo link is what goes on college applications, and every future change is saved and revertible.

Easiest way — VS Code's built-in button recommended

  1. He needs a free GitHub account first (github.com).
  2. In VS Code, click the Source Control icon in the left bar (looks like a branch).
  3. Click Publish to GitHub. VS Code handles sign-in through the browser, creates the repo, and uploads everything in one step.
  4. Choose a name like tennis-match-predictor and pick public (so admissions can see it).

That is it. Any later change: type a short message in the Source Control box, click the check to commit, then Sync to push.

Command-line way (or let Claude Code run these)

From the terminal in his project folder. He can also just tell Claude Code "commit everything and push it to a new public GitHub repo" and it will run these for him, a great teaching moment.

git init
git add .
git commit -m "Initial commit: tennis match predictor study"
git branch -M main
git remote add origin https://github.com/USERNAME/tennis-match-predictor.git
git push -u origin main

before the first commit

Add a .gitignore file so junk does not get uploaded:

.ipynb_checkpoints/
__pycache__/
.DS_Store
*.pyc
Auth note: if the command line asks for a password, GitHub no longer accepts account passwords there, it wants a personal access token, which is why the Publish to GitHub button is easier (it does auth for you). If he hits friction, fall back to the button.

What to build the UI in

The models are Python. You want something that runs them, handles the data, and is interactive, without turning into a full web-dev project.

Recommendation: Streamlit. It is a Python library that turns a plain Python script into an interactive web app. He already knows Python and pandas, so there is almost nothing new to learn: no HTML, CSS, or JavaScript required. It runs his actual scikit-learn model, reads his CSV, and gives him sliders, dropdowns, charts, and tables out of the box. It is the standard tool for exactly this kind of ML demo.

Why it fits this project

  • Runs the real model. The app is Python, so it loads his trained model and predicts for real, no need to rebuild anything in another language.
  • Handles the data naturally. Same pandas he already uses, so charts and tables from the notebook drop straight in.
  • Interactive with one line each. st.slider(...), st.selectbox(...), st.bar_chart(...), done.
  • Easy to run and to host. One command locally, and free hosting straight from his GitHub repo (next point).

Run it locally

pip install streamlit
streamlit run app.py

That opens the app in his browser at localhost:8501, updating live as he edits the file. This is the "see it on localhost" he wanted.

Host it free (for the application link)

  • Streamlit Community Cloud connects to his GitHub repo and deploys the app at a public URL for free. Push a change, the site updates.
  • Hugging Face Spaces is an equally good free alternative that also hosts Streamlit apps.
One honest caveat: free-hosted apps "sleep" after a while and take a few seconds to wake on the first visit. Fine for a demo link. (Check each service's current free-tier terms when you deploy.)

The alternatives, briefly

  • Gradio is like Streamlit but even simpler, aimed purely at "inputs in, prediction out". Great if you want the predictor and nothing else. Streamlit wins if you also want the paper, charts, and a game on the page.
  • A plain static web page (GitHub Pages) is the other extreme: no Python server, the logistic regression's math is rewritten in a few lines of JavaScript so it runs in the browser. Upside, the link never sleeps. Downside, it cannot run the tree or neural-net models, only the simple one. A good fallback if hosting a Python app ever becomes a pain.
  • Flask / FastAPI are "real" web backends. More powerful, but they make you write routing and HTML yourself. Overkill here.

What to put on the page

The goal is something a non-technical person (an admissions reader) finds instantly fun, sitting on top of the serious paper.

★ The centerpiece: a live "Who wins?" predictor

The one thing that makes non-technical people go "oh, cool". The reader sets up a matchup and watches the model react instantly:

  • Simple version (build this first): two sliders for the players' rankings (and a surface dropdown). A big win-probability bar fills in live, "Player A wins: 68%", as they drag. Instant, visual, satisfying.
  • Cooler version (add later): two dropdowns of famous players (Alcaraz, Djokovic, Sinner...) with their rankings pre-filled, so the reader picks "Alcaraz vs Djokovic" and sees the call. Much more relatable than abstract numbers.

Make the probability a big colored bar or a tug-of-war between the two names. The visual is what sells it.

★ The showstopper: "Can you beat the model?" intuition game

A genuinely engaging mini-game that also teaches the whole point of the study. Show a real past matchup (two players and their rankings, result hidden). The reader guesses the winner. Then reveal what actually happened and what the model predicted. Keep score over several rounds: the reader vs the model.

Why it is brilliant for this project: the reader discovers first-hand that even they can only get ~65% right, and so does the AI. It turns the "predictability ceiling" finding into something they feel, not just read. This is the kind of thing that gets remembered.

Supporting pieces (lower effort, round it out)

"What actually matters" bar

A single clean bar chart showing ranking dwarfs everything else. Makes the main finding tangible in one glance.

Model scoreboard

The seven-model comparison as a tidy bar chart with a one-line caption: "seven very different algorithms, all stuck at the same ceiling". Shows the breadth of work.

Biggest upsets showcase

A few cards of the most shocking real results (a low-ranked player beating a top seed), where the model was most confidently wrong. Fun, human, and honestly illustrates why tennis is hard to predict.

The paper itself

His README write-up, laid out as readable sections on the page, with the charts inline. The app is the paper, plus the interactive toys on top.

Suggested build order for the app: (1) the page shell with the paper text and charts, (2) the simple slider predictor, (3) the intuition game, (4) the famous-players dropdown and any extra visuals. Ship each piece working before starting the next, committing to GitHub as you go.

Starter kit for the build

Save the model, hand the AI a clear brief, and know what the app skeleton looks like so he can steer it.

1  Save the trained model (in the notebook)

The app should load a ready-made model, not retrain every time. For the predictor, a small logistic regression on one or two intuitive inputs (the ranking gap, optionally surface) keeps the interface clean. Save it with joblib:

import joblib
from sklearn.linear_model import LogisticRegression

# a simple, explainable model on just the ranking gap (great for a demo UI)
ui_model = LogisticRegression(max_iter=1000).fit(train[["rank_diff"]], train["target"])
joblib.dump(ui_model, "model.joblib")
print("saved model.joblib")

note

Using one feature keeps the app dead simple (the user just sets two rankings). It scores near the baseline, which is completely fine for a demo, the full seven-model comparison still lives in the notebook and the paper. He can add features to the UI model later if he wants.

2  A prompt to give the AI to start the app

Paste something like this to Claude Code / Cursor / Copilot. Specific briefs get much better results than "build me a UI".

Create a Streamlit app in app.py for my tennis match predictor.

Context:
- model.joblib is a scikit-learn LogisticRegression trained on one feature,
  rank_diff = player A's ranking minus player B's ranking.
- Lower ranking number = better player.

The app should have:
1. A title and a short intro paragraph.
2. Two sliders: "Player A ranking" and "Player B ranking" (1 to 200).
3. Compute rank_diff = rank_a - rank_b, get the model's probability that
   player A wins with predict_proba, and show it as a big percentage plus a
   progress bar.
4. A one-line explanation of who the model favors and why.

Keep it clean and well commented. Explain each part so I understand it.
Coach the habit here: when the AI returns the code, have Roman read it line by line and explain it back to you before running it. If a line is unclear, he asks the AI "what does this line do?". That is the whole skill.

3  What the skeleton looks like

So you both recognize whether the AI produced something sane. A first app.py is about this short:

import streamlit as st
import joblib

model = joblib.load("model.joblib")

st.title("ATP Tennis Match Predictor")
st.write("Set two players' rankings and see who the model favors.")

rank_a = st.slider("Player A ranking", 1, 200, 10)
rank_b = st.slider("Player B ranking", 1, 200, 50)

rank_diff = rank_a - rank_b
prob_a = model.predict_proba([[rank_diff]])[0][1]

st.metric("Player A win probability", f"{prob_a*100:.0f}%")
st.progress(prob_a)

if prob_a > 0.5:
    st.write(f"The model favors Player A ({prob_a*100:.0f}%).")
else:
    st.write(f"The model favors Player B ({(1-prob_a)*100:.0f}%).")

Run it with streamlit run app.py and it opens on localhost. From here, he grows it with the AI: nicer visuals, the famous-players dropdown, the intuition game, the charts, the paper text.

Commit as you go: each time a piece works (the predictor, then the game, then the charts), commit and push. If an AI change breaks something, he can roll back to the last working version. That safety net is exactly why we pushed to GitHub before starting.
Where this lands: by the end he has a live app on localhost (and hostable from his repo) with a working predictor, the paper, and at least one delightful interactive piece. Next sessions: add the game and the famous-players matchup, then deploy so the college-application link is live.
