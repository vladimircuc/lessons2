import pandas as pd
import numpy as np
from sklearn.linear_model import LogisticRegression
from sklearn.tree import DecisionTreeClassifier

df = pd.read_csv("atp_2000_2024_model_ready.csv", low_memory=False)

df = df.sort_values("tourney_date")

X_train, y_train = train[feature_cols], train["target"]
X_test,  y_test  = test[feature_cols],  test["target"]

# rebuild baseline + the two earlier models
baseline_acc = accuracy_score(y_test, (test["rank_diff"] < 0).astype(int))
logreg = LogisticRegression(max_iter=1000).fit(X_train, y_train)
logreg_acc = accuracy_score(y_test, logreg.predict(X_test))

print("baseline:", round(baseline_acc, 3), " logreg:", round(logreg_acc, 3), " tree:", round(tree_acc, 3))

You should see all three near 0.64. Those are the numbers your new model and experiments this week get measured against.

Model 3: Random Forest

A stronger model that is really just many decision trees working together.

What a random forest is.

A single decision tree is easy to fool: change the data a little and it draws a very different flowchart. A random forest fixes that by training many trees, each on a slightly different random slice of the data and features, then letting them vote. One tree might overreact to a quirk, but the crowd averages those quirks out, so the forest is usually more accurate and more stable than any single tree. Same fit and predict pattern as always.

Cell · train a random forest

forest = RandomForestClassifier(n_estimators=200, max_depth=8, random_state=42, n_jobs=-1)
forest.fit(X_train, y_train)
forest_pred = forest.predict(X_test)

forest_acc = accuracy_score(y_test, forest_pred)
print("random forest:", round(forest_acc, 3))

n_estimators=200 is the number of trees, max_depth=8 caps each tree's depth, and n_jobs=-1 uses all your CPU cores so it trains faster. Expect an accuracy around 0.64, in the same neighborhood as the others.

Note it will not blow the baseline away. On this data the forest lands within a point of everything else. That is not disappointing, it is the finding: the signal that exists is easy to capture, and no fancier model can squeeze out much more.

Cross-validation: trustworthy accuracy

A single train/test split gives one number, and that number got lucky or unlucky. Cross-validation gives you a range you can trust.

Why one split is not enough. Your 0.64 came from one particular slice of matches used as the test set. Split the data a different way and you might get 0.62 or 0.66. Reporting a single number hides that wobble. Cross-validation splits the data into several parts, trains and tests several times using a different part as the test each time, and reports the average plus how much it varied. Now you can honestly say "about 0.66, give or take a point" instead of pretending 0.64 is exact.

Cell · cross-validate the logistic regression

X_all = df[feature_cols]
y_all = df["target"]

scores = cross_val_score(LogisticRegression(max_iter=1000), X_all, y_all, cv=5)
print("fold scores:", scores.round(3))
print("mean:", round(scores.mean(), 3), " give or take:", round(scores.std(), 3))

cv=5 means five train/test rounds. You get five accuracies, then their mean and standard deviation. The mean is your headline number and the standard deviation is the honest wobble around it.

A subtlety for time data. The default cross-validation shuffles matches randomly, which lets it peek slightly across time. For a strict version that always trains on the past and tests on the future, scikit-learn has TimeSeriesSplit. On this data both land around 0.66, so it does not change the story, but it is worth a mention in your write-up that you were aware of it.

3.In a markdown cell, explain why a cross-validated score is more trustworthy than a single train/test split. write it

Example answer

A single split depends on which matches happened to land in the test set, so the number can be lucky or unlucky. Cross-validation repeats the test several times on different parts of the data and averages the results, which cancels out that luck. It also reports how much the accuracy varied, so we can state a trustworthy range instead of one possibly-misleading number.

Adding features: does more help?

A natural instinct is "use more columns and the model gets better". Let us actually test that, honestly.

One-hot encoding for categories.

Models need numbers, but surface is text (Hard, Clay, Grass, Carpet). One-hot encoding turns one text column into several 0/1 columns, one per category, so "Clay" becomes a 1 in the clay column and 0 in the others. pd.get_dummies does this in one line. Then we can bolt those columns onto our numeric features and see if they help.

Cell · build a bigger feature set: surface + best_of

surface_cols = pd.get_dummies(df["surface"], prefix="surface")   # Hard/Clay/Grass/Carpet as 0-1 columns

X_more = pd.concat([df[feature_cols], surface_cols, df[["best_of"]]], axis=1)
y_more = df["target"]

X_more.columns.tolist()

pd.concat(..., axis=1) glues the columns together side by side. You now have the four differences, one column per surface, and best_of.

Cell · retrain on the bigger set and compare

Xm_train, Xm_test = X_more.iloc[:cut], X_more.iloc[cut:]

logreg_more = LogisticRegression(max_iter=1000).fit(Xm_train, y_train)
more_acc = accuracy_score(y_test, logreg_more.predict(Xm_test))

print("4 features:        ", round(logreg_acc, 3))
print("with surface+best_of:", round(more_acc, 3))

The two numbers are almost identical. Adding surface and best-of barely moved the needle. That is the honest, slightly surprising result at the heart of your study.

Why more features did not help. Ranking already reflects how well a player does across all surfaces and formats, so telling the model the surface adds little it did not already know. This is a real finding worth stating plainly: in tennis, the ranking gap dominates, and extra context adds only crumbs.

Cell · check the redundant features

# do rank and points ever disagree on who the favorite is?
agreement = ((test["rank_diff"] < 0) == (test["points_diff"] > 0)).mean()
print("rank and points agree on the favorite:", round(agreement, 3))

You will see they agree essentially 100% of the time. Ranking and ranking points are two ways of saying the same thing, which is why the tree's feature importance can flip between them arbitrarily depending on the data. Good to know, and worth explaining in the write-up.

The honest conclusion so far. Three algorithms and a baseline all score about 0.64 to 0.66. Extra features do not help. Ranking (and its twin, ranking points) is nearly the whole story. Stated plainly: ATP outcomes are largely determined by who is stronger on paper, and the remaining upsets are close to irreducible randomness. That is a credible, mature result, and the fact that it holds across models and features is what makes it convincing.

Example answer
