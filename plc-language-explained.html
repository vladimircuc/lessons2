How your language works

From text to running program: the lexer, the parser, the interpreter and the analyzer, with every demo running the same rules as your Java.

All semester you are building one machine, one part per project. Here is a single line of code going through all of it. Click through the stages, or type your own expression.

The machine, in order

Textwhat you type
LexerP1: cuts text into tokens
ParserP2: builds a tree
AnalyzerP4: checks the meaning

Notice the order. The course builds the interpreter in P3 and the analyzer in P4, but when a program actually runs, the analyzer goes first: check the program, then run it. You built the cook before the inspector, but the inspector stands at the kitchen door.

The key idea: every stage only understands the output of the stage before it. The parser never sees characters, only tokens. The interpreter never sees tokens, only the tree. That is why each project could be tested on its own: the tests hand each stage exactly what the previous stage would have produced.

P1, the lexer. Input: a String. Output: a list of tokens. Your file: Lexer.java.

What it does

The lexer reads the text one character at a time and groups characters into tokens, the words of the language. It throws away spaces and newlines. Every token remembers three things: its type, its exact text, and the index where it started.

Think of it like this: a person reading out loud. They don't see "i-f-x->-1", they see the words "if", "x", ">", "1". The lexer does that grouping, and nothing more. It has no idea what the words mean.

The six token types

TypeRule, in wordsExamples
IDENTIFIERa letter or _, then letters, digits, _ or -x, LET, print, my-var
INTEGERoptional sign, then 0 or a number not starting with 00, 42, -7, +3
DECIMALan integer, a dot, at least one digit1.5, -0.25
CHARACTERone character or one escape between single quotes'a', '\n'
STRINGany characters or escapes between double quotes, on one line"hi", "a\tb"
OPERATOR< > ! = with an optional =, or any other single character<=, +, ;, (

Keywords are not special here. LET, IF and TRUE come out as plain IDENTIFIER tokens. Deciding that IF means "if" is the parser's job.

How the code works: peek and match

The whole lexer is built on two small helpers:

  • peek(patterns) asks "are the next characters like this?" without moving.
  • match(patterns) asks the same, and if yes, steps past them.

Then each token type is one method: lexIdentifier, lexNumber, lexCharacter, lexString, lexOperator. lexToken peeks at the first character and calls the right one. The parser reuses this exact peek and match idea, one level up: tokens instead of characters.

P2A, the parser, expressions. Input: tokens. Output: a tree. Your file: Parser.java.

Why a tree?

Tokens are a flat list, but meaning has structure. In 1 + 2 * 3 the multiplication happens first. The tree makes that visible: lower in the tree means done first.

One grammar rule, one method

The grammar is a list of rules. The parser has one method per rule, and a rule that mentions another rule simply calls that method. This style is called recursive descent.

additive_expression ::= multiplicative_expression (('+' | '-') multiplicative_expression)*

// becomes:
Ast.Expression left = parseMultiplicativeExpression();
while (peek("+") || peek("-")) {
    String operator = tokens.get(0).getLiteral();
    tokens.advance();
    Ast.Expression right = parseMultiplicativeExpression();
    left = new Ast.Expression.Binary(operator, left, right);
}
return left;

The ladder: why * happens before +

The expression methods form a ladder. Each one calls the rung below it before looking for its own operators. So the lower rungs grab their operators first, and end up deeper in the tree.

AND ORparseLogicalExpression: top rung, binds loosest
< <= > >= == !=parseEqualityExpression (comparisons)
+ -parseAdditiveExpression
* /parseMultiplicativeExpression
. nameparseSecondaryExpression: fields and methods
1 "hi" x f() (…)parsePrimaryExpression: bottom rung, the actual values

Think of it like this: a company where each manager first asks their team for an answer before adding their own step. The intern at the bottom (primary) does the most basic work first. The CEO at the top (logical) acts last.

Three shapes to remember

  • Same rung, left to right. 1 - 2 - 3 is (1 - 2) - 3, because of the while loop.
  • AND and OR share a rung. So a OR b AND c is (a OR b) AND c. Different from Java, where && binds tighter.
  • Parentheses make a Group node. (1 + 2) * 3 keeps the group in the tree, so later stages know it was there.

The operator lesson, from the graders. Store the operator exactly as written. In 2A, code that turned AND into && lost 9 points. In 2B, code that turned && into AND lost 10 points on the same tests. Keeping tokens.get(0).getLiteral() unchanged passes both.

P2B, the parser, statements and programs. Same file, more methods.

From expressions to programs

A program is a list of fields (global variables), then a list of methods. Each method has a list of statements. Statements contain expressions, which you already parse.

source    ::= field* method*
field     ::= 'LET' 'CONST'? identifier ':' identifier ('=' expression)? ';'
method    ::= 'DEF' identifier '(' parameters ')' (':' identifier)? 'DO' statement* 'END'
statement ::= 'LET' ... | 'IF' ... | 'FOR' ... | 'WHILE' ... | 'RETURN' ... | expression ('=' expression)? ';'

The : identifier parts are the types added for P4, shown in the Analyzer tab.

The traffic cop: parseStatement

parseStatement looks at the first token and sends it to the right method. Anything that doesn't start with a keyword is an expression or an assignment.

public Ast.Statement parseStatement() throws ParseException {
    if (peek("LET"))    return parseDeclarationStatement();
    if (peek("IF"))     return parseIfStatement();
    if (peek("FOR"))    return parseForStatement();
    if (peek("WHILE"))  return parseWhileStatement();
    if (peek("RETURN")) return parseReturnStatement();
    Ast.Expression expression = parseExpression();      // x = 1;  or  print(x);
    ...
}

The trap you hit: forget one of those lines and the method is never called. WHILE then gets treated as a variable name, and the error says "Expected a semicolon", which points nowhere near the real problem.

P3, the interpreter. Input: the tree. Output: values and printed text. Your file: Interpreter.java.


  
Walking the tree

  
The interpreter has one visit method per kind of node. That is the Visitor pattern. Each visit asks its children for their values first, then does its own job. So evaluation goes bottom-up: the parser built the tree from the top, the interpreter answers from the leaves.

The five mistakes that cost the most

  
    
    
  1. Not restoring the scope. Use try { ... } finally { scope = ... } so the old scope comes back even when a RETURN or an error flies out.
    2. 
    
  2. A function's scope comes from where it was written, not from where it's called. Save it in a variable, definingScope, before making the lambda.
    3. 
    
  3. Each loop pass gets a fresh scope. Otherwise LET t = 1; inside a loop crashes on the second pass: "already defined".
    4. 
    
  4. AND and OR stop early. FALSE AND anything is false without looking at the right side.
    5. 
    
  5. Every branch must return. Your AND block once fell through to "Unknown operator" because its last return line was missing.
    6.

P4, the analyzer. Input: the tree. Output: the same tree, with a type on every expression, or an error. Your file: Analyzer.java. Plus small changes to Parser.java.


  
What it is for

  
The interpreter only finds a mistake when it reaches that line while running. The analyzer reads the whole program before anything runs and rejects anything that can't make sense.


  

    
Think of it like this: "The table ate the soup" has perfect grammar, so the parser accepts it. But a table can't eat. The analyzer is the reader who says "that sentence doesn't make sense." In code: count = "five"; is grammatical, but if count holds numbers, it is nonsense.

  


  
Step 1: the parser learns types

  
To check types, the program must say them. Three rules in the grammar change. Your lexer needs nothing new: a type is just an identifier, and : is already an operator.

  

    
Before, P2After, P4

    
      
FieldLET total = 0;LET total: Integer = 0; type required

      
MethodDEF f(n) DODEF f(n: Integer): Integer DO parameter types required, return type optional

      
DeclarationLET x = 1;LET x = 1; or LET x: Integer; or both. Type optional.

    
  

  
The parser only records the type names as text. Checking them is the analyzer's job. ParserModifiedTests.java shows the expected trees, and the modified parser is part of the December 5 final.


  
Step 2: the types and their family

  

  
Each line connects a type to its parent above it. Any is like Java's Object: everything fits in it. Comparable holds the four types that can be compared with <. Notice Boolean is not Comparable here, so even TRUE == FALSE is rejected.


  
Step 3: requireAssignable, the one rule behind everything

  
requireAssignable(target, type) answers: can a value of type go into a box labeled target? Exactly three cases say yes:

  
    
    
  1. They are the same type.
    2. 
    
  2. The target is Any.
    3. 
    
  3. The target is Comparable and the value is Integer, Decimal, Character or String.
    4. 
  

  
Everything else throws. Try it:

      value into a
      
      box
    

    

  

  
The same rule checks assignments, LET values, function arguments, RETURN values against the method's return type, and IF or WHILE conditions against Boolean.


  
Step 4: labeling the tree

  
As it checks, the analyzer writes the answers into the tree. Every expression gets setType. Every Access gets setVariable. Every function call and method gets setFunction. P5, the generator, reads those labels to write Java.


  

    
Think of it like this: the interpreter opened every box to see what was inside. The analyzer never opens a box. It only reads and writes the labels. That is why its visit methods return Void, not values.

Say it back

  
If you can explain these without looking, you understand the whole machine, no matter what tools helped you write it.

  
    
    
  1. The lexer cuts text into tokens. Each token has a type, its exact text and where it started. It doesn't know what words mean.
    2. 
    
  2. The parser turns tokens into a tree, one method per grammar rule. Lower in the tree means done first, which is how * beats +.
    3. 
    
  3. parseStatement picks a method by the first token. If no keyword matches, it's an expression or an assignment.
    4. 
    
  4. The interpreter visits the tree bottom-up and returns a value for every node. Statements return NIL. RETURN throws an exception that the method catches.
    5. 
    
  5. New scopes are opened for blocks and methods, and always restored in finally. A function remembers the scope where it was written.
    6. 
    
  6. The analyzer checks types before running. It never computes values. It labels every expression with its type, using requireAssignable: same type, Any, or Comparable.
    7.
