An image is a grid of numbers

The single most important idea in computer vision, and it is simpler than people expect.

The idea. A computer does not see a picture. It stores a grid of numbers, one per pixel, where each number is a brightness value. A dark pixel is a low number, a bright pixel is a high number. That is it. An 8 by 8 image is just an 8 by 8 table of numbers, and "seeing" is finding patterns in those numbers.

The same digit, two ways. Low numbers are the dark background, high numbers trace the bright strokes of the handwriting. Squint at the grid and you can see the zero.

Doing math on an image

If an image is numbers, then editing an image is arithmetic. This is what every photo filter really is.

The idea. Because an image is just an array, ordinary math changes the picture. Add a number to every pixel and the image gets brighter. Subtract every pixel from the maximum and you invert it, like a photo negative. Reverse the column order and the image flips. Slice a smaller rectangle out of the array and you have cropped it. No special image library is needed for any of this, it is plain array work.

Brightness, inversion, and flipping are all just operations on the numbers. Photo editing apps do exactly this, on much bigger arrays.

Cell · four operations

img = digits.images[0]

brighter = np.clip(img + 4, 0, 16)     # add to every pixel, keep inside 0..16
inverted = 16 - img                     # flip dark and light
flipped  = np.fliplr(img)               # mirror left to right
cropped  = img[2:6, 2:6]                # rows 2-5, columns 2-5

fig, axes = plt.subplots(1, 5, figsize=(10, 2))
for ax, picture, name in zip(axes,
        [img, brighter, inverted, flipped, cropped],
        ["original", "brighter", "inverted", "flipped", "cropped"]):
    ax.imshow(picture, cmap="gray"); ax.set_title(name, fontsize=9); ax.axis("off")
plt.show()

Five versions of the same digit. Note the cropped one is a smaller array, 4 by 4 instead of 8 by 8, which matters later: models need every image to be the same size.

Why np.clip? Adding 4 could push a pixel above the legal maximum of 16. np.clip(array, 0, 16) forces every value back inside the allowed range. With real photos you clip to 0 and 255 instead.
Why this matters for tennis. These operations are the basis of data augmentation, a technique we will likely need. If you only have a few hundred tennis photos, you can flip, crop, and brighten them to create more training variety from the same pictures. A flipped photo of a clay court is still a clay court, so the label stays valid while the model sees something new.

Flatten, then classify with what you know

The bridge from your tennis work: an image is a row of features, so your old models work as is.

The trick: flattening. Your models expect each example to be a row of numbers (for tennis: rank_diff, elo_diff, and so on). An image is a grid, so you lay the grid out into one long row: take row 1 of pixels, then row 2 after it, and so on. An 8 by 8 grid becomes a single row of 64 numbers. Now each image is just an example with 64 features, and every classifier you know works on it, unchanged.

Flattening lays the rows of the grid end to end. The picture becomes a single row of numbers, exactly the shape your classifiers expect.

Already done for you. That is what digits.data is: the flattened version, shape (1797, 64), while digits.images is the grid version, shape (1797, 8, 8). Same data, two shapes. You train on digits.data, and you look at digits.images.

Cell · split and train, exactly like tennis

X = digits.data          # 1797 rows, 64 pixel-features each
y = digits.target        # the digit each image shows

X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, random_state=42)

model = LogisticRegression(max_iter=5000)
model.fit(X_train, y_train)
acc = accuracy_score(y_test, model.predict(X_test))
print("accuracy:", round(acc, 4))

About 0.9733. Your first computer vision model, 97% accurate, using the same logistic regression you used on tennis.

Why this is so much higher than tennis (65%), honestly. It is not that this model is better, it is the same algorithm. The difference is the problem. A handwritten 3 really does look different from a handwritten 8, and the pixels contain nearly all the information needed. In tennis, the pre-match numbers simply do not contain the answer, because upsets happen. This is the clearest possible lesson that accuracy is a property of the problem and the data, not a scoreboard for your skill.
One new detail: train_test_split shuffles randomly here, unlike tennis where you split by time. Images have no time order, so random splitting is correct. random_state=42 makes the shuffle repeatable.

Normalization, and an honest test of it

Standard advice in image work is to normalize pixels, rescaling them into the 0 to 1 range by dividing by the maximum. Rather than take that on faith, test it, exactly like you tested features in the tennis project:

raw  = LogisticRegression(max_iter=5000).fit(X_train, y_train)
norm = LogisticRegression(max_iter=5000).fit(X_train / 16.0, y_train)

print("raw pixels: ", round(accuracy_score(y_test, raw.predict(X_test)), 4))
print("normalized: ", round(accuracy_score(y_test, norm.predict(X_test / 16.0)), 4))

Raw about 0.9733, normalized about 0.9667. Normalizing is slightly worse here.

Read that honestly. Normalization did not help on this dataset, because these pixels already sit in a small, consistent 0 to 16 range, so there was nothing to fix. It becomes genuinely important with real photos, where values span 0 to 255 and lighting varies wildly between pictures, and it is close to required for neural networks, which train badly on large raw numbers. So keep the technique, but note that here the measurement says it adds nothing. Same habit as tennis: test, do not assume.

Looking inside the model

Here is something tennis could never give you. The logistic regression learned one weight per pixel per digit, so you can reshape those weights back into 8 by 8 images and see what the model is looking for:

print("coefficient shape:", model.coef_.shape)   # (10 digits, 64 pixels)

fig, axes = plt.subplots(1, 5, figsize=(9, 2))
for ax, i in zip(axes, range(5)):
    ax.imshow(model.coef_[i].reshape(8, 8), cmap="RdBu")
    ax.set_title(f"digit {i}", fontsize=9)
    ax.axis("off")
plt.show()

Shape (10, 64), one row of 64 pixel-weights per digit. Each picture is a map of evidence: red areas are pixels that push toward that digit when bright, blue areas push away. The map for 0 shows a ring shape, because a bright ring with a dark middle is what makes a zero a zero.

Why this is worth doing. Being able to visualize what a model learned is a real advantage of image work, and it is genuinely useful for debugging. If the surface classifier ever learns something silly, like keying on a scoreboard in the corner instead of the court, this kind of look inside is how you would catch it.

Working with real photo files

The practical half of computer vision, and the exact groundwork for tennis. Everything so far was pre-packaged, real photos are not.

What changes with real photos. The digits arrived clean: all the same size, grayscale, tidy value range, already flattened. A folder of tennis photos gives you none of that. They are different sizes, in color, stored as JPG files, with values 0 to 255. So before any model sees them, you have to load, resize, and convert them into a consistent array. That pipeline is what this tab teaches, and it is the single most useful thing in this lesson for the project ahead.

Save any tennis photo from the web into your project folder as court.jpg, then:

Cell · load a real image file

from PIL import Image          # Pillow, the standard Python image library

img = Image.open("court.jpg")
print("size (width, height):", img.size)
print("mode:", img.mode)              # RGB means color

arr = np.array(img)                    # turn the photo into numbers
print("array shape:", arr.shape)       # (height, width, 3)
print("value range:", arr.min(), "to", arr.max())
plt.imshow(arr); plt.axis("off"); plt.show()

The shape is (height, width, 3), for example (300, 400, 3). That trailing 3 is the color channels, red, green, and blue, one value each per pixel. Values run 0 to 255, not 0 to 16.

A color photo stores three numbers per pixel. A clay-court pixel is high in red and low in blue, while a grass pixel is high in green. That difference is the core signal the surface classifier will use.

Cell · the preparation pipeline

# 1. resize so every photo is the same size (models require this)
small = img.resize((64, 64))
small_arr = np.array(small)
print("resized:", small_arr.shape, " total numbers:", small_arr.size)

# 2. grayscale, if color is not needed
gray = np.array(img.convert("L"))      # "L" means luminance, one value per pixel
print("grayscale:", gray.shape)

# 3. normalize into 0 to 1 (important for real photos and neural networks)
normalized = small_arr / 255.0
print("normalized range:", round(float(normalized.min()), 3), "to", round(float(normalized.max()), 3))

# 4. flatten, if feeding a classic model
flat = small_arr.reshape(-1)
print("flattened length:", flat.shape[0])

A 64 by 64 color image holds 12,288 numbers (64 x 64 x 3). Compare that to 64 numbers for a digit, which is why real image work needs more capable models and more computing power.

Resizing is not optional. Every model needs its inputs to be the same shape, but photos come in every size imaginable. So a fixed resize (say 64 by 64, or 224 by 224) is always step one of an image pipeline. It does lose detail, which is a real trade-off: smaller is faster to train but blurrier, bigger keeps detail but costs time and memory.

A preview of the actual tennis problem

Here is the surface signal, in one calculation. Average the color channels over a region and compare:

top    = arr[:arr.shape[0]//2]         # top half of the photo
bottom = arr[arr.shape[0]//2:]         # bottom half

print("top    average R,G,B:", [int(v) for v in top.mean(axis=(0, 1))])
print("bottom average R,G,B:", [int(v) for v in bottom.mean(axis=(0, 1))])

Three numbers per region, the average red, green, and blue. On a clay court photo the red value runs high, and on grass the green dominates. You could almost build a crude surface classifier from these three numbers alone, which is a good sign this project is genuinely learnable.

The limit of flattening, and what comes next

A two-line experiment that reveals exactly what this approach is missing, and why the next lesson exists.

A suspicion worth testing. When you flatten an image, you throw away the layout. The model sees 64 numbers in a row, but nothing tells it that pixel 1 sits next to pixel 2 and above pixel 9. Does the model actually know anything about the shape of the image? Here is a clean way to find out: scramble the pixel positions, the same scramble for every image, then retrain. If the model understood spatial layout, scrambling should wreck it.

Cell · the scramble test

rng = np.random.default_rng(0)
perm = rng.permutation(64)               # one fixed random reordering of the 64 pixels

X_train_s = X_train[:, perm]             # apply the SAME scramble to every image
X_test_s  = X_test[:, perm]

m = LogisticRegression(max_iter=5000).fit(X_train_s, y_train)
print("normal pixels:   ", round(accuracy_score(y_test, model.predict(X_test)), 4))
print("scrambled pixels:", round(accuracy_score(y_test, m.predict(X_test_s)), 4))

Both print 0.9733. Identical, to four decimal places.

What that proves. The model does not care where the pixels are. To it, an image was never a picture, just 64 unrelated numbers, so shuffling their order changes nothing as long as it is shuffled consistently. It learned "pixel 27 tends to be bright for a 3" without any notion that pixel 27 is in the middle of the image. A human shown the scrambled version could not recognize a single digit, but the model scores exactly the same.
Why this breaks on tennis photos. For neat, centered 8 by 8 digits, ignoring layout works fine. Real photos are different, because the same court appears shifted, zoomed, rotated, and lit differently in every picture, and every one of those changes moves the pixels around. A model with no sense of shape or position has to memorize each variation separately, and there will never be enough photos for that.

The fix is a network built to respect spatial layout: a convolutional neural network (CNN). Instead of one long row of pixels, it slides small detectors across the image looking for local patterns (edges, textures, colors) wherever they appear. Because a detector that finds "grass texture" works anywhere in the frame, a CNN handles shifted and zoomed photos naturally. That is the next lesson, and it is what will actually read tennis surfaces.

The size problem, too. Your 64-pixel digits flatten into 64 features. A modest 64 by 64 color photo flattens into 12,288 features, and a 224 by 224 one into over 150,000. Classic models buckle under that many inputs with few examples. CNNs handle it by reusing the same small detectors across the whole image instead of learning a separate weight for every pixel.
