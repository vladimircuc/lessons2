From Text to Tree

How the lexer works, how it feeds the parser, and exactly what to build for Project 2A

Start with one fact. Source code is just text. A file containing LET x = 5 + 3; is fourteen characters. It means nothing to a computer until a program reads it and decides what to do.

That program is what you are building this semester. It is not six assignments. It is one program, built in six pieces, and each piece hands its output to the next.

Four things that surprise everyone

1. Keywords are just identifiers

"LET"   ->  [IDENTIFIER(LET)]
"IF"    ->  [IDENTIFIER(IF)]
"NIL"   ->  [IDENTIFIER(NIL)]
"TRUE"  ->  [IDENTIFIER(TRUE)]

The lexer has no idea keywords exist. To it, LET and banana are the same thing: a word.

Keywords become keywords one stage later, when the parser looks at a token and asks "is your text spelled L-E-T?" That is what single quotes in the grammar mean. 'LET' means an IDENTIFIER token whose text happens to be LET. There is no reserved word list anywhere in this language.

2. Numbers swallow their sign

"x+10"    ->  [IDENTIFIER(x), INTEGER(+10)]
"x + 10"  ->  [IDENTIFIER(x), OPERATOR(+), INTEGER(10)]

With no spaces there is no plus operator at all. The number rule is [+-]? [0-9]+ ..., so the sign belongs to the number. The lexer is greedy and takes it.

This means x + 10 is a valid expression and x+10 is not. Whitespace changes the answer.

3. Identifiers can contain hyphens

"x-10"  ->  [IDENTIFIER(x-10)]

One single token. The rule is [A-Za-z_] [A-Za-z0-9_-]*, and that trailing - inside the brackets allows hyphens. So x-10 is a variable whose name is literally x-10.

4. Only some two-character operators merge

"<="  ->  [OPERATOR(<=)]                 merged
"!="  ->  [OPERATOR(!=)]                 merged
"||"  ->  [OPERATOR(|), OPERATOR(|)]     NOT merged
"&&"  ->  [OPERATOR(&), OPERATOR(&)]     NOT merged

The rule is [<>!=] '='?, so only those four characters followed by an equals sign combine. Everything else is one character at a time.

The habit to build: when the parser misbehaves, print the tokens first. Half of debugging Project 2 is discovering the input was not what you assumed.

peek and match

Your lexer is built almost entirely from two helpers, and the parser reuses the exact same idea one level up.

peek

"Are the next characters what I am about to describe? Do not move."

match

"Same question, but if the answer is yes, eat them."

match is peek plus movement. That is the only difference. Look at lexIdentifier:

match("[A-Za-z_]");                  // eat the first letter
while (match("[A-Za-z0-9_-]")) { }   // eat letters and digits until you cannot
return chars.emit(Token.Type.IDENTIFIER);

Read it out loud and it says what it does. That is the pattern for the entire lexer, and you are about to repeat it for the parser.

A grammar is the rulebook. It says which sequences of tokens are legal. It looks intimidating and it is actually five symbols.

How to tell a token type from another rule: the token types are the six names from the lexer, identifier, integer, decimal, character, string, operator. Anything else lowercase is another rule you go look up.

Now read the rule as a sentence: the word LET, then any word, then optionally an equals sign and a whole expression, then a semicolon.

The four-step check

This is the procedure for answering "is this input valid for rule X." Do not read it like a programmer. Walk it like a machine.

  1. Lex it by hand first. Write out the tokens before you look at any rule. This is the step everyone skips and it is where most wrong answers come from.
  2. Copy down the rule.
  3. Walk the rule left to right, crossing off tokens as you consume them.
  4. Ask two questions. Did every required part get satisfied? Did I use up every token?

If either answer in step 4 is no, the input is invalid.

Failure A: leftover tokens

The rule finished but tokens remain. Valid plus garbage still means invalid.

Failure B: missing tokens

The rule demands something and it is not there.

Three reading rules

  • Quoted means keyword. If a word appears in the grammar inside single quotes it is reserved. If it never appears in quotes anywhere, it is just an ordinary name.
  • Star and question mark can match zero times. statement* is happy with no statements at all.
  • The parser checks shape, not meaning. It has no idea whether a variable exists. banana + 7 parses fine even though banana was never declared. Checking that names exist is the Analyzer, Project 4.

Worked examples

FOR EACH IN array DO END against the statement rule

Tokens: six plain identifiers. FOR, EACH, IN, array, DO, END.

Rule: 'FOR' identifier 'IN' expression 'DO' statement* 'END'

Rule wantsTokenOK?
'FOR'FORyes

'IN'INyes

Valid. Nothing missing, nothing left over. The empty body is fine because of the star.

x+10 against the expression rule

Tokens: [IDENTIFIER(x), INTEGER(+10)]. Only two, and neither is an operator.

Rule: additive_expression ::= multiplicative_expression (('+' | '-') multiplicative_expression)*

  • The first part consumes x. Good.
  • The loop needs an OPERATOR token spelled +. The next token is INTEGER +10. Not an operator. Loop runs zero times.
  • The rule returns, having produced just x.

Invalid. INTEGER(+10) is still sitting there. Leftover tokens.

nil against the expression rule

Tokens: [IDENTIFIER(nil)]

Walk the alternatives of primary_expression in order:

  • 'NIL' is uppercase. Our token is lowercase. No match.
  • Not TRUE, not FALSE, not a number, not a character, not a string, no paren.
  • identifier is [A-Za-z_][A-Za-z0-9_-]*. Does nil match? Yes.

Valid, but as a variable named nil, not as the NIL literal. "Is it legal" and "what does it mean" are different questions.

1 < x || y < 10 against the expression rule

Tokens: [INTEGER(1), OPERATOR(<), IDENTIFIER(x), OPERATOR(|), OPERATOR(|), IDENTIFIER(y), OPERATOR(<), INTEGER(10)]

The logical operators in this language are the words AND and OR. The symbols || and && appear nowhere in the grammar, and they do not even lex as one token.

  • The comparison level consumes 1 < x.
  • The logical loop asks: is the next token the word AND or OR? It is OPERATOR(|). Neither. Loop runs zero times.

Invalid. Five tokens left over. Write 1 < x OR y < 10 and it works.

The full grammar for Project 2A

This is all of it. The highlighted part is what you implement this week.

expression            ::= logical_expression

logical_expression    ::= comparison_expression (('AND' | 'OR') comparison_expression)*

comparison_expression ::= additive_expression

additive_expression   ::= multiplicative_expression (('+' | '-') multiplicative_expression)*

multiplicative_expression ::= secondary_expression (('*' | '/') secondary_expression)*

secondary_expression  ::= primary_expression

The parser's output is a tree. Here is why a flat list is not enough, and what the tree is actually made of.

Why a tree

Order of operations is a shape, not a sequence. 1 + 2 * 3 and 1 * 2 + 3 have almost the same tokens but mean different things. A flat list cannot express that. A tree can:

   1 + 2 * 3                1 * 2 + 3

       +                        +
      / \                      / \
     1   *                    *   3
        / \                  / \
       2   3                1   2

    = 7                      = 5

In the left tree the multiply sits inside the add, so it happens first. Precedence is not a rule stored somewhere at runtime. It is baked into the shape.

An AST node is just a Java object

This is the unlock. Forget "tree" for a second. Ast.Expression.Binary is a class with three fields:

public Binary(String operator, Ast.Expression left, Ast.Expression right)

So when you draw this:

      Binary "+"
      /        \
 Literal 1   Literal 2

you are drawing this:

new Ast.Expression.Binary("+",
    new Ast.Expression.Literal(new BigInteger("1")),
    new Ast.Expression.Literal(new BigInteger("2")))

A tree is what nested constructor calls look like when you draw them. Branches are constructor arguments. Your parser is a machine that reads tokens and emits nested new calls.

These are the only five. Project 2A is about exactly these.

All sixteen AST classes

Expression has a value. Statement does something. 5 + 3 equals 8, so it is an expression. IF x DO ... END does not equal anything, so it is a statement. Statements contain expressions. Expressions never contain statements. That is why the two groups are separate.

You never edit Ast.java and you never submit it. It has zero TODOs. It was given to you finished.

One idea runs the whole assignment. Everything else is a consequence of it.

Every rule in the grammar becomes one Java method. Every reference to another rule becomes a method call.

That is why it is called recursive descent. You descend through the rules, and because rules refer back to each other, the methods call each other recursively. Parser.java is not eighteen mysterious TODOs. It is eighteen transcriptions.

That dual behavior is also how keywords work. There is no reserved word list. A keyword is a token whose spelling the parser checked.

The ladder: seven methods

The expression rules form a chain. Each one calls the next.

loosest at the top, tightest at the bottom

Lower on the ladder binds tighter, because it finishes first and ends up deeper in the tree. There is no precedence table anywhere in the code. Precedence is the call order.

Everything climbs all the way down

Even parsing just the number 5 walks through all seven:

parseExpression              "not my job, pass it down"
  parseLogicalExpression     "any AND or OR? no. pass it down"
    parseEqualityExpression  "any < > == != ? no. pass it down"
      parseAdditiveExpression          "any + or - ? no. pass it down"
        parseMultiplicativeExpression  "any * or / ? no. pass it down"
          parseSecondaryExpression     "any dot? no. pass it down"
            parsePrimaryExpression     "an INTEGER! eat it."
                                       -> Literal(5)
          <- Literal(5)
        <- Literal(5)
      <- Literal(5)
    <- Literal(5)
  <- Literal(5)
<- Literal(5)

Seven calls down, seven returns up, to parse one token. That is normal and correct.

Each rung has exactly two outcomes

1. Ask the rung below me for one thing.
2. Is MY operator the next token?
     NO  -> hand back what I got, untouched.
     YES -> eat it, ask the rung below for another thing,
            wrap both in a Binary, and check again.
        PASS THROUGH                    WRAP

   parseAdditive                  parseAdditive
        |                              |
        v                          Binary "+"
   [whatever came up]              /        \
                           [came up]     [next thing]

The tree that comes out is the record of which rungs said yes. Two rungs fire on 1 + 2 * 3, and the tree has exactly two Binary nodes.

The template, four jobs

parseAdditiveExpression:

  1. left = parseMultiplicativeExpression()      get one thing from below
  2. while the next token is "+" or "-":         the ( ... )* in the grammar
  3.     operator = current token's literal      peek first, you need the text
         advance past it
         right = parseMultiplicativeExpression()
  4.     left = new Binary(operator, left, right)   wrap what you have so far
  return left

That left = new Binary(...) reassignment is what makes 1 + 2 + 3 come out as (1 + 2) + 3 rather than 1 + (2 + 3). Left to right, which matters for subtraction: 10 - 3 - 2 must be 5, not 9.

Three things that trip people here

  • BigInteger, not int. Ast.java compares by exact type and the tests build new BigInteger("1"). Same for BigDecimal.
  • Literals need processing, not copying. The token for 'c' is three characters including quotes. Strip them with substring(1, length - 1), then convert escapes so the two characters backslash-n become one real newline.
  • The group branch is the recursion. This is the bottom of the ladder and it calls parseExpression, the top.

The ladder is actually a loop

   parseExpression  <-------------+
        |                          |
        v                          |
    ...five rungs...               |
        |                          |
        v                          |
   parsePrimaryExpression          |
        |                          |
   sees "(" ----------------------+

That is what makes ((1 + 2) * (3 - 4)) work. Every set of parentheses starts a fresh climb down the whole ladder. The loop is the "recursive" in recursive descent.

parseSecondaryExpression, the dot

Plain English: parse one thing, then keep swallowing .something as long as there are dots.

receiver = parsePrimaryExpression()

while match("."):
    require an identifier, grab its name, advance
    if match("("):
        receiver = Function(receiver, name, arguments)
    else:
        receiver = Access(receiver, name)

return receiver

Same accumulator trick as the binary methods, but it wraps into receiver instead of left.

The argument list, written once and reused

if the next token is not ")":
    parse an expression, add it
    while match(","):
        parse an expression, add it
require ")"

Trailing commas fail for free. On f(a, b,) the loop matches the second comma, calls parseExpression, which sees ) and throws. No special handling needed.

parseStatement

expression = parseExpression()

if match("="):
    value = parseExpression()
    require ";"
    return Statement.Assignment(expression, value)

require ";"
return Statement.Expression(expression)

Direct transcription of expression ('=' expression)? ';'. Note the assignment target is a full expression, not a name. That is what makes x.y = 10; work.

Build order

  1. peek and match. Nothing runs without them. About twenty lines. Start from your lexer's versions and swap chars for tokens.
  2. parsePrimaryExpression. The biggest method, and it unblocks every test. Literal and Group tests go green.
  3. parseMultiplicativeExpression. Write it once, carefully, using the four-job template.
  4. Copy it upward four times. Additive, equality, logical, and the one-line parseExpression. Binary tests go green.
  5. parseSecondaryExpression. The dot. Access and Function tests go green.
  6. parseStatement. The last two tests go green.
  7. Error indices and your own extra tests.

Steps 1 through 4 cover most of the tests. Get those done before the first test submission.

Five traps

1. Two different Ast.java files exist. One names things Ast.Stmt and Ast.Expr, which is the HW2 quiz version. The other uses Ast.Statement and Ast.Expression, which is P2. The provided tests use the P2 spelling. Wrong file means nothing compiles and the error will not obviously point at the cause. Check this first.

2. The provided test contradicts the spec grammar. The grammar says the logical operators are the words AND and OR. The provided test file hands the parser && and expects Binary("&&", ...). Accepting all four spellings, AND, OR, &&, ||, costs one extra condition and satisfies both. Then post the question to the course forum, since asking a good question publicly is worth participation credit.

3. The provided tests do not check for leftover tokens. The helper compares the returned node and stops. A buggy parser that reads x and ignores + 10 would still pass some of them. The real grader almost certainly checks. Write your own tests that verify the stream is empty at the end.

4. Error index math is graded but untested. If a bad token is present, report its getIndex(). If tokens ran out, report the character just past the last one: previous.getIndex() + previous.getLiteral().length(). You get the previous token with tokens.get(-1), because get(offset) returns tokens.get(index + offset).

5. A private GitHub repo with the peer mentor added is required to pass the course. Not the assignment, the course. Do it now, it takes five minutes.
