The whole project in one sentence

Sound goes in, the browser turns it into a list of numbers 60 times a second, and a renderer turns those numbers into a picture.

Everything else in the repo exists to make that sentence work: getting the sound, measuring it, keeping time, and drawing.

Before anything can be drawn, the sound has to become numbers. The browser does that part for you.

The 1024 numbers

The audio engine uses a browser tool called an AnalyserNode. Sixty times a second it hands back a list of 1024 numbers, called bins.

  • Position in the list means pitch. Number 0 is the deepest bass. Number 1023 is the highest hiss.
  • Value means loudness, from 0 for silent to 255 for very loud.

Think of it like this: a piano with 1024 keys. The deepest key is on the left, the highest on the right. Each number says how hard that key is being pressed right now. Sixty times a second, you get a new photo of the whole keyboard.

bin 2, about 47 Hz 0 bin 20, about 470 Hz 0 bin 100, about 2.3 kHz 0 bin 600, about 14 kHz 0

Look at where the color is. Almost all of it is on the far left. Bass, voices and most instruments live in the first few hundred Hz to a few thousand. The right half is nearly empty. Keep that in mind, because it is the whole story of the bands fix in tab 6.

What each frame carries

The loop packs the numbers into a small object called frame and passes it to the renderer:

frame.bins        // the 1024 numbers, 0 to 255
frame.sampleRate  // 48000: how many sound samples per second
frame.fftSize     // 2048: how detailed the split is (bins = fftSize / 2)
frame.pulse       // beat detector, always 0 until LOS-20 is built

With these settings each bin covers about 23 Hz, so bin 1 is around 23 Hz and bin 1023 is around 24,000 Hz, the top of what the computer records.

Nobody on the team writes math for this. Splitting sound into pitches is called an FFT, and the browser's AnalyserNode does it. Your code only reads the numbers.

Pictures on a screen don't move. The loop makes them look like they move by drawing a new one again and again.

A flipbook, 60 pages a second

The render loop asks the browser to call it before every screen refresh. That is requestAnimationFrame. Each time, it gets fresh numbers and tells the renderer to draw one picture.

  • 60 pictures a second means each one has about 16 milliseconds to finish.
  • Go slower than that and the animation stutters.
  • The loop never draws anything itself. It calls the renderer's draw().

Think of it like this: the stage manager has a metronome. Every click, they shout "next picture" at whichever lighting designer is working tonight. The stage manager never touches the lights.

pictures drawn 0 per second 0 ms each 0 state running

Click Hide the panel and the counter stops. The real loop does this when the panel is hidden, so it doesn't drain the laptop battery drawing pictures nobody sees.

Per picture or per second? A note from Juan's review

Your particles move a fixed distance each picture, and live for 60 pictures. On most screens that is 60 pictures a second. But some laptops, like newer Macs, refresh 120 times a second.

Think of it like this: you take one step every time the metronome clicks. If someone doubles the metronome speed, you walk twice as fast, without deciding to.

With the default setting, the 120 Hz dot runs twice as fast. Press the button and both move at the same speed, because each step is scaled by the time since the last picture. That time is usually called dt.

What you did about it: nothing in code, on purpose. Juan said it is fine until the loop is finished, so you flagged it on LOS-12: the frame should carry a dt value so every mode can move per second.

The contract every renderer signs

The loop doesn't know or care whether it is talking to bars or particles. It only knows the contract in renderer.ts:

export interface Renderer {
  readonly id: ShapeMode;                  // 'bars', 'particles', ...
  draw(ctx, frame, settings): void;        // draw one picture
  reset?(): void;                          // optional: forget old state (you added this)
}

Think of it like this: a job description. "Must be able to draw one picture when asked." Anyone who meets it can work the show, so the user can switch between bars and particles and the stage manager doesn't change at all.

The pool: 240 parking spots

Look at objects created since load. It says 240 and it never goes up, no matter how many dots appear.

Your file makes 240 dot objects once, when it loads. After that it never makes or deletes one. The grid above shows all 240: filled means a dot is alive in that slot, empty means the slot is free.

Think of it like this: a parking lot with 240 painted spots. Cars arrive and leave all night, but nobody builds new spots or tears old ones down. "Spawning" a dot means parking in a free spot. A dot "dying" means the car drove away and the spot is free again.

Why not just create a new dot each time? Because the browser has a cleaning crew, the garbage collector, that removes objects nobody uses. When it works, the show pauses for a moment. Hundreds of new objects a second means the crew stops the show constantly, and the animation stutters. A fixed pool gives the crew nothing to clean.

function spawn(band, energy, width, height) {
  for (let i = 0; i < MAX_PARTICLES; i++) {
    const p = pool[i];
    if (!p || p.age < p.life) continue;   // spot taken, try the next one
    p.x = ((band + 0.5) / BANDS) * width;   // this band's column
    p.y = height;                           // start at the bottom
    p.vx = (Math.random() - 0.5) * energy * 0.012;
    p.vy = -energy * 0.02;                  // louder = faster upward
    p.age = 0;
    p.life = 60;                            // lives 60 pictures
    p.band = band;
    return;                                 // parked one car, done
  }
}

What draw() does, every picture

  1. Wash the stage. Paint the whole canvas with the background color at 22% strength. Old dots fade a bit each time instead of vanishing, which leaves short trails. Turn trails off above to see the difference.
  2. Measure the four bands. Turn the 1024 numbers into 4 loudness values, one per column. Tab 6 explains how.
  3. Spawn. For each band louder than the threshold, park 1 to 3 new dots in its column. Louder means more dots, launched faster.
  4. Move, fade, draw. Every live dot moves a step, gets one picture older, and is drawn more transparent as it ages: 1 - age / life. At age 60 it is invisible and its spot is free.

Juan's note on switching modes: reset()

The pool lives as long as the page does. So if the user switches to bars and later back to particles, the old half-faded dots pick up exactly where they stopped, flying mid-air.

Try the two buttons under the demo. Old way freezes, then the same dots continue. With reset() starts clean.

Think of it like this: between two songs, the crew sweeps up the confetti from the last one. reset() is the broom.

reset() {
  for (let i = 0; i < MAX_PARTICLES; i++) {
    const p = pool[i];
    if (p) p.age = p.life;   // every car leaves: every spot is free
  }
},

It doesn't delete anything. It just marks every spot as free, the same way a dot dies naturally. You added reset?() to the contract as optional, with a question mark, so bars doesn't have to have one. Calling it when the mode changes is the loop's job, which is why you noted it on LOS-12.

You fixed this: the band split in particles.ts, after Juan's main review comment on PR #5.

The problem in plain words

Your particles have 4 columns, one per band. The first version split the 1024 numbers into 4 equal groups of 256. That sounds fair, but it isn't, because of how pitch works.

Think of it like this: on a piano, every octave doubles the pitch. The lowest A is 27.5 Hz, then 55, 110, 220, 440, 880, 1760, 3520, 7040. Seven of the piano's octaves fit below 3,520 Hz. Split 0 to 24,000 Hz into four equal parts and the first part, 0 to 6,000 Hz, holds almost the entire piano. The last two parts, 12,000 to 24,000 Hz, hold almost nothing a song plays.

So with music, columns 3 and 4 almost never got loud enough to spawn dots. Juan put it as: most frames spawn from 2 of 4 columns. Watch it happen with the same pretend song:

The dashed line is the threshold, 0.18. A column only spawns dots when its bar is above it. The percentage is how often that column spawned over the last few seconds.

The fix: log-spaced bands inside the user's range

Two changes, both from Juan's comment:

  1. Use settings.range. The user can choose which frequencies to show, 20 to 16,000 Hz by default. The old code ignored it and used everything up to 24,000 Hz.
  2. Space the bands like a piano, not like a ruler. Each band covers about the same number of octaves, so each one gets real music.

Here are the real band edges your code computes, at 48,000 samples per second and fftSize 2048:

BandBinsFrequenciesWhat lives there

The first band is only 4 bins wide and the last is 550. That looks unfair, until you remember the piano: each band covers roughly the same number of octaves, so each gets a fair share of the music.

// bandEdges: where each band starts and ends, as bin numbers
for (let edge = 0; edge <= count; edge++) {
  out[edge] = Math.floor(low * Math.pow(ratio, edge / count));
}

Math.pow with a fraction is what makes the steps grow instead of staying equal. low and ratio come from settings.range, turned into bin numbers with the shared helper hzToBin.

Measure once, not every picture

Juan's second request: compute the edges only when they can change. They depend on just five things: the number of bins, the sample rate, the fftSize, and the low and high ends of the range. Those almost never change during a song.

Think of it like this: painting the lane lines on a running track. You paint them once, and repaint only if the track is rebuilt. You don't repaint them before every race.

// inside draw(): recompute only if something they depend on changed
if (
  binCount !== edgesFor.binCount ||
  frame.sampleRate !== edgesFor.sampleRate ||
  frame.fftSize !== edgesFor.fftSize ||
  settings.range.low !== edgesFor.low ||
  settings.range.high !== edgesFor.high
) {
  bandEdges(binCount, frame.sampleRate, frame.fftSize, settings.range, edges);
  // ...then remember what they were computed for
}
bandEnergies(frame.bins, edges, settings.gain, energies);   // every picture: just averaging

You did this: the LOS-17 spike. Its answer decides how LOS-10, tab audio, gets built.

What a spike is

A spike is a short experiment with a time limit, two hours here, to answer one question before anyone builds the real thing. The code is thrown away. The answer is what matters.

The question

To show visuals for a YouTube video, the extension needs that tab's sound. Chrome hands it out as a stream id. The question was: can the side panel itself use a stream id, or does it need a hidden helper page?

Think of it like this: a backstage pass. The box office, the background worker, prints one only while you are standing at the window, which means during your click on the icon. The pass works once and expires in seconds. The question was whether the stage, the side panel, is allowed to use a pass at all.

The three runs

Run 1

  1. Click the icon. The setting openPanelOnActionClick opens the panel.
  2. Click a button inside the panel. The panel asks Chrome for a pass.
  3. Chrome says: "Extension has not been invoked for the current page."

Failed at step 1. Opening the panel this way never counts as a real click.

Run 2

  1. Click the icon. The background worker hears the click and opens the panel itself.
  2. Click a button inside the panel. The panel asks Chrome for a pass.
  3. Chrome gives the same refusal.

Failed at step 1. The pass has to be asked for during the icon click, and a button in the panel is too late.

Run 3

  1. Click the icon. During that same click, the background worker asks Chrome for the pass.
  2. Chrome hands it over.
  3. The background worker passes it straight to the side panel.
  4. The side panel uses it and gets the tab's sound: 1 audio track.

Worked. The side panel can use the pass, as long as the box office prints it during the click.

What this changes for LOS-10

  • No hidden helper page is needed. Sound can live in the side panel, which keeps the design simple.
  • openPanelOnActionClick has to go. With it on, tab capture can never work. It gets replaced by a click handler, action.onClicked, that opens the panel with sidePanel.open and asks for the pass in the same moment.
  • A "This tab" button inside the panel can't start capture by itself. Capture has to start from the icon click.

Four checks on every pull request

When you open or update a pull request, GitHub runs four checks automatically. All four must pass.

  1. Lint. Reads the code for sloppy mistakes, like a variable you created and never used.
  2. Typecheck. Makes sure types match, like never passing text where a number belongs.
  3. Test. Runs every test file. If any test fails, the check fails.
  4. Build. Builds the real extension, to prove it still packages.

Think of it like this: the sound check before the show. Nobody goes on stage until the mics work, the cables are plugged in, and the speakers are on.

Say it back

If you can explain these six without looking, you understand your part of the project, no matter what tools helped you write it.

  1. The extension turns sound into 1024 numbers 60 times a second, and a renderer turns those numbers into a picture.
  2. A renderer is anything with a draw() function. Bars and particles follow the same contract, so the loop can swap them.
