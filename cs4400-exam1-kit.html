Cardinality ratio

The label sits on the line next to an entity, and it answers this: one row on the far side can reach how many of this one? Get the direction right and the rest is easy.

RatioMeaningIn SQL
1 : 1Each side pairs with at most one of the other.Foreign key plus a unique constraint, or merge into one table.
1 : NThe 1 side reaches many. The N side reaches one.Foreign key column on the N side.
M : NBoth sides reach many.A junction table holding both keys.
Direction check. In DEPARTMENT 1 - WORKS_FOR - N EMPLOYEE, the 1 sits beside DEPARTMENT and means an employee has one department. The N beside EMPLOYEE means a department has many employees.

Participation

Cardinality caps the maximum. Participation sets the minimum, and it is carried only by line weight.

  • Single line, partial. Minimum 0. Some rows on this side never appear in the relationship.
  • Double line, total. Minimum 1. Every single row on this side must appear. Also called an existence dependency.

Three consequences worth memorizing, because the exam tests all three:

  1. If X is total and the other side is empty, X must be empty too.
  2. If X is total and X is labelled 1, then X can never outnumber the other side.
  3. Deleting one row can only break a total participation constraint. Nothing else fails from a single deletion.

Weak entities

A weak entity has no key of its own. Room 204 means nothing until you know the building. Four marks always travel together, so if you draw one and not the others, something is wrong.

  1. Double rectangle on the weak entity.
  2. Double diamond on the relationship that identifies it.
  3. Dashed underline on its partial key.
  4. Double lines from the weak entity to that relationship, always total. It cannot exist unattached.

The owner side is usually 1, and in SQL the whole thing is PRIMARY KEY (owner_key, partial_key).

Specialization, superclass and subclass

One entity that comes in flavours. The subclass inherits every attribute and relationship of the parent, and adds its own. Two independent switches sit on the diagram. Read them separately, because the exam grades them separately.

SwitchMarkMeans
Letter in the circled disjointA row belongs to at most one subclass.
o overlappingA row may belong to several subclasses at once.
Line from parent to circleSingle, partialA row may belong to no subclass at all.
Double, totalEvery row must belong to at least one subclass.
All four combinations are legal. Disjoint and total means exactly one. Overlapping and partial means zero, one or several. Never assume the letter implies the line weight.

The small arc drawn on each branch is the subset symbol. It points from the subclass toward the parent and carries no extra meaning you have to mark.

SQL reference

The order a query actually runs

You write it in one order and the engine runs it in another. Every tracing question is answered by walking these seven steps in this exact sequence.

StepClauseWhat happens
1FROMCollect the rows from the tables.
2WHEREThrow away rows that fail the test. Runs before any grouping, so it cannot see aggregates.
3GROUP BYCollapse the survivors into one row per distinct combination.
4HAVINGThrow away whole groups. This is where aggregates get tested.
5SELECTBuild the output columns, compute expressions, apply aliases.
6ORDER BYSort the finished rows.
7LIMIT / OFFSETSkip, then take.
WHERE or HAVING? If the test looks at one row, it is WHERE. If it looks at a whole group, meaning it contains COUNT, SUM, AVG, MIN or MAX, it is HAVING.

Aggregates

FunctionBehaviour
COUNT(*)Counts rows, including rows full of NULLs.
COUNT(col)Counts rows where that column is not NULL. This is where the two differ.
COUNT(DISTINCT col)Counts different non-NULL values.
SUM, AVGSkip NULLs entirely. AVG divides by the count of non-NULL values, not by the row count.
MIN, MAXSkip NULLs. Work on text and dates as well as numbers.
No GROUP BYThe whole table is one group, so you get exactly one row back.

NULL, in three-valued logic

  • Any comparison with NULL gives unknown, never true. salary = NULL and salary <> NULL both match nothing.
  • Only IS NULL and IS NOT NULL can test for it.
  • WHERE keeps a row only when the test is true. Unknown is discarded, so rows with NULL vanish silently from both = and <> filters.
  • NOT IN against a subquery that contains even one NULL returns no rows at all. IN is safe.
  • Aggregates ignore NULL, but COUNT(*) does not.
  • GROUP BY puts all the NULLs together in one group.

Operators worth knowing cold

OperatorNotes
BETWEEN a AND bInclusive of both ends. Same as >= a AND <= b.
IN (list)Matches any value in the list or subquery.
LIKE '%abc%'% is any number of characters, _ is exactly one.
'%aya' versus '%aya%'The first anchors at the end, the second matches anywhere.
DISTINCTRemoves duplicate output rows, applied across all selected columns together.
CONCAT(a, b, c)Joins strings. Can wrap an aggregate, as in CONCAT(note, ': ', MIN(id)).
ASRenames a column. The alias is not visible to WHERE, because SELECT runs later.
ORDER BY a DESC, b ASCSorts by the first key, then breaks ties with the second.
LIMIT n OFFSET kSkip k rows, then return up to n. Returns fewer than n if the rows run out.
Ranked rows. For "the nth through mth highest", use ORDER BY col DESC LIMIT (m - n + 1) OFFSET (n - 1). Third through seventh is LIMIT 5 OFFSET 2.

Nested queries

SELECT customer_id, username
FROM Customers
WHERE customer_id NOT IN (
      SELECT customer_id FROM Orders WHERE order_note = 'Express'
);

Trace it inside out. Run the inner query first, write its result down as a plain list of values, then substitute that list and run the outer query. That habit alone answers most nested tracing questions.

The traps this exam repeats

  1. A multivalued attribute never requires more than one value. The double oval grants permission. One value satisfies it.
  2. Two owners may reuse the same partial key. Two companies can both have a car with plate ABC123.
  3. Total participation is an existence rule. Empty the far side and everything that totally participates must be empty as well.
  4. The letter and the line are independent. A d circle can sit on a single line, meaning at most one subtype and possibly none.
  5. <> silently drops NULL rows. Counting employees whose supervisor is not 333445555 excludes the employee with no supervisor at all.
  6. Strict beats inclusive. "More than 5 hours" excludes exactly 5.0. Read the boundary word twice.
  7. WHERE before grouping, HAVING after. Filtering rows and filtering groups produce different answers.
  8. OFFSET is one less than the rank. The 3rd row means OFFSET 2.
  9. Write the column headers in tracing answers. They are part of the mark.
  10. Attach subclass attributes to the subclass. Putting them on the parent loses the point even when everything else is right.

The instruction on the paper: include all elements relevant to the description, meaning attributes, partial and total participation, cardinality, and superclass or subclass relationships.

Paragraph 1 → Box 1

The primary goal is to track clients and the roles they play within the firm. The system stores information about every person who interacts with the firm, where some clients may act as investors, beneficiaries, or both, while other clients could not choose to be either. The firm recognizes its top investors by recording the total investments worth made by an investor. When a person is registered, they are assigned a client ID that uniquely identifies them. The system also stores each client's name (combination of first and last name), date of birth, and email. For legal purposes, the database calculates a client's age for tax benefit.

Paragraph 2 → Box 2

All clients must own assets. An asset is recognized by an equity ID in the database, which is made up of a combination of its order date and order number. As the market grows more volatile, it is important to store the cost of each asset so that the firm can review this in future. The firm has an adverse history of court cases. To deal with legal obligations, the database must keep a record of the list of lawyers for each equity asset.

Show solution for box 2
Why, clause by clause
  • "recognized by an equity ID" makes equity_id the key, so its name is underlined with a solid line.
  • "made up of a combination of its order date and order number" makes that key composite. Draw order_date and order_number as children below it. Do not underline the children, the parent carries the underline.
  • "store the cost of each asset" is one plain oval.
  • "keep a record of the list of lawyers" is the only double oval on the page. A list cannot fit in one column, so multivalued it is. In SQL this becomes a second table, asset_lawyers(equity_id, lawyer).

The first sentence, "all clients must own assets", is not yours to draw. It is the double line already printed on the Client side of OWNS. Read it as a worked example of the same rule you are applying elsewhere.

Paragraph 3 → Box 3

To manage how their assets are distributed, an investor must enroll in exactly one estate plan. An estate plan is customized for each investor and is unique to them. An estate plan cannot exist without an investor and is identified by the plan number and an investor that tracks it. The system also stores an initiation date of each estate plan.

Show solution for box 3
Why, clause by clause
  • "cannot exist without an investor" makes Estate Plans a weak entity, so the rectangle is doubled.
  • "identified by the plan number and an investor that tracks it" is the giveaway line for an identifying relationship. The plan number alone does not identify a plan, you also need to know whose plan it is. So ENROLL becomes a double diamond and estate_number gets a dashed underline.
  • "must enroll in exactly one estate plan" gives two marks at once. "One" is the cardinality, "must" is total participation on the Investor side, so a double line.
  • "customized for each investor and is unique to them" makes the other side a 1 as well, so the relationship is 1:1.
  • "cannot exist without" also forces a double line on the Estate Plans side. Weak entities always participate totally in their identifying relationship. There is no such thing as a floating weak entity.
  • "stores an initiation date" is a plain oval on Estate Plans.
Sanity checkFour doubled marks in this one box: two lines, the diamond, and the rectangle, plus a dashed rather than solid underline. If you drew a double rectangle without a double diamond, or the other way round, go back. They always appear together.

In SQL this box is PRIMARY KEY (investor_id, estate_number) on the estate plan table.

Paragraph 4 → Box 4

Beneficiaries can register other beneficiaries as nominees. A beneficiary can be registered as a nominee by at most one beneficiary. However, a beneficiary may nominate as many beneficiaries as they prefer. The system must track the date when a nominee was registered in the database.

Show solution for box 4
Why, clause by clause

Both lines leave Beneficiary and both arrive at the same diamond. That is a recursive relationship, an entity related to itself, and it only looks strange. The notation is identical to every other relationship.

  • "registered as a nominee by at most one beneficiary" caps the nominating side at 1. Each person is claimed by one nominator at most.
  • "may nominate as many beneficiaries as they prefer" makes the other direction N.
  • "can" and "may" throughout keep participation partial, so single lines on both connections. A beneficiary who nominates nobody and is nominated by nobody is legal.
  • "track the date when a nominee was registered" is an attribute of the registration event, not of a person, so it hangs off the diamond. Putting it on Beneficiary would be wrong, because one beneficiary can nominate several people on several different dates.

In SQL: a nullable nominated_by foreign key on the beneficiary table, pointing at the beneficiary table, plus a nominated_on date column.

Section 2. EERD Interpretation, 8 points

The Georgia Tech Transportation System EERD, four true or false questions at two points each. The paper adds two assumptions: no attribute can be NULL, and if an entity or relationship exists then all of its attributes exist and are valid.

Question 1

Apart from Regular and Self-Driving Car types, no other subtypes of cars can exist in the database.

True   /   False

Show solution
True.

Look at the line running from Car down into the d circle. It is drawn doubled, which makes the specialization total. Total specialization says every single Car row must belong to at least one of the subclasses shown.

The diagram is the complete schema for this system. If a third subtype were allowed, it would have to be drawn. Since the specialization is total and only two branches exist, a car that is neither Regular nor Self-Driving has nowhere to live in the database.

What would change the answer. Make that a single line, and the specialization becomes partial. A Car could then sit outside both subtypes, and the statement would be false. The d is doing something different: it says a car cannot be Regular and Self-Driving at the same time. Letter and line weight are separate facts.

Question 2

A Driver must have more than one certification, having one is not sufficient.

True   /   False

Show solution
False.

certifications is drawn as a double oval, which makes it a multivalued attribute. That notation says the attribute is permitted to hold several values. It does not say it must.

A driver with exactly one certification satisfies a multivalued attribute perfectly. So does a driver with six.

Why this trick works. The exam takes a notation that grants permission and restates it as one that imposes a requirement. Watch for the same move with participation: a single line permits a row to sit out, it does not require it to.

The one thing the paper's assumption does add is that the attribute is never empty. Combined with "no NULLs", a driver has at least one certification. Still not "more than one".

Question 3

Two different TaxiService companies may own Cars with the same plate number.

True   /   False

Show solution
True.

Car is drawn with a double rectangle, and Owns is a double diamond. Car is a weak entity, owned and identified by TaxiService. That makes plateNum a partial key, shown with a dashed underline.

A partial key is only unique within one owner. The real key of a Car is the TaxiService plus the plate number together. Two rows sharing ABC123 are perfectly legal as long as the owning companies differ.

PRIMARY KEY (taxiservice_name, plateNum)

What would change the answer. Draw Car as a single rectangle with plateNum solidly underlined, and the plate becomes a full primary key. Then no two cars anywhere could share one, and the statement would be false.

Question 4

If there are 0 Cars in the database, then there cannot be any Trips present in the system.

True   /   False

Show solution
True.

Follow the facilitates relationship. The line entering Trip is doubled, so Trip participates totally: every Trip row must be attached to a Car.

With zero Cars there is nothing for a Trip to attach to, so no Trip can satisfy its own constraint. The Trip table has to be empty as well.

The general rule. Total participation is an existence dependency, and it always runs the same direction. If side X totally participates in a relationship with side Y, then emptying Y forces X to empty too. Note the direction is one-way: zero Trips would not force zero Cars, because Car's side of facilitates is a single line. A car can sit in the lot all day.

Show solution
First, turn the marks into arithmetic
  • Double line at Employee on works on: every employee needs at least one project.
  • Double line at Project: every project needs at least one employee.
  • Double line at Manager on managed by, with a 1 on that side: every manager must manage at least one employee, and each employee answers to at most one manager. Therefore managers can never outnumber employees.
  • Single line at Employee on managed by: an employee may have no manager. Nothing to check.
Case 1. Employee 2, Project 3, Manager 1 → Possible

Both employees can be assigned a project. Because works on is M:N, those two employees can cover all three projects between them, so no project is left unstaffed. The single manager needs at least one employee and there are two available. Nothing breaks.

Case 2. Employee 4, Project 2, Manager 7 → Impossible

This is the counting rule. Each of the seven managers must manage at least one employee. The 1 on the manager side means an employee can be assigned to only one manager, so no employee can be shared. Seven managers would need seven different employees and only four exist.

The projects are fine here: 4 employees and 2 projects satisfies both totality rules in an M:N relationship. Only the manager count fails, and one failure is enough.

Case 3. Employee 3, Project 0, Manager 3 → Impossible

The double line at Employee says every employee works on at least one project. With zero projects there is nothing to work on, so three employees cannot exist. The manager count of 3 against 3 employees would have been fine on its own.

The portable versionWhen the side labelled 1 carries a double line, that side can never outnumber the other side. And whenever a side carries a double line, emptying the opposite side forces this side empty too. Those two sentences settle nearly every question of this shape.

Step 1. Group the rows

There is no WHERE, so all seven orders survive. GROUP BY order_note splits them into three groups, so the answer has exactly three rows. Knowing the row count before doing any arithmetic is a good check.

GroupOrders in itquantity / customer_id for each
Gift Box301, 304, 3062/1 = 2,   2/2 = 1,   6/1 = 6

Step 2. The first column

MIN(order_id) is computed per group, then glued to the note by CONCAT with the literal ': ' in the middle. An aggregate can sit inside a string function like this, which is what makes the column look unusual.

  • Gift Box, smallest order_id of 301, 304, 306 is 301.
  • Express, smallest of 302 and 305 is 302.
  • Front Door, smallest of 303 and 307 is 303.
Step 3. The second column

Read the nesting carefully. The division happens per row first, then AVG averages those quotients, then the result is multiplied by 10. Averaging the quantities and dividing once would give different numbers.

  • Gift Box: (2 + 1 + 6) / 3 = 3, times 10 = 30.
  • Express: (0.5 + 2.5) / 2 = 1.5, times 10 = 15.
  • Front Door: (0.8 + 0.2) / 2 = 0.5, times 10 = 5.

Notice AVG divides by the number of rows in the group, not by the number of rows in the table.

Marks live in the header rowThe output columns are named by the aliases, so the first row of your answer table is batch_log and avg_qty. Writing the data without the headers throws away part of the mark.

  3. jsmith99, customer 1
Step 4. Skip, then take

OFFSET 1 throws away the first row, so sara_jones is gone. LIMIT 5 then asks for up to five rows, but only two remain, so you get both. A LIMIT larger than the available rows is not an error, you simply get what is left.

Two traps in one questionSorting by the wrong column, since the output starts with customer_id but the sort key is username. And expecting five rows because the query says LIMIT 5. Also remember that OFFSET is applied after the sort, never before.

One safety note for real work: NOT IN against a subquery that can return a NULL yields no rows at all. Here customer_id is a primary key on the Orders side, so no NULL can appear and the query is safe.

Basic queries and conditions

practiceQuery14

Retrieve all information for employees in department 5 whose salary is between $30,000 and $40,000.

Show solution
select * from employee
where dno = 5 and salary between 30000 and 40000;

"All information" means every column, so select * rather than naming columns.

BETWEEN is inclusive on both ends, so an employee earning exactly 30000 or exactly 40000 is included. Writing > 30000 and < 40000 would silently drop two rows.

Returns Smith at 30000, Wong at 40000 and Narayan at 38000. English is in department 5 but earns 25000, so she is out.

practiceQuery18

Retrieve the first and last names of all employees who do not have supervisors.

Show solution
select fname, lname from employee
where superssn is null;

"Does not have" means the column holds NULL, and NULL needs its own operator.

superssn = null returns an empty result, every time. A comparison against NULL evaluates to unknown, and WHERE keeps only rows where the test is true. Unknown is thrown away exactly like false.

Only James Borg qualifies.

practiceQuery43

Display the sum of 4 and 6 as 'my_sum', the product of 3 and 7 as 'my_product', and the difference of 9 and 5 as 'my_difference'.

Show solution
select 4 + 6 as my_sum,
       3 * 7 as my_product,
       9 - 5 as my_difference;

No FROM clause, because no table is involved. SELECT can evaluate plain arithmetic and hand back a single row: 10, 21, 4.

The point of the exercise is AS. Without aliases the column headers would be the expressions themselves, and the grader checks the names.

practiceQuery52

Retrieve the first name, last name and address of all employees, and display the first and last name as a combined 'Whole Name'. (Hint: use concat)

Show solution
select concat(fname, ' ', lname) as 'Whole Name',
       address
from employee;

The output has two columns, not three. The combined name replaces the two separate ones rather than being added next to them, which is what "display the first and last name as a combined" is asking for.

The middle argument ' ' is the space between them. Leave it out and you get JohnSmith.

practiceQuery63

Retrieve the first name, last name and address of all employees who are in department 5 or earn more than 30000 in salary.

Show solution
select fname, lname, address from employee
where dno = 5 or salary > 30000;

OR, so a row qualifies by satisfying either condition. Six of the eight employees come back: the four in department 5, plus Borg at 55000 and Wallace at 43000.

Note "more than 30000" is strict, so Smith at exactly 30000 would not qualify on salary alone. He is in the result only because he is in department 5.

practiceQuery66

Retrieve the first name, last name, address and birthdate of all employees born after January 1st, 1964 and before August 10th, 1970.

Show solution
select fname, lname, address, bdate from employee
where bdate > '1964-01-01' and bdate < '1970-08-10';

Dates are written as quoted strings in YYYY-MM-DD form and compare with the ordinary operators, where later means greater.

"After" and "before" are both strict, so use > and < rather than BETWEEN, which would include the endpoints. No employee sits exactly on either date here, so both happen to give the same answer, but only one matches the wording.

Three rows: Smith 1965, Zelaya 1968, Jabbar 1969. English at 1972 falls outside the upper bound.

practiceQuery70

Retrieve the first name, last name and address of all employees in the order of last name and then first name.

Show solution
select fname, lname, address from employee
order by lname, fname;

ORDER BY is ascending unless you say otherwise, so no keyword is needed. Listing two columns means sort by last name, then use first name only to break ties.

The sort order has nothing to do with the order columns appear in SELECT.

practiceQuery75

Retrieve the first name, last name and address of all employees whose last names contain the pattern 'aya' where the pattern is not at the end of the string.

Show solution
select fname, lname, address from employee
where lname like '%aya%'
  and lname not like '%aya';

Two conditions, because the question has two parts. '%aya%' finds the pattern anywhere. '%aya' anchors it to the end, since nothing follows the pattern, so NOT LIKE '%aya' rules out the ones that finish with it.

Narayan contains aya in the middle and survives. Zelaya ends with it and is excluded. Only one row comes back.

Remember the two wildcards: % is any run of characters including none, _ is exactly one character.

Aggregates

practiceQuery19

Find the sum of the salaries of all employees, the maximum salary, the minimum salary, and the average salary.

Show solution
select sum(salary), max(salary), min(salary), avg(salary)
from employee;

No GROUP BY, so the entire table counts as one group and you get exactly one row back. That is worth knowing as a sanity check: an aggregate without grouping always returns one row.

Put the four functions in the order the question names them. Result: 281000, 55000, 25000, and an average of 35125.

practiceQuery81

Retrieve the sum of the salaries for all employees in department number 5.

Show solution
select sum(salary) from employee
where dno = 5;

WHERE runs before the aggregate, so SUM only sees the four department 5 rows: 30000 + 40000 + 25000 + 38000 = 133000.

This is the model for the WHERE and HAVING distinction. The filter looks at a single row's dno, so it is a WHERE.

practiceQuery86

Retrieve the number of employees whose superssn is not equal to 333445555.

Show solution
select count(*) from employee
where superssn <> 333445555;
The answer is 4, not 5.

Eight employees, three of them supervised by 333445555, so instinct says five remain. It returns four.

James Borg has NULL in superssn. Comparing NULL to anything, including with <>, produces unknown rather than true. WHERE only keeps rows that test true, so Borg is silently dropped.

This is the most instructive query in the set. Pair it with query 18 and you have the whole of three-valued logic: NULL is not a value you can compare, it is the absence of one.

If you genuinely wanted Borg counted, you would write where superssn <> 333445555 or superssn is null.

practiceQuery139

Retrieve the total salary paid to employees who were born between January 1st, 1962 and January 1st 1969.

Show solution
select sum(salary) from employee
where bdate between '1962-01-01' and '1969-01-01';

"Between" in the question maps directly to BETWEEN, endpoints included.

Three employees fall inside the window: Smith 1965, Narayan 1962, Zelaya 1968. Total 93000.

Watch Ahmad Jabbar, born 1969-03-29. That is 1969, but it is after January 1st, so he is outside the range. Reading the year and stopping there is the error to avoid.

Grouping and HAVING

Every question below hinges on the same decision. Filtering rows uses WHERE and happens before grouping. Filtering whole groups uses HAVING and happens after. Get that right and these are all short.

practiceQuery89

Retrieve the department number, minimum salary, average salary and maximum salary for the employees in each department with less than four employees.

Show solution
select dno, min(salary), avg(salary), max(salary)
from employee
group by dno
having count(*) < 4;

"In each department" is the GROUP BY. "With less than four employees" is a statement about a whole group, so it is HAVING.

Put the four output columns in the order the question lists them: number, minimum, average, maximum.

Department 5 has four employees so it fails the test. Department 1 returns 55000 three times, since Borg is alone. Department 4 returns 25000, 31000, 43000.

COUNT(*) in HAVING does not have to appear in SELECT. You can test something you do not display.

practiceQuery100

Retrieve the total number of employees whose salaries exceed $25,000 in each department.

Show solution
select dno, count(*) from employee
where salary > 25000
group by dno;
This one is WHERE, not HAVING.

The salary test looks at one employee at a time, so it filters rows before any grouping happens. Writing group by dno having salary > 25000 is the classic wrong answer, and it either errors or gives nonsense because salary is not a property of a group.

Trace it in order. WHERE keeps the five employees over 25000: Smith, Wong, Narayan, Borg and Wallace. GROUP BY then buckets those survivors: department 5 gets 3, department 1 gets 1, department 4 gets 1.

Side effect worth noticing: a department where nobody earns over 25000 disappears from the output entirely, because its rows were all removed before grouping. It does not appear with a count of zero.

Compare directly with query 102 below, which is the same shape but genuinely needs HAVING.

practiceQuery102

Retrieve the department numbers for departments where fewer than four employees work.

Show solution
select dno from employee
group by dno
having count(*) < 4;

Now the test is about the group. You cannot know whether a department has fewer than four employees by looking at any single row, so the filter has to run after grouping. That makes it HAVING.

Departments 1 and 4 come back. Only dno is displayed, even though COUNT is what the filter used.

Hold 100 and 102 side by side. Same table, same style of wording, opposite clause. The deciding question is always: does this test need a whole group to answer it?

practiceQuery132

Display the department number and number of employees for departments where the total salary exceeds 100000.

Show solution
select dno, count(*) from employee
group by dno
having sum(salary) > 100000;

You display COUNT but filter on SUM. HAVING can use any aggregate, not just the one in SELECT.

Department totals: 5 has 133000, 4 has 93000, 1 has 55000. Only department 5 clears the bar, returning 5 and 4 employees.

practiceQuery133

Retrieve the SSNs of employees who are assigned to more than one project, considering only those projects where the employee worked more than 5 hours.

Show solution
select essn from works_on
where hours > 5
group by essn
having count(*) > 1;

Both clauses in one query, doing different jobs. "Considering only those projects where the employee worked more than 5 hours" throws away rows, so WHERE. "Assigned to more than one project" counts what is left per employee, so HAVING.

Order matters. WHERE runs first, then the counting happens on the survivors only.

The boundary trap. Ahmad Jabbar, 987987987, works 35 hours on project 10 and exactly 5.0 hours on project 30. Five is not more than five, so that row is discarded and he is left with a single qualifying project. He does not appear in the answer.

Also note that employee 888665555 has NULL hours, and NULL > 5 is unknown, so that row goes too.

Five SSNs come back: 123456789, 333445555, 453453453, 987654321 and 999887777.

practiceQuery134

Retrieve the project numbers where the average hours worked per employee on the project is greater than 20 and at least two employees are assigned to the project.

Show solution
select pno from works_on
group by pno
having avg(hours) > 20 and count(*) >= 2;

Two conditions, both about the group, so both live in HAVING joined by AND. Group by project this time rather than by employee.

Watch the two different thresholds: "greater than 20" is strict, "at least two" is inclusive, so > and >=.

Running the groups: project 1 averages 26.25 across 2 people and qualifies. Project 3 averages 25 across 2 people and qualifies. Projects 2, 10, 20 and 30 all average under 20. Answer: 1 and 3.

Project 20 is a quiet lesson. It has three assignment rows, but one has NULL hours. AVG ignores NULL and divides by 2, while COUNT(*) still counts 3. The two functions disagree about how many rows there are, which is exactly why COUNT(*) and COUNT(hours) are different functions.

practiceQuery138

Retrieve the SSNs of employees who on average worked more than 15 hours while working on 2 or more projects.

Show solution
select essn from works_on
group by essn
having avg(hours) > 15 and count(*) >= 2;

Same shape as 134, grouped by employee instead of project. No WHERE at all, because nothing filters individual rows here.

Wong, 333445555, is the interesting exclusion. He is on four projects, easily clearing the "2 or more" bar, but ten hours on each averages exactly 10, which fails the first condition. Passing one test is not enough.

Five SSNs qualify: 123456789 averaging 20, 453453453 averaging 20, 987654321 averaging 17.5, 987987987 averaging 20, and 999887777 averaging 20.

practiceQuery155

Retrieve the department number and sex, and the number of employees for each (department, sex) combination. Order by department number ascending, then sex ascending.

Show solution
select dno, sex, count(*) from employee
group by dno, sex
order by dno asc, sex asc;

Grouping by two columns creates one group per distinct pair, not one per column. Five combinations exist in this data, so five rows come out.

Rule of thumb: everything in SELECT that is not inside an aggregate has to appear in GROUP BY. Here that is dno and sex.

Result: department 1 has 1 male, department 4 has 2 female and 1 male, department 5 has 1 female and 3 male.

practiceQuery156

Retrieve for each department and salary, the number of employees that earn that salary. Order by salary descending and department ascending.

Show solution
select dno, salary, count(*) from employee
group by dno, salary
order by salary desc, dno asc;

Grouping on a numeric column feels odd but works the same way: each distinct department and salary pair becomes one row.

Almost every count is 1, because most salaries are unique within a department. The exception is department 4 at 25000, where Jabbar and Zelaya both sit, giving a count of 2.

The two sort directions differ, so write both keywords out. ORDER BY salary desc, dno would also work since ASC is the default, but being explicit is safer under time pressure.

Ordering, ranking and limits

practiceQuery157

Retrieve information for the 3rd-7th highest salaried employees. Display first name, last name, SSN and salary.

Show solution
select fname, lname, ssn, salary from employee
order by salary desc
limit 5 offset 2;
nth through mth means LIMIT (m - n + 1) OFFSET (n - 1).

Third through seventh is five rows, so LIMIT 5. To start at the third you skip two, so OFFSET 2. The off by one comes from OFFSET counting rows skipped rather than naming a position.

Sorted descending the salaries run 55000, 43000, 40000, 38000, 30000, 25000, 25000, 25000. Skipping the first two leaves Wong, Narayan, Smith, English and Jabbar.

Column order matters here: the question asks for first name, last name, SSN, salary, which is not the order they sit in the table.

One caveat for real work rather than the exam. Three employees tie at 25000, and which of them lands in seventh place is not guaranteed by the SQL standard when the sort key has ties. On this fixed data you will get a consistent answer, so do not spend time debugging that row.

practiceQuery161

Retrieve the SSN, first name, last name, and salary of employees ordered by salary in descending order. Display only the 3rd and 4th highest paid employees.

Show solution
select ssn, fname, lname, salary from employee
order by salary desc
limit 2 offset 2;

Same formula as 157. Third and fourth is two rows, so LIMIT 2, and starting at the third means skipping two, so OFFSET 2.

Returns Franklin Wong at 40000 and Ramesh Narayan at 38000.

Note the column order differs from 157: SSN comes first here. Read that part of the question, it is free marks either way.

practiceQuery158

Retrieve each department number and the number of projects associated with that department. Display only the top two departments with the highest number of associated projects.

Show solution
select dnum, count(*) from project
group by dnum
order by count(*) desc
limit 2;

The only question in this set that queries the project table, and the department column there is called dnum, not dno. Reaching for dno out of habit is an easy mistake.

"Top two" means sort then cut, so ORDER BY ... DESC LIMIT 2. No OFFSET, because you start from the first row.

You can sort by an aggregate directly. Department 5 owns ProductX, ProductY and ProductZ for 3. Department 4 owns Computerization and Newbenefits for 2. Department 1 has only Reorganization and gets cut.

practiceQuery159

Retrieve each department number and the number of employees in that department. Display only departments with at least 2 employees, ordered by employee count in descending order.

Show solution
select dno, count(*) from employee
group by dno
having count(*) >= 2
order by count(*) desc;

Three clauses stacked in the order they run: group, filter the groups, then sort. Getting them out of order is a syntax error, so the sequence GROUP BY then HAVING then ORDER BY is worth memorizing as a block.

"At least 2" is inclusive, so >=. Department 5 with 4 and department 4 with 3 survive. Department 1 has a single employee and is dropped.

practiceQuery160

Retrieve each supervisor SSN and the number of employees they supervise. Display only supervisors who supervise at least 2 employees, ordered by the supervised employee count in descending order.

Show solution
select superssn, count(*) from employee
group by superssn
having count(*) >= 2
order by count(*) desc;

Grouping by superssn asks "who reports to whom" using only the employee table, since the supervisor is just another employee referenced by SSN. That self-referencing column is the recursive relationship from the EER half of the course, showing up as data.

Three supervisors qualify: 333445555 with 3 reports, then 888665555 and 987654321 with 2 each.

There is a fourth group you never see. James Borg has NULL in superssn, and GROUP BY collects all the NULLs into their own group, unlike WHERE which discards them. That group has one member, so HAVING removes it. Had the threshold been 1, a NULL row would have appeared in your output, which surprises people.
