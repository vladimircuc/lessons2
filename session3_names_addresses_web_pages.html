Network interview prep. Session 3.

Names, addresses, and web pages

Sessions 1 and 2 got a packet to a server, even across a router. But you didn't type an IP address; you typed a name. And your laptop had no address at all when you opened the lid. This session is the four helpers that fill those gaps, and it ends with the story every interviewer asks for.

Start here

You know how a packet travels: envelopes, a switch, ARP, a router. Four things are still missing before a web page can appear, and you use all four every time you open a browser:

  1. Getting an address. When your laptop joins a Wi-Fi network, something hands it an IP address, a mask, a gateway, and one more thing. That's DHCP.
  2. Turning a name into an address. You typed google.com. Packets need a number. That's DNS.
  3. Asking for the page. The letter the browser writes, and the reply that comes back. That's HTTP.
  4. Doing it privately. The padlock. That's HTTPS.

Then the last tab puts everything from three sessions into one story: what happens when you type a web address and press Enter. Say that story well and you've covered most of what a networking interview asks.

How this page works

  • Same as before: short text, a widget, quick checks, then interview questions I ask out loud. Every new term is underlined and in the Glossary.
  • Everything here is something you can see on your own laptop: the Wi-Fi joining, the address bar, a 404 page, the padlock. When a term feels abstract, that's the thing to picture.
  • Same envelope colors as always: the letter TCP or UDP envelope IP envelope Ethernet envelope.

The one idea for today. Every one of these four helpers is just a small conversation between your computer and a server, in a fixed format, over the packets you already understand. Nothing new happens underneath. New letters, same envelopes.

Joining the network

When your laptop connects to a Wi-Fi network, it has a MAC address and nothing else. No IP address, no mask, no gateway, and no idea who to ask about names. Within about a second it has all four, and you never see it happen. The helper is DHCP.

Four messages

It's a short conversation between your laptop and a DHCP server, which at home is your router and in an office is usually a dedicated machine.

  1. Discover. The laptop shouts to the whole network: "Is there a DHCP server here? I'm MAC ...0a and I need an address." It has to be a broadcast, because it has no IP address to send from and doesn't know the server's address. Same trick as ARP.
  2. Offer. The server picks a free address from its pool and replies: "You can have 192.168.1.23 for the next 24 hours. Mask /24, gateway 192.168.1.1, and here's the DNS server to use."
  3. Request. The laptop says "I'll take it." Also broadcast, so that if two servers made offers, both learn which one won.
  4. Acknowledge. The server confirms. Done.

People remember the four as DORA. The address is a lease: borrowed for a set time, and the laptop quietly asks to renew it halfway through. Servers and printers usually get fixed addresses instead, set by hand or reserved on the DHCP server, so they don't move.

Interview questions

I ask, you answer out loud, one to two minutes. Then we open the answer together.

Interview question

Your laptop joins a Wi-Fi network. What happens before you can load a web page?

What a strong answer covers
  • The laptop has only a MAC address. It broadcasts a DHCP Discover.
  • The DHCP server (the router, at home) offers an address with a lease, a mask, a gateway, and a DNS server. Request, Acknowledge.
  • Now the laptop knows who it is, what's nearby, where to send far traffic, and who to ask about names.
  • Bonus: it ARPs for the gateway the first time it sends something far, exactly as in session 2.

Follow-up: Two laptops on the same network got the same IP address. How could that happen? (Someone set one by hand inside the DHCP pool, or two DHCP servers are running. Symptom: both work intermittently.)

Interview question

What's the difference between DHCP and DNS? People mix them up.

What a strong answer covers
  • DHCP gives your computer its own address and settings when it joins a network. It runs once at connection time and renews quietly.
  • DNS turns other computers' names into addresses. It runs every time you visit a new name.
  • They're linked: one of the settings DHCP hands out is which DNS server to use.
  • Both are small request-and-reply conversations over UDP.

Follow-up: DHCP works but DNS doesn't. What can you still do? (Reach anything by IP address: ping 8.8.8.8 works, google.com doesn't. That split is how you diagnose it.)

Names to addresses

You type www.example.com. Packets need 93.184.216.34. DNS is the phone book that turns one into the other. It's a distributed phone book: no single computer knows every name. Instead, names are a tree, and the lookup walks down it.

The walk

  1. Your laptop asks its resolver: the DNS server DHCP told it about, usually your router, or a public one like 8.8.8.8 or 1.1.1.1. "What's the address for www.example.com?"
  2. The resolver checks its memory. If it answered this recently, it replies instantly and the walk is over.
  3. Otherwise it asks a root server: "who handles .com?" Every resolver knows the root servers' addresses; they're built in.
  4. It asks a .com server (a TLD server): "who handles example.com?"
  5. It asks example.com's own server (the authoritative server): "what's www.example.com?" That server owns the answer: 93.184.216.34, good for 3,600 seconds.
  6. The resolver sends the answer to your laptop and remembers it for those 3,600 seconds. Your laptop remembers it too.

That "good for 3,600 seconds" is the TTL. It's how long anyone may cache the answer before asking again. Short TTLs let a site move quickly; long ones cut the number of lookups. The whole first walk takes tens of milliseconds. The second lookup takes about one.

DNS runs over UDP on port 53: a small question, a small answer, and if one gets lost, ask again. The kinds of answer are called records. Four you should be able to name: A (name to IPv4 address), AAAA (name to IPv6 address), CNAME (this name is an alias for that name), MX (the mail server for this domain).

Interview questions

Out loud, one to two minutes each.

Interview question

Walk me through what happens when your laptop looks up www.example.com for the first time.

What a strong answer covers
  • The laptop asks its resolver (the DNS server it got from DHCP) over UDP port 53.
  • The resolver checks its cache, misses, and walks the tree: root ("who runs .com?"), then .com ("who runs example.com?"), then example.com's authoritative server ("what's www?").
  • The answer comes back with a TTL; the resolver and the laptop both cache it.
  • Second lookup within the TTL is answered from cache, no walk.

Follow-up: Why don't laptops just ask the root servers directly? (The roots would be crushed; resolvers cache and serve millions of clients. Also the walk needs several steps, which the resolver does on your behalf.)

Interview question

What is a TTL in DNS, and what's the trade-off between a long one and a short one?

What a strong answer covers
  • How long a cached answer may be used before asking again, set by the domain's owner on each record.
  • Long TTL: fewer lookups, faster pages, less load on the servers. But if the site moves to a new address, some users keep going to the old one until the TTL runs out.
  • Short TTL: changes take effect fast (good before a migration or for failover), at the cost of more lookups.
  • Common practice: lower the TTL a day before a planned change, raise it after.

Follow-up: You changed a site's address and half the world still sees the old site an hour later. Why? (The old record's TTL hasn't expired in those resolvers' caches. Nothing to do but wait, which is why you lower it beforehand.)

Interview question

ping 8.8.8.8 works, ping google.com fails. What's broken, and what do you check?

What a strong answer covers
  • Packets get out fine by IP, so layers 1 to 3 and the gateway are healthy. The failure is name resolution.
  • Either the laptop has no or a wrong DNS server configured, or the resolver isn't reachable or isn't answering.
  • Check which resolver the laptop is using (its network settings, or /etc/resolv.conf on Linux), then nslookup google.com against it and against 8.8.8.8 directly to see which one fails.
  • This split, IP works and names don't, is the classic DNS signature and you should say it out loud.

Follow-up: nslookup against 8.8.8.8 works but against your router doesn't. What does that tell you? (Your resolver, the router, is the problem, not the internet or the domain.)

Asking for the page

With an address in hand, the browser opens a TCP connection to the server (the handshake from session 1) and writes a letter. The letter's format is HTTP, and it's plain text you can read. Here is a complete request:

GET /index.html HTTP/1.1
Host: www.example.com
Accept: text/html

Line one: a method (what I want to do), a path (which page), and the version. Then headers, one per line, which are notes about the request. The Host header matters most: one server often hosts many websites, and this is how it knows which one you meant. A blank line ends the request. Two methods cover almost everything: GET means "give me this," and POST means "here's some data" (a form, a login), with the data after the blank line.

The reply is the same shape with a status code on the first line:

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 87

<html><body><h1>Welcome</h1><img src="/logo.png"></body></html>

Status codes come in families by their first digit. 2xx: fine, here it is. 3xx: it's somewhere else, go there. 4xx: you asked for something wrong. 5xx: the server broke. Five to know by heart: 200 OK, 301 moved permanently, 404 not found, 500 server error, 503 server unavailable. The one people get wrong: a 404 means the server is up and answered you. The network is fine. It just doesn't have that page.

One more thing that surprises people: a page is never one request. The HTML comes back, the browser reads it, finds a stylesheet and images and scripts, and asks for each of those too, usually reusing the same TCP connection. A typical page is dozens of requests.

Interview question
    
What's in an HTTP request, and what's in the response?

    
What a strong answer covers
    
      
  • Request: a method (GET, POST), a path, the version, then headers (Host above all), a blank line, and a body for POST.
    • 
      
  • Response: version, status code and phrase, headers (Content-Type, Content-Length), blank line, body.
    • 
      
  • It's plain text over a TCP connection, port 80 for HTTP and 443 for HTTPS.
    • 
      
  • Strong answers can name the code families and say what Host is for.
    • 
    
Follow-up: How does the browser know where the body ends? (Content-Length, or chunked encoding when the size isn't known up front.)

  

  
Interview question
    
What's the difference between a 404 and a 500, and where would you look for the cause of each?

    
What a strong answer covers
    
      
  • Both mean the server is up and answered. Neither is a network problem.
    • 
      
  • 404: the path doesn't exist. Look at the request: a typo, a moved page, a bad link.
    • 
      
  • 500: the server's code failed while handling a valid request. Look at the server's logs.
    • 
      
  • Contrast with no response at all: that's a network, DNS, or dead-server problem, and it looks like a timeout.
    • 
    
Follow-up: A user reports "the site is down" and sends a screenshot of a 503. Is it down? (Not exactly: the server is reachable and responding but refusing work, usually overload or maintenance. Very different fix from a timeout.)

  

  
Interview question
    
Why does loading a single web page generate dozens of HTTP requests, and why does that matter?

    
What a strong answer covers
    
      
  • The HTML references other files: CSS, scripts, images, fonts. Each is its own request.
    • 
      
  • They mostly reuse the same TCP connection (keep-alive), so you don't pay a handshake each time.
    • 
      
  • It matters because each request is at least one round trip, so pages with many small files are slow on high-latency links. That's why sites bundle files and use CDNs close to users.
    • 
      
  • Bonus: HTTP/2 lets many requests share one connection at the same time.
    • 
    
Follow-up: A page feels slow but the server responds fast. What else could it be? (Many round trips over a long distance, a slow DNS lookup, or a third-party script blocking rendering. The network round-trip time multiplies by the number of sequential requests.)

  







  
Locking the door

  
HTTP is a postcard. Every router on the path, and anyone on the same Wi-Fi, can read the request and the reply. HTTPS is the same letter inside a locked box. The lock is called TLS, and the padlock icon in your browser means it's on.


  
A second handshake

  
After the TCP handshake, the browser and server do one more before any HTTP is sent:

  
    
    
  1. The browser says hello: which versions of TLS it speaks, which encryption methods it knows, a random number, and the name of the site it wants.
    2. 
    
  2. The server says hello back, picks a method, and sends two things: its certificate and its half of a key exchange.
    3. 
    
  3. The browser checks the certificate. Is it issued to the name I asked for? Is it signed by a certificate authority the browser already trusts? Is it still valid? If any answer is no, you get the red warning page.
    4. 
    
  4. Both sides combine their halves and arrive at the same secret. Nobody who only watched the wire can compute it. From this point on, every byte is scrambled with that secret.
    5. 
  

  
Then the HTTP request from the last tab goes through, inside the box. A certificate is an ID card: it says "this key belongs to www.example.com," and it's signed by an issuer whose signature your browser can verify because a list of trusted issuers ships with the browser and the operating system. The site owner proved to the issuer that they control the name, and the issuer vouched for it.


  
What it hides and what it doesn't

  
HTTPS hides the path you asked for, the headers, your cookies, and the whole content in both directions. Someone on the path cannot read or alter any of it, and cannot pretend to be the server. What they still see: that you connected to that server's IP address, usually which site name (it's sent in the clear at the start so the server can pick the right certificate), and roughly how much data moved and when. Privacy of the content, not secrecy of the visit.

Out loud, one to two minutes each.

  
Interview question
    
What does HTTPS protect you from, and what doesn't it protect you from?

    
What a strong answer covers
    
      
  • Protects: anyone on the path reading the content, changing it, or impersonating the server. Path, headers, cookies, and body are all encrypted, both directions.
    • 
      
  • Doesn't hide: the server's IP address, usually the site name, the amount and timing of data. Doesn't make the site trustworthy; a phishing site can have a perfect padlock.
    • 
      
  • Mechanism in one line: a TLS handshake after TCP that authenticates the server with a certificate and agrees on a shared secret.
    • 
    
Follow-up: Can your employer's network see which sites you visit over HTTPS? (Yes, by IP and usually by name. Not what you read or typed there.)

  

  
Interview question
    
How does your browser decide to trust a certificate?

    
What a strong answer covers
    
      
  • It checks the name on the certificate matches the site it asked for.
    • 
      
  • It checks the certificate is signed by a certificate authority in the browser's or OS's built-in trusted list (possibly through a chain of intermediate certificates).
    • 
      
  • It checks the validity dates and that it hasn't been revoked.
    • 
      
  • Fail any check: warning page, connection refused. Certificate authorities are trusted because they verify domain control before signing.
    • 
    
Follow-up: Why does an expired certificate cause a hard warning if the encryption would still work? (Trust has a shelf life: the issuer only vouched for the key up to that date, and expired certificates are exactly what a stolen key would look like.)

  

  
Interview question
    
An HTTPS page load needs two handshakes. What does each one do, and why can't one do both jobs?

    
What a strong answer covers
    
      
  • TCP handshake: makes sure both sides are there and sets up reliable, ordered delivery. Knows nothing about who you're talking to or secrecy.
    • 
      
  • TLS handshake: proves the server's identity with a certificate and agrees on a secret for encryption. Runs on top of the TCP connection.
    • 
      
  • Separate layers, separate jobs: TCP is layer 4, TLS sits between transport and application, HTTP rides inside.
    • 
      
  • Cost: at least two round trips before the first HTTP byte (TLS 1.3 needs one; newer protocols like QUIC merge them).
    • 
    
Follow-up: Which envelope from session 1 does TLS live in? (Inside the TCP envelope, wrapped around the letter. Ethernet, IP, and TCP headers are unchanged; only the letter is scrambled.)

Interview question
    
Same page, but this time the site is on your own office network instead of the internet. What changes in the story?

    
What a strong answer covers
    
      
  • DNS still happens, though the answer may come from an internal DNS server and be a private address.
    • 
      
  • Near or far now says near: ARP for the server's own MAC and frame directly to it, no gateway, no routers, no TTL change.
    • 
      
  • TCP, TLS (if the site uses it), and HTTP are identical. The application layers don't know or care how far the server is.
    • 
      
  • That's the point: layers 2 and 3 changed, layers 4 and up didn't.
    • 
    
Follow-up: Would the TLS certificate check still work for an internal site? (Only if the certificate is signed by an authority the browser trusts, which for internal names usually means the company installs its own authority on every laptop.)

  

  
Interview question
    
A user in another country says our site is slow, but our servers respond in under 10 milliseconds. Using the trip, where does the time go?

    
What a strong answer covers
    
      
  • Server time is a small part. Each of the four round trips costs the full distance, maybe 150 ms across an ocean, so 600 ms before the first byte even with a perfect server.
    • 
      
  • Then every additional request for the page's resources adds round trips, though fewer with connection reuse and HTTP/2.
    • 
      
  • DNS may be slow too if their resolver has to walk the tree.
    • 
      
  • Fixes are about distance: a CDN or servers near the user, fewer sequential requests, longer DNS TTLs, keeping connections open.
    • 
    
Follow-up: Would a faster internet connection for the user help? (Barely. Bandwidth isn't the limit; the round-trip time is. You can't send the second message until the first reply arrives.)

Practice

  
Out loud first, then open the answer.


  
1. What does DHCP give a computer, and why does it broadcast?
An IP address on a lease, the subnet mask, the default gateway, and a DNS server. It broadcasts because a computer that just joined has no address of its own and doesn't know where the server is.

  
2. How does a name become an address?
The laptop asks its resolver. The resolver answers from cache if it can; otherwise it asks a root server who handles .com, a .com server who handles example.com, and example.com's own server for the answer. The answer comes with a TTL and gets cached at every step on the way back.

  
3. What does a 404 tell you about the network?
That it's working. The request crossed the network, the server received it, and the server answered. The problem is the path you asked for, not the connection.

  
4. What does HTTPS hide and what does it leave visible?
Hidden: the path, headers, cookies, and content, both ways. Visible: the server's IP address, usually the site name, and how much data moved. Plus a guarantee: you're talking to the real owner of that name.

  
5. Why two handshakes for one page?
TCP's handshake makes a reliable connection between two machines. TLS's handshake proves who the server is and agrees on a secret. Different jobs at different layers; HTTP rides inside both.

  
6. The whole trip, two minutes.
DNS query over UDP to the resolver; address back with a TTL. Far, so frames to the gateway, IP to the server. TCP handshake to port 443 across the routers. TLS handshake, certificate checked, padlock. HTTP GET with Host inside TLS. 200 OK with HTML. More requests for the page's files over the same connection. Render. Four round trips before the first byte.


  
Paper problems

  
a. Name the parts of https://shop.example.com:8443/cart?item=5
https is the scheme (TLS on). shop.example.com is the host name, resolved by DNS. 8443 is the port (443 would be assumed if it were missing). /cart is the path. item=5 is the query string, extra data for the server. The browser turns this into a TCP connection to the resolved address on port 8443, a TLS handshake, and a GET /cart?item=5 with Host: shop.example.com.

  
b. A record's TTL is 300. You look the name up at 10:00:00 and again at 10:03:00 and at 10:06:00. How many times does the resolver go to the authoritative server?
Twice. The 10:00 lookup walks and caches until 10:05. The 10:03 lookup is a cache hit. The 10:06 lookup finds the entry expired and walks again.

  
c. Round trip to a server is 100 ms. Server processing is 5 ms. How long until the first byte of HTML arrives over HTTPS, and what fraction of that was the server?
DNS 100, TCP 100, TLS 100, HTTP 100 plus 5 of processing: about 405 ms. The server was about 1 percent of it. Everything else was distance. Halve the round trip by putting a server closer and you nearly halve the whole number.

  
d. Match each symptom to the helper: (1) address starts with 169.254; (2) ping 8.8.8.8 works, ping google.com fails; (3) red warning "your connection is not private"; (4) page says Not Found.
(1) DHCP: no server answered. (2) DNS: names don't resolve, packets flow fine. (3) TLS: the certificate failed a check, wrong name, expired, or untrusted issuer. (4) HTTP: server up, no such path, a 404.

  
e. A web server hosts twenty small sites on one IP address. How does it know which one a request is for?
The Host header in the HTTP request, and for HTTPS the site name the browser sends at the start of the TLS handshake so the server can present the right certificate.

    2. Talk to a web server by hand
    
      
    Ten lines of Python, no libraries beyond the standard ones. Open a TCP connection to example.com on port 80, send the request from the HTTP tab as raw text, and print what comes back. You'll see the real status line, the real headers, and the real HTML.
    
      
    import socket

s = socket.create_connection(("example.com", 80))
s.sendall(b"GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")
data = b""
while True:
    chunk = s.recv(4096)
    if not chunk:
        break
    data += chunk
s.close()
print(data.decode(errors="replace")[:1200])
    
      
    Then change the path to /nothing-here and look at the status line. Then try port 443 with the same code and see what a server does when you speak plain HTTP to a TLS port.
    
      
    Stretch: wrap the socket with ssl.create_default_context().wrap_socket(s, server_hostname="example.com") before sending, on port 443, and watch the same request work through TLS. Print s.version() and s.getpeercert()["subject"]: that's the certificate from the HTTPS tab.

    Tutor notes (for me)
    

      
Pacing for 90 minutes. Start 5, DHCP 12, DNS 20, HTTP 18, HTTPS 15, Whole trip 20. The whole trip is the point of the session; protect it. If short on time, cut the HTTP POST scenario and the TLS expired-certificate branch.

      
What "good" looks like. She lists four things for DHCP, not three. She says "resolver" and "cache" in the DNS walk without prompting. She says a 404 means the server answered. She separates what HTTPS hides from what it doesn't. She tells the whole trip in order with the round-trip count. If she volunteers the "ping by IP works, by name doesn't" diagnostic, she's ahead.

      
The usual confusions. DHCP versus DNS (they sound alike; the interview question on it exists for that reason). Thinking DNS returns a page rather than an address. Thinking a 404 means the network is broken. Thinking HTTPS hides which site you visited. Thinking the TCP and TLS handshakes are the same thing. Forgetting that DNS runs over UDP.

      
Python checks. Port 80, path /: the output begins with HTTP/1.1 200 OK and headers including Content-Type: text/html. Path /nothing-here: 404 Not Found. Port 443 with plain HTTP: the server either closes the connection immediately (empty output) or returns an error; either way, no HTTP status line, which is the lesson. The ssl stretch prints TLSv1.3 (or TLSv1.2) and a subject containing example.com. If example.com is unreachable from her network, any plain-HTTP site works; neverssl.com is a good fallback for the port 80 part.
