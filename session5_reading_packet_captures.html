Network interview prep. Session 5.

Reading packet captures

Every envelope from the last four sessions, as it really looks on the wire. You already know how to read these. Today you find out.

Start here

So far every packet has been a drawing. Today they're real. A packet capture is a recording of every frame that passed through a network card, saved to a file, and Wireshark is the program that opens that file and shows each frame as one row with its envelopes unwrapped underneath. Nothing new happens in the network. You're just seeing the Ethernet, IP, and TCP envelopes you already know, with the real bytes in them.

The interview tests two things here: can you read a capture, and can you use one to say where something broke. Both are recognition skills. You recognize the handshake because you learned it in session 1; you recognize the DNS answer because you learned it in session 3. This session is practice at recognizing, first on this page, then in the real program.

What you need

  • Wireshark on your Mac. One installer, no settings. The step-by-step is in the second tab. If it isn't installed yet, every capture is also on this page, so nothing stops.
  • The capture files. Nine small files in a folder I'm giving you. Each one is one exchange from a previous session, or one broken page load.
  • No capturing. You open files. You don't record anything unless you want to try at the end of the week.

How this page works

  • Each tab has a Wireshark look-alike with real rows from the capture files. Click rows, open envelopes, type filters. It behaves like the real thing so the real thing feels familiar.
  • Each tab has numbered tasks with a box to type the answer. Do them in order; they're the whole lesson.
  • Then quick checks and interview questions, as always.

The one idea for today. A capture is the trip from session 3, written down one packet per line. To read one, you walk the trip: did ARP get an answer, did DNS, did the handshake finish, did the server reply, what did it say. Wherever the walk stops is where the problem is.

What a capture is

Below is your first capture: a laptop pinging another computer on the same network. Eight frames. Before you look, say what you expect from session 1: an ARP question to everyone, an ARP answer from one machine, then ping requests and replies.

The three parts of the window

  1. The packet list at the top. One row per frame, in the order they were captured. Seven columns: the number, the time since the first frame, source, destination, the protocol Wireshark recognized, the length in bytes, and a one-line summary called Info. Most of your reading happens in the Protocol and Info columns.
  2. The packet details in the middle. Click a row and this shows its envelopes, outside in: Ethernet II, then Internet Protocol, then the next one, then the letter. Each section opens with a click. This is where the fields from the lessons live: the destination MAC, the TTL, the TCP flags.
  3. The bytes at the bottom in the real program. The raw hex. You can ignore it today.

Reading the Time column. It's seconds since the first frame, not clock time. A gap of a second between two rows is a program waiting; a gap of a millisecond is the network answering. In troubleshooting, gaps are evidence: three requests a second apart with nothing between them means nobody answered.

Interview question

What is a packet capture, and what can you learn from one that you can't learn from logs?

What a strong answer covers
  • A recording of every frame on a network card, with timestamps, saved to a file (pcap). Wireshark and tcpdump read them.
  • It shows what actually crossed the wire, including things no log mentions: ARP, retransmissions, resets, timing gaps, who answered and who didn't.
  • It settles arguments: a log says "timeout," a capture says whether the request even left the machine.
  • Limits: it's only the traffic at that point; encrypted content stays hidden; files get large fast, so you filter.

Follow-up: Where would you capture to see traffic between a laptop and a server: the laptop, the server, or in between? (Both ends if you can. If the laptop sees the SYN leave and the server never sees it arrive, the problem is in between.)

Interview question

Open this capture in your head: eight rows, two ARP then six ICMP. Tell me what happened, row by row, and what it proves.

What a strong answer covers
  • Row 1: ARP request to broadcast, the laptop asking who has the target IP. Row 2: ARP reply, unicast, with the MAC.
  • Rows 3 to 8: three ICMP echo requests and three replies, a second apart, each reply within a millisecond.
  • Proves: the two machines are on the same network, layer 2 works, the target is up, and the round trip is tiny.
  • What it doesn't prove: anything about ports, services, or the internet.

Follow-up: Same capture but only the requests, no replies. Two different explanations? (The target is down or firewalled against ping, or ARP never resolved and the requests are going nowhere. Check whether row 2 exists.)

Installing on a Mac

  1. Go to wireshark.org and click Download. Pick the macOS Arm disk image if your Mac has an Apple chip (M1 or newer), or macOS Intel if it doesn't. If you're not sure: Apple menu, About This Mac, look at the Chip line.
  2. Open the downloaded file. A window appears with the Wireshark icon and an Applications folder. Drag Wireshark into Applications. The same window also has an installer called ChmodBPF. Skip it: that's for recording live traffic, and you're only opening files.
  3. Open Wireshark from Applications. The first time, macOS asks whether you're sure. Click Open.
  4. You'll see the Welcome screen: a list of your network interfaces with little activity graphs, and a filter box. Ignore all of it.
  5. Menu File, then Open (Command-O). Pick 01_arp_ping.pcap from the folder I sent. The main window appears with the three panes from the last tab.
  6. Click the first row. In the middle pane, click the small arrow next to Ethernet II to open it. You're looking at the destination MAC of a broadcast. That's the lesson from session 1, in a real file.

Now open 03_dns_http.pcap the same way. It's the one below.

The filter bar

The green box above the packet list is the display filter. Type a word, press Enter, and only matching rows stay. Four filters cover most of what you'll ever need: arp, dns, tcp, http. Two more are worth knowing: ip.addr == 8.8.8.8 shows everything to or from one address, and tcp.port == 80 shows one conversation's port. The box turns green when the filter is valid and red when Wireshark doesn't understand it. Clear it to see everything again.

Interview questions

Out loud, one to two minutes each.

Interview question

You open a capture of a page load. How do you find the TCP handshake, and what do you expect to see?

What a strong answer covers
  • Filter on tcp, or on the server's address, and look for the first three rows: SYN from the client, SYN-ACK from the server, ACK from the client.
  • Flags in the Info column: [SYN], [SYN, ACK], [ACK]. Relative Seq=0 on the first two, Ack=1 after.
  • Timing: the gap between SYN and SYN-ACK is one round trip to the server, a useful number.
  • If the SYN-ACK is missing, the handshake never completed, and that's the first place the page load broke.

Follow-up: What does Wireshark's "relative sequence number" mean, and why does it matter when you compare two captures? (It subtracts the random start. Two captures of the same connection show the same relative numbers but different raw ones; always compare raw numbers across captures.)

Interview question

A capture has ten thousand rows. What do you do first?

What a strong answer covers
  • Filter. Start with the address or port of the thing you care about: ip.addr for a host, tcp.port for a service.
  • Then narrow by what you're looking for: dns to check resolution, tcp.flags.syn to find connection attempts, http for requests.
  • Look at the Time column for gaps and at Info for retransmissions and resets.
  • Follow one conversation at a time; right-click, Follow, TCP Stream shows a whole exchange as text.

Follow-up: Give one filter that shows only failed connection attempts. (tcp.flags.syn == 1 and tcp.flags.ack == 0 shows every SYN; then look for ones with no SYN-ACK after them, or filter tcp.flags.reset == 1 for refusals.)

Interview questions

Out loud, one to two minutes each.

Interview question

Describe what a complete DHCP exchange looks like in a capture, and name one way to spot a DHCP problem from one.

What a strong answer covers
  • Four rows: Discover and Request from 0.0.0.0 to 255.255.255.255 on UDP 68 to 67; Offer and ACK from the server on 67 to 68, also broadcast.
  • The Offer carries the proposed address and the options: mask, router, DNS, lease time.
  • Problem signs: Discovers with no Offer (no server reachable), or two Offers from different servers (a rogue DHCP server).
  • Filter: dhcp, or bootp in older versions.

Follow-up: The laptop sends Discovers forever and gets nothing. What's your first check? (Is the laptop on the right network at all: link up, right Wi-Fi? Then is the DHCP server alive and is anything blocking broadcasts.)

Interview question

In a capture of a web page load, which rows would you point to in order to say "the network did its job, the problem is the server"?

What a strong answer covers
  • DNS query and response with an address: name resolution worked.
  • SYN, SYN-ACK, ACK: the server is reachable and the port is open.
  • The GET, and the server's ACK of it: the request arrived.
  • Then whatever the server said: a 500, a long delay before the reply, or a reply that never comes while the connection stays open. All of those are the server's side.

Follow-up: What would the capture look like if the problem were the network instead? (Missing rows: no DNS answer, or SYNs with no SYN-ACK, or retransmissions of the GET with no ACK.)

tcpdump

tcpdump is Wireshark without the window: one line per packet, printed in a terminal. It's on every Linux server and already on your Mac, and it's what you reach for when you're logged into a machine with no screen, which is most servers. You don't need to run it today. You need to read its lines, because interviewers paste them.

Reading a line

Every line is the same shape: the time, the protocol, source and destination, and then the details for that protocol. For TCP the details are the flags, the sequence numbers, the window, and the length. The flags use one-letter codes: S for SYN, . for ACK, P for PSH, F for FIN, R for RST. So [S.] is SYN-ACK and [P.] is data with ACK.

Interview questions

Out loud, one to two minutes each.

Interview question

You're on a server with no desktop. How do you see what's happening on the network, and how do you get it somewhere you can read it comfortably?

What a strong answer covers
  • tcpdump on the server: pick the interface, use -n, filter with host or port to keep it small.
  • Watch the screen for a quick look, or -w to a file for anything longer.
  • Copy the file to a laptop (scp) and open it in Wireshark for filtering and following streams.
  • Mention capture size: filter at capture time or it fills the disk.

Follow-up: You want only the handshake attempts to port 443. What's the tcpdump filter? (port 443 and "tcp[tcpflags] & tcp-syn != 0", or simply port 443 and read the flags.)

Interview question

Here's a tcpdump line: "IP 192.168.1.23.51234 > 93.184.216.34.80: Flags [S], seq 3401242617, win 64240, length 0". Read it to me.

What a strong answer covers
  • An IPv4 packet from 192.168.1.23 port 51234 to 93.184.216.34 port 80.
  • Flags [S]: a SYN, the first message of a TCP handshake, so this is a client opening a connection to a web server.
  • seq is the raw initial sequence number; win is the receive window; length 0 means no data, as expected for a SYN.
  • What should come next: a [S.] from port 80 back to 51234 with ack 3401242618.

Follow-up: The next line is the same SYN again one second later. What happened? (No SYN-ACK arrived; the client retransmitted. Either the SYN never got there, or the reply didn't come back, or something dropped it silently.)

Where did it die?

This is the skill the interview is really after. Six captures, each a page that didn't load, each broken at a different step of the trip. The method is always the same: walk the trip from session 3 and find the first step that didn't happen. Did ARP get an answer? Did DNS? Did the SYN get a SYN-ACK? Did the server answer the request, and with what? The capture tells you exactly where the walk stops.

Interview questions

Out loud, one to two minutes each. These are the ones that get asked.

Interview question

A user says a website won't load. You have a capture from their laptop. Walk me through how you read it.

What a strong answer covers
  • Walk the trip in order. ARP: did the laptop resolve its gateway? DNS: query and a real answer? TCP: SYN, SYN-ACK, ACK to the right port? TLS: handshake complete, or an alert? HTTP: request sent, reply received, what status?
  • At each step, the capture either shows the expected row or it doesn't. The first missing or wrong row is the location.
  • Say what each signature means: silence after SYN is a drop, RST is a closed port, NXDOMAIN is a bad name, a 5xx is the server.
  • Say what you'd do next for the step that failed.

Follow-up: Everything in the capture looks perfect, 200 OK and all, and the user still sees a blank page. What now? (The network and server did their jobs; it's the browser or the page's content, which is outside the capture: look at the page's other requests, or a JavaScript error.)

Interview question

What's the difference, in a capture, between "the server is down" and "the server is up but the service isn't"? And between either of those and "a firewall is in the way"?

What a strong answer covers
  • Service not running: SYN gets an immediate RST. The host answered; nothing listens.
  • Firewall drop: SYN gets nothing, retransmitted on a timer, then the client gives up with a timeout. A reject-style firewall may instead send RST or ICMP unreachable.
  • Host down: also silence, and usually the ARP for it (if local) or the ping to it fails too. Hard to tell from a drop on the laptop side alone; a capture on the server side settles it.
  • So: RST means reachable, silence means ambiguous, and you resolve the ambiguity by capturing closer to the server or by checking a different port on the same host.

Follow-up: Port 443 times out but port 22 to the same host connects. What do you know? (The host is up and reachable; something is specifically blocking or not serving 443: a firewall rule or a stopped web server.)

Practice

Out loud first, then open the answer.

1. What are the three panes in Wireshark and what's in each?

The packet list, one row per frame. The packet details, the selected frame's envelopes outside in. The bytes, the raw hex, which you can ignore.

2. Name four display filters and say what each shows.

arp, dns, tcp, http show only that protocol. ip.addr == 8.8.8.8 shows everything to or from that address. tcp.port == 80 shows one service's conversations.

3. Read a handshake in a capture.

Three rows: [SYN] from the client with Seq=0, [SYN, ACK] from the server with Seq=0 Ack=1, [ACK] from the client with Seq=1 Ack=1. The gap between the first two is one round trip.

4. Six signatures, one line each.

ARP with no reply: host not there. DNS with no reply: resolver down. DNS "no such name": bad name. SYN with no reply: dropped, firewall. SYN then RST: port closed. Handshake plus request plus 5xx: server's code.

5. tcpdump: the one command to record a capture to a file.

sudo tcpdump -i en0 -n -w capture.pcap, then Control-C, then open the file in Wireshark.

Paper problems

a. Rows: 1 DNS query, 2 DNS response, 3 SYN, 4 SYN, 5 SYN. What happened and what's the next check?

DNS worked and returned an address. The SYN to that address got no answer three times: a silent drop, almost always a firewall, or an unreachable host. Next: can you reach any other port on that host, and what does a capture on the server side show?

b. Rows: 1 SYN, 2 SYN-ACK, 3 ACK, 4 GET, 5 ACK, then nothing for 30 seconds, then a FIN from the client. Where's the problem?

The server received the request (it acknowledged it) and never produced a reply. The network is fine; the server's application hung. Server side.

c. A DNS query at 0.000 and a second identical query at 5.000 with the same transaction ID. What does the gap tell you?

No response came back in five seconds, so the laptop retried. The resolver isn't answering, or the query isn't reaching it.

d. Which tcpdump filter shows only DNS traffic to Google's resolver?

host 8.8.8.8 and port 53.

e. In the Info column you see "80 → 51234 [RST, ACK]". Who sent it and what does it mean?

The server (port 80 is the source) is resetting the connection from the client's port 51234: no service is accepting on 80, or it's refusing this client. The host itself is reachable.

Narration rubric: a page won't load, I have a capture

  • Said you walk the trip in order rather than hunting at random.
  • ARP: checked the gateway's MAC was resolved (or the local target's).
  • DNS: checked for a query and a real answer, and named NXDOMAIN as the bad-name case.
  • TCP: checked for SYN, SYN-ACK, ACK to the right port, and named silence versus RST.
  • TLS: mentioned a failed handshake or certificate alert as a possible stop.
  • HTTP: checked the request was sent and acknowledged, and read the status code.
  • Said what each failure signature means in one sentence.
  • Said what you'd check next for the step that failed.
  • Mentioned capturing at the other end to resolve "silence."
  • Used the Time column as evidence (gaps, retransmissions).
