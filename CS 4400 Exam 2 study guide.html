Schema mapping

Mapping turns an ER diagram into relations. Underline the primary key, tag each foreign key with [fkN], and list every foreign key under the relations. This is the notation the exam grades.

Movie = (title, releaseYear, sequelTitle[fk1])
Acts_In = (actorID[fk2], title[fk3], screenTime)
fk1: sequelTitle → Movie(title)
fk2: actorID → Actor(actorID)
fk3: title → Movie(title)

Entities and attributes

Diagram elementHow it maps
Strong entity (rectangle)One relation with every simple attribute. Underline the key attribute.
Key attribute (underlined oval)The primary key. A composite key, like licenseID made of licenseNumber and state, becomes a composite PK of its parts.
Composite attribute (oval with child ovals)Store only the simple parts (fname, lname), never the parent (name).
Derived attribute (dashed oval)Don’t store it anywhere: age, totalScreenTime, YearsTenured.
Multivalued attribute (double oval)A new relation holding the owner’s PK as an FK plus the value. The PK is both together. A composite multivalued attribute, like Authors (name, phoneNum), keeps all its parts in the PK.
Weak entity (double rectangle)A relation with the owner’s full PK as an FK plus the partial key (dashed underline). PK = owner’s PK + partial key.

Relationships

RelationshipWhere the foreign key goesRelationship attributes
1:1Foreign key approach (the default): FK on either side, preferably the side with total participation. Merged relation: allowed only when both sides are total. Relationship relation: a new table holding both keys.With the FK, or in the merged or new relation
1:NFK on the N side, pointing to the 1 side.On the N side
M:NAlways a new relation with an FK to each side. PK = both FKs.In the new relation
Recursive (one entity type)Same rules, but the FK points to its own table and gets a role name: mentorID, sequelTitle. A recursive M:N becomes a new table with two FKs to the same table.Same as its cardinality
N-ary (3 or more entity types)A new relation with an FK to every participant. PK = all of them, minus the FK of any side marked 1.In the new relation
Identifying (double diamond)Already covered: the weak entity’s PK includes the owner’s key.On the weak entity, since it’s the N side
Participation

A double line means total participation. It decides whether the merged 1:1 option and the subclass-only EER option are legal. It doesn’t move a foreign key.

Worked example: Fall 2025 free response

Actor has the key actorID, a composite name, and a derived totalScreenTime. Movie has the key title, releaseYear, and a multivalued genres. Actor and Movie are M:N through Acts_In, which has screenTime, and Movie has a 1:1 recursive Sequel_Of.

  1. Strong entities first: Actor keeps actorID, fname, and lname. Drop totalScreenTime because it’s derived.
  2. Sequel_Of is 1:1 recursive, so Movie gets sequelTitle as an FK back to Movie(title).
  3. Acts_In is M:N, so it becomes its own relation keyed by both FKs, and screenTime goes with it.
  4. genres is multivalued, so it gets its own relation keyed by title and genre.
Actor = (actorID, fname, lname)
Movie = (title, releaseYear, sequelTitle[fk1])
Acts_In = (actorID[fk2], title[fk3], screenTime)
Genres = (title[fk4], genre)
fk1: sequelTitle → Movie(title)
fk2: actorID → Actor(actorID)
fk3: title → Movie(title)
fk4: title → Movie(title)

EER mapping

EER diagrams add specializations (superclass and subclasses) and union types (categories). Each has a fixed set of mapping options.

Specialization: a circle with d or o

d means disjoint: an entity is in at most one subclass. o means overlapping. A double line from the superclass to the circle means total: every entity is in some subclass. In the table, k is the superclass key.

OptionRelationsLegal whenWatch for
8A: superclass and subclassesL = (k, superclass attributes) and each S = (k[fk], subclass attributes), with k → L(k)AlwaysEach subclass PK is k, even if the subclass has its own key attribute. Book keeps pubID as its PK, and ISBN is a plain attribute.
8B: subclasses onlyEach S = (k, superclass attributes, subclass attributes). No L.Total specialization. Use it with disjoint, since overlapping stores an entity twice.The superclass’s relationship FKs move into every subclass: registerNum sits in Sedan, SUV, and Muscle.
8C: one relation, one type attributeL = (k, every attribute, type)DisjointMany NULLs
8D: one relation, Boolean flagsL = (k, every attribute, isS1, isS2, …)Overlapping, and disjoint tooMany NULLs

A relationship attached to a subclass uses that subclass’s relation. Chapter references Book, and Muscle carries its owner’s ssn.

Union types: a circle with u

A category is a subclass of two or more different superclasses. A Payer is an Employer or an InsuranceCompany.

  • Superclasses with different keys: add a surrogate key to the category, then add it as an FK in each superclass.
  • Superclasses with the same key: no surrogate. The category uses that key.
Payer = (payerID, email)
Employer = (employerID, payerID[fk1], employerName)
InsuranceCompany = (corpID, payerID[fk2], phone)
fk1: payerID → Payer(payerID)
fk2: payerID → Payer(payerID)
Exam trap

The FK goes from each superclass to the category. The category doesn’t point at its superclasses.

Checking a mapping

True/false questions show a diagram and a schema. One wrong attribute, key, or foreign key makes the answer False. Check in this order:

  1. Relations: every strong entity, weak entity, M:N relationship, multivalued attribute, and n-ary relationship has one, unless the EER option says otherwise.
  2. Attributes: only the simple parts of composites, no derived attributes, none missing, and relationship attributes on the correct side.
  3. Primary keys: weak entity = owner’s key + partial key, M:N = both FKs, multivalued = owner’s key + value, merged 1:1 = either side’s key.
  4. Foreign keys: each one points at the referenced relation’s PK, in the right direction, with every part of a composite key.
  5. EER option: the option is legal for the specialization’s constraints, and union types use a surrogate when the keys differ.

Common reasons a mapping is False

  • A weak entity, or a relation that references one, copies only part of the key.
  • An FK references a non-key column, or points the wrong way.
  • A derived attribute is stored, or a composite attribute is stored as one column.
  • A multivalued attribute is left inside its entity’s relation.
  • An M:N relationship is mapped as a plain FK.
  • A merged 1:1 relation is used when one side is partial, or 8B is used for a partial specialization.

CREATE TABLE and guarantees

Matching a schema

The correct option matches the schema exactly. Check four things in each option:

  1. Table names match the relation names.
  2. Column names match the attribute names: writtenBy, not authorId.
  3. Every underlined attribute is the PRIMARY KEY. A composite key is PRIMARY KEY (a, b).
  4. Every FOREIGN KEY names a column that exists in this table and REFERENCES the parent’s primary key column.
CREATE TABLE Author (
  authorId VARCHAR(20) PRIMARY KEY,
  fullName VARCHAR(100)
);

CREATE TABLE Book (
  bookId    VARCHAR(20) PRIMARY KEY,
  title     VARCHAR(255),
  writtenBy VARCHAR(20),
  FOREIGN KEY (writtenBy) REFERENCES Author(authorId)
    ON UPDATE CASCADE ON DELETE SET NULL
);

CREATE TABLE Trips (
  trip_id         INT PRIMARY KEY,
  taxi_service_id INT,
  plate_num       CHAR(4),
  FOREIGN KEY (taxi_service_id, plate_num)
    REFERENCES Cars(taxi_service_id, plate_num)
);

How to answer “guaranteed” questions

Try to build a valid database state that breaks the statement. If one exists, the statement isn’t guaranteed. A statement that says something is possible is guaranteed as soon as one valid state shows it.

Integrity constraints

Each question runs an INSERT, UPDATE, or DELETE against the reference database and its foreign key policies. You mark which errors happen. Questions are independent, and one statement can cause more than one error type.

The three error types

ErrorWhat breaks itTypical cause
Key integrityTwo rows with the same PK value.An INSERT or UPDATE that repeats an existing PK.
Entity integrityNULL in any PK column.An INSERT or UPDATE that puts NULL in a PK column, or ON DELETE SET NULL on an FK that’s part of a child’s PK.
Referential integrityAn FK value with no matching parent, or a parent change that RESTRICT blocks.Inserting a child whose parent doesn’t exist, or deleting a parent that RESTRICT protects.

Non-key updates, statements whose WHERE matches no rows, and CASCADE or SET NULL actions that cause nothing else all succeed.

Foreign key policies

PolicyParent row deletedParent key updated
CASCADEDelete the matching child rows, then check their children.Change the child FK values to the new key.
SET NULLSet the child FK to NULL. If that column is part of the child’s PK, it’s an entity error.Same, on update.
RESTRICT or NO ACTIONBlock the statement if any child row matches: a referential error.Block it if any child uses the old key.
SET DEFAULTSet the child FK to its default value.Same, on update.

Decision procedure

  1. Find the rows the statement touches. If the WHERE matches nothing, it succeeds.
  2. INSERT: a duplicate PK is a key error, NULL in the PK is an entity error, and each non-NULL FK value must exist in its parent or it’s a referential error.
  3. UPDATE of a PK: a duplicate new value is a key error and NULL is an entity error. Then apply the children’s ON UPDATE policies. UPDATE of an FK: the new value must exist in the parent. UPDATE of any other column: success.
  4. DELETE: never a key error. For each child table pointing at the deleted rows, RESTRICT with matches is a referential error, SET NULL on a PK column is an entity error, and CASCADE deletes those children, so repeat this step for them.
  5. Mark every type you found.

Worked chain: Fall 2025 Q4

DELETE FROM Members WHERE legal_name LIKE 'C%C%'; matches Charlie Chen, member 3. Follow every policy that points at member_id:

  • Repositories.owner_id is CASCADE, so repo 111 is deleted too. Its commits cascade away, but PullRequests (PR 5) and Issues (111, 4) both RESTRICT deleting repo 111: a referential error.
  • Issues.opened_by is SET NULL and part of the Issues PK, so (001, 3) would become (001, NULL): an entity error. Reviews.reviewed_by is also SET NULL inside its PK.
  • PullRequests.author_id is SET NULL, but author_id isn’t in that PK, so it’s fine.

Answer: entity and referential.

Joins and tracing

Join types

JoinKeepsColumns with no match
[INNER] JOIN … ONOnly pairs where ON is true.Not applicable.
LEFT JOINEvery row of the left side.Right-side columns are NULL.
RIGHT JOINEvery row of the right side, the table named after RIGHT JOIN.Left-side columns are NULL.
CROSS JOINEvery pair: rows × rows.Not applicable. Filter with WHERE.
FULL OUTER JOINNot available in MySQL. Use a LEFT JOIN UNION a RIGHT JOIN.Both sides can be NULL.

Chained joins run left to right

A LEFT JOIN B ON … RIGHT JOIN C ON … means (A LEFT JOIN B) RIGHT JOIN C. The result keeps every C row and drops A rows that match no C row. That’s the Fall 2025 tracing question: every member stays.

ON versus WHERE in an outer join

SELECT d.dname, e.lname
FROM department d
LEFT JOIN employee e
  ON e.dno = d.dnumber AND e.sex = 'F';

This keeps every department. A department with no women shows one row with a NULL lname. Moving e.sex = 'F' to WHERE drops those departments, which turns the LEFT JOIN into an inner join.

NULL rules

  • NULL = NULL isn’t true, so NULLs never match in ON. Test with IS NULL or IS NOT NULL.
  • MySQL sorts NULLs first in ascending order and last in descending order.
  • Joining on part of a key can match unrelated rows. Spring 2026 Q2 joins cars to trips on plate_num alone, and plate 1234 exists under two taxi services.
  • Without ORDER BY, row order isn’t guaranteed. Answer keys list rows in table order.

Logical order of a query

  1. FROM and JOINs
  2. WHERE
  3. GROUP BY
  4. HAVING
  5. SELECT, which creates the aliases
  6. DISTINCT
  7. ORDER BY
  8. LIMIT and OFFSET

Tracing by hand

  1. Write the header row from the SELECT aliases, in order.
  2. Build the join one step at a time, writing NULLs for unmatched outer rows.
  3. Apply WHERE, then grouping, then ORDER BY.
  4. Apply LIMIT last, and write NULL wherever a value is missing.

The LEFT JOIN + COUNT trap

SELECT d.dept_id, COUNT(e.emp_id) AS employee_count
FROM departments d
LEFT JOIN employees e ON d.dept_id = e.dept_id
GROUP BY d.dept_id;

A department with no employees still gets one joined row, with NULLs on the employee side. COUNT(*) counts that row as 1. COUNT(e.emp_id) skips the NULL and returns 0. This was Fall 2025 design Q2.

Joins repeat rows

After you join employee to works_on, an employee appears once per project, so AVG(e.salary) weights that employee once per project. Spring 2026 coding Q5 expects exactly this. Use a subquery or COUNT(DISTINCT …) when you need one value per employee.

ONLY_FULL_GROUP_BY

The coding exam turns this mode on. Every column in SELECT, HAVING, or ORDER BY must be in GROUP BY, inside an aggregate, or determined by a primary key you grouped by. Group by every non-aggregated column you select.

SELECT dno, lname, AVG(salary)
FROM employee
GROUP BY dno;

This query fails because lname isn’t grouped or aggregated.

  • ROUND(AVG(salary), 2) rounds to 2 decimal places.
  • GROUP BY puts all NULLs in one group.

Subqueries and set operations

FormMeaningExample
Scalar subqueryReturns one value to compare with =, <, or >=.salary < (SELECT AVG(salary) FROM employee)
IN, NOT INThe value is, or isn’t, in the returned list.ssn IN (SELECT essn FROM works_on)
EXISTS, NOT EXISTSTrue when the inner query returns any row. Usually correlated.NOT EXISTS (SELECT * FROM works_on w WHERE w.essn = e.ssn)
ANY, ALLCompare with some, or every, returned value.salary > ALL (SELECT salary FROM employee WHERE dno = 5)
Derived tableA subquery in FROM. It needs an alias.FROM (SELECT dno, AVG(salary) AS a FROM employee GROUP BY dno) AS t
Traps
  • NOT IN returns no rows if the list contains a NULL. Use NOT EXISTS, or filter the NULLs out.
  • > ALL of an empty list is true. > ANY of an empty list is false.
  • A scalar subquery that returns 2 or more rows is an error.
  • Comparing with a scalar subquery that returns NULL is never true, so no rows come back.

“Only” and “every” questions

“Employees whose every session is over 4 hours” means no session is 4 hours or less. Both of these work:

SELECT ssn FROM time_frames
GROUP BY ssn
HAVING MIN(duration) > 4;

SELECT DISTINCT t.ssn FROM time_frames t
WHERE NOT EXISTS (SELECT * FROM time_frames x
                  WHERE x.ssn = t.ssn AND x.duration <= 4);

Set operations

  • UNION removes duplicates. UNION ALL keeps them.
  • Both sides need the same number of columns with compatible types. Column names come from the first SELECT.
  • One ORDER BY at the end sorts the whole result.
  • MySQL 8.0.31 and later support INTERSECT and EXCEPT. On older versions, use IN for an intersect and NOT IN or NOT EXISTS for an except.
SELECT ssn FROM in_office WHERE building = 'Main'
UNION
SELECT ssn FROM remote_access;

Views

A view is a named, stored query. It stores no data: MySQL reruns the query every time you use the view, so the result is always current. MySQL has no materialized views.

CREATE OR REPLACE VIEW high_earners AS
SELECT ssn, fname, lname, salary
FROM employee
WHERE salary > 40000;

SELECT * FROM high_earners WHERE lname LIKE 'W%';

DROP VIEW high_earners;

Why use views

  • Hide a complex query behind a simple name.
  • Limit access: expose some columns or rows without granting the base table.
  • Reuse the same logic in many queries.
  • Keep queries working when the base tables change.

Updatable views

You can INSERT, UPDATE, or DELETE through a view only when each view row maps to exactly one base-table row. In practice that means one base table, and no aggregates, GROUP BY, HAVING, DISTINCT, or UNION. An INSERT also needs every NOT NULL column that has no default. WITH CHECK OPTION rejects changes that would push a row outside the view’s WHERE.

Views on the coding exam

  • Every answer is a view named practiceQuery1 to practiceQuery5.
  • ORDER BY and LIMIT inside a view work in MySQL.
  • The grader compares values by column position, so keep the column order the prompt asks for. Column names don’t matter.

Keys and design

TermMeaning
SuperkeyAny set of attributes that uniquely identifies a row.
Candidate keyA minimal superkey: removing any attribute makes it non-unique.

Picking a primary key from a scenario

  1. Say what one row represents: one reservation, one surgery.
  2. Find the rule that stops two rows from repeating, like “no two surgeries for the same surgeon at the same time.”
  3. Use the attributes in that rule.
  4. Drop extras. If a smaller set is already unique, a bigger option isn’t minimal.

Identifiers that are only unique inside something else, like a room number inside a branch. They pull the outer key into the PK.

Crib sheet

The whole exam on one page. Copy it onto your sheet, then add your own weak spots.

Mapping

  • Strong entity: every simple attribute, key underlined.
  • Composite: simple parts only. Derived: drop it.
  • Multivalued: new relation (owner key, value), both in the PK.
  • Weak entity: owner’s full key + partial key = PK.
  • 1:1: FK on either side, preferring the total side. Merge only if both sides are total.
  • 1:N: FK on the N side. M:N: new relation, PK = both FKs.
  • Relationship attributes go where the FK goes, or in the new relation.
  • 8A always. 8B needs total (use with disjoint). 8C disjoint. 8D overlapping.
  • Union with different keys: surrogate key, FK in each superclass.

Constraints

  • Key: duplicate PK. Entity: NULL in the PK. Referential: missing parent, or a RESTRICT block.
  • A DELETE never causes a key error.
  • SET NULL on an FK inside a PK: entity error.
  • CASCADE: follow the chain to the next RESTRICT.
  • WHERE matches nothing: success. Non-key update: success.
  • UNIQUE allows many NULLs. FK + UNIQUE: at most one child per parent.
  • FK + NOT NULL: every child has a parent. Nothing forces a parent to have children.

SQL

  • Order: FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT.
  • LEFT keeps left rows, RIGHT keeps right rows, and chains run left to right.
  • In an outer join, filters in ON keep rows and filters in WHERE drop them.
  • COUNT(*) counts NULL rows. COUNT(col) doesn’t.
  • NOT IN with a NULL in the list returns no rows.
  • NULLs sort first in ascending order.
  • 2nd row: LIMIT 1 OFFSET 1. 2nd to 5th: LIMIT 4 OFFSET 1.

Coding

  • Strings in single quotes (ANSI_QUOTES).
  • || concatenates. It isn’t OR.
  • Group by every non-aggregated column.
  • Exact matches use =. Patterns use LIKE.
  • > for “exceeding,” >= for “at least.”
  • Don’t type in values you looked up. The grader changes the data.
