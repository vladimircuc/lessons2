How one computer runs everything at once

Last time: the CPU, caches, and virtual memory. This time: the program in charge of all of it. Processes, threads, the scheduler, interrupts, and how to read a sick server.

Start here

Session 1 was hardware: a CPU that fetches and executes, caches that hide slow memory, an MMU that translates addresses through a table. It kept saying "the OS builds the table," "the OS handles the fault," "the OS switches to another process." This session is that OS.

The operating system is a program. It happens to be the one program that's allowed to touch the hardware directly, and its job is to share one computer among many programs so that each one believes it has the machine to itself. Everything in this session is a piece of that sharing: sharing the CPU (scheduling), sharing memory (processes), sharing devices (interrupts and I/O), and sharing safely (threads and locks).

The story this session tells

  1. The kernel runs in a privileged mode; your program runs in a restricted one. The only way across is a system call.
  2. A process is a running program plus everything the kernel tracks about it. Processes are born by fork, transformed by exec, and die into zombies until someone collects them.
  3. With more processes than cores, a scheduler hands out time slices and a timer interrupt takes the CPU back.
  4. Threads share a process's memory, which is fast and dangerous. Locks make it safe; misused locks make it stop.
  5. Devices interrupt the CPU when they have something. That's how a packet on the wire becomes bytes in your program.
  6. A GPU is a different kind of processor built on a different bet: thousands of slow cores instead of a few fast ones. The difference is one idea, and it's the reason the network matters so much in an AI data center.
  7. All of it is visible from a shell, if you know which columns to read.

The kernel and system calls

The kernel is the core of the operating system: the part that's always in memory and owns the hardware. It decides which process runs, which frame each page gets, what happens when a device interrupts. It is code like any other, but it runs in a special state.

Two modes

The CPU has a mode bit. In kernel mode, every instruction is allowed: talk to devices, change page tables, halt the machine. In user mode, the dangerous instructions fault instead of executing, and the only memory reachable is what the process's own page table maps. Your programs run in user mode. The kernel runs in kernel mode. The hardware enforces the line, which is why a buggy program can crash itself but not the machine.

The one door: system calls

If user mode can't touch a disk, how does a program read a file? It asks. A system call is a request to the kernel, and the mechanism is a special instruction, the trap, that does three things at once: flips the mode bit to kernel, saves where the program was, and jumps to one fixed address inside the kernel. The kernel reads which call was requested and its arguments, checks that they're legal (that buffer had better be inside your own memory), does the work, and executes the return path, which flips the mode back and lands the program on the next instruction.

Linux has around 350 system calls. You need a dozen by name: open, read, write, close for files; socket, connect, accept, send, recv for the network; fork, exec, wait, exit for processes; mmap for memory. Everything your language's standard library does eventually bottoms out in these. printf is a library function that formats text and then calls write. malloc is a library function that hands out pieces of memory it got from the kernel with mmap or brk.

What a call costs

The mode switch, the argument checking, and the cache and pipeline disruption cost hundreds of nanoseconds to a microsecond, hundreds of times an ordinary instruction. That's why reading a file one byte at a time is catastrophically slow and why every language buffers I/O: read 64 KB in one call, hand out bytes from the buffer for free. It's also why a system call that can't finish immediately doesn't spin. If you recv on a socket with nothing in it, the kernel marks your process blocked, puts it to sleep, and runs something else until data arrives. That's the scheduler's job, two tabs from now, but you can watch it happen in the simulation below.

Interview question

What's the difference between user mode and kernel mode, and why does the split exist?

What a strong answer covers
  • A CPU mode bit. Kernel mode can execute every instruction and touch all memory; user mode can't touch devices, page tables, or other processes' memory.
  • The hardware enforces it, so a buggy or malicious program can't take down the machine or read another program's data.
  • The only way from user to kernel is a trap: a system call the program requests, or an interrupt or fault the hardware forces.
  • Cost: crossing the line isn't free, which shapes how programs do I/O.

Follow-up: What happens if a user-mode program tries to execute a privileged instruction? (The CPU faults into the kernel, which typically kills the process with an illegal instruction signal.)

Interview question

What is a system call? Walk me through what happens when my program calls read() on a file.

What a strong answer covers
  • The library wrapper puts the call number and arguments in registers and executes the trap instruction.
  • The CPU flips to kernel mode, saves the user registers, jumps to the kernel's entry point.
  • The kernel validates the file descriptor and the buffer address, finds the file, and either copies from the page cache or issues a disk read and blocks the process until it completes.
  • Return: registers restored, mode back to user, read() returns the byte count. Two mode switches minimum.

Follow-up: Where does the data sit between the disk and your variable? (In the kernel's page cache, in RAM, then copied into your buffer. A second read of the same file skips the disk entirely.)

Interview question

Why is it much faster to read a file in 64 KB chunks than one byte at a time, when the total bytes are the same?

What a strong answer covers
  • Each read is a system call: mode switch, validation, cache disruption. Hundreds of nanoseconds each, regardless of size.
  • One byte per call means a million calls per megabyte; 64 KB per call means sixteen.
  • This is why language runtimes buffer: the library does one big read and serves your small ones from user-space memory.
  • Bonus: the same logic applies to writes and to network sends. Batching across the kernel boundary is a general principle.

Follow-up: Is there a downside to a huge buffer? (Memory, and latency: you may wait to fill it before acting on the first bytes. There's a sweet spot, usually tens to hundreds of KB.)

Processes

A process is a running program plus everything the kernel has to remember about it: its own virtual address space (session 1), a PID, a parent, a current user, its open files, and, when it isn't running, a saved copy of every register including the program counter. The program is the recipe; the process is the cooking.

What's inside

The address space has a conventional shape. Code at the bottom, then global data, then the heap growing up as you allocate, shared libraries in the middle, the stack at the top growing down, and unmapped gaps between. Touching a gap is a segfault.

The kernel also keeps a table of the process's file descriptors: small integers naming open files, sockets, and pipes. Three exist from birth: 0 is standard input, 1 is standard output, 2 is standard error. Every open or socket call returns the next free number. That's what the fd argument to read and write is.

Birth, transformation, death

On Linux, new processes come from exactly one place. fork() makes a copy of the calling process: same code, same data, same open files, a new PID. The copy is cheap because the pages are shared until one side writes (copy-on-write). fork returns twice: the child's PID in the parent, zero in the child, which is how each side knows who it is.

exec() replaces the calling process's program with a new one. The address space is thrown away and rebuilt from the new binary; the PID and the open files stay. A shell runs ls like this: fork, the child execs ls, the parent calls wait() until the child exits.

When a process calls exit(), its memory and files are released, but its table entry stays until the parent calls wait() to collect the exit status. In that window it's a zombie: dead, taking up nothing but a PID. If the parent dies first, the child is an orphan and the kernel reparents it to PID 1, which reaps zombies as a matter of routine. Every process on the machine descends from PID 1 (systemd or init).

Interview question

What is a process, and what does the operating system keep track of for each one?

What a strong answer covers
  • A running instance of a program with its own virtual address space.
  • Kernel state: PID and parent, saved registers and PC, the page table, open file descriptors, current directory, user and permissions, scheduling state and priority, exit status.
  • Address space layout: code, data, heap, libraries, stack.
  • Strong answers distinguish program (a file) from process (a running thing) and note one program can be many processes.

Follow-up: Two copies of the same program are running. What do they share? (The code pages in RAM, read-only, mapped into both. Nothing else unless they set up shared memory.)

Interview question

Explain fork and exec, and how a shell uses them to run a command.

What a strong answer covers
  • fork clones the caller: new PID, copy of the address space (copy-on-write), same open files. Returns the child PID to the parent and 0 to the child.
  • exec replaces the caller's program: new address space from the binary, same PID, files stay open.
  • Shell: fork; in the child, set up redirections on file descriptors, then exec the command; in the parent, wait for the child.
  • Why two calls instead of one "spawn": the gap between fork and exec is where redirection and pipes get set up, using the inherited file descriptors.

Follow-up: How does "ls > out.txt" work? (Between fork and exec, the child opens out.txt and makes it file descriptor 1. ls then writes to stdout as usual and never knows.)

Interview question

What is a zombie process, why does it exist, and how do you get rid of one?

What a strong answer covers
  • A process that has exited but whose parent hasn't called wait. Only the table entry remains, holding the exit status.
  • It exists so the parent can find out how the child ended. It costs a PID slot and nothing else.
  • kill does nothing to it; it's already dead. You fix or kill the parent. If the parent dies, PID 1 adopts and reaps the zombie.
  • Thousands of zombies means a parent that forks and never waits, a real bug.

Follow-up: How would you find a zombie's parent from a shell? (ps -o ppid= -p the zombie's PID, or look at the PPID column in ps.)

Scheduling and context switches

A laptop runs a few hundred processes on four or eight cores. Most of them are asleep, waiting for something, but whenever more processes are ready to run than there are cores, something has to pick. That's the scheduler, a piece of the kernel that runs every few milliseconds and on every event that changes who's ready.

Three states

At any moment a process is running on a core, ready (could run, waiting for a core), or blocked (waiting for something else: disk, network, a keypress, a lock, a sleep timer). Blocked processes cost the scheduler nothing; they aren't candidates. The transitions are the whole story: running becomes ready when its turn ends, running becomes blocked when it asks for something slow, blocked becomes ready when the thing arrives.

Time slices and preemption

A running process would happily run forever, so the kernel sets a timer. When the time slice (also called a quantum, a few milliseconds) expires, the timer interrupt fires, the kernel takes the CPU back, and the scheduler picks the next ready process. Taking the CPU away from a running process is preemption. Without it, one infinite loop would freeze the machine.

Policies

The simplest policy is first come, first served: run each ready process until it blocks or finishes. Simple, and awful for interactive work: your text editor waits behind a video encoder. Round robin fixes that by rotating through the ready queue with a fixed slice. Real schedulers layer priorities on top: Linux's default gives every process a fair share of CPU, weighted by its nice value, and quietly favors processes that sleep a lot, because those are the interactive ones.

The slice length is a trade. Short slices mean responsive, because nobody waits long for a turn, but every turn ends in a context switch, and those aren't free. Long slices waste less but make interactive programs sluggish.

The context switch

Switching processes means saving everything the CPU knows about the current one (registers, program counter, stack pointer), loading the next one's saved state, and pointing the MMU at the next one's page table. The direct cost is a microsecond or so. The indirect cost is bigger: the new process finds the caches and the TLB full of the old process's data, and spends its first thousands of cycles missing. Switching between threads of the same process is cheaper, since the page table doesn't change.

The number you'll see everywhere on Linux. It's the average number of processes that are runnable or in uninterruptible disk wait, over the last 1, 5, and 15 minutes. Interview question

What is a context switch, and what makes it expensive?

What a strong answer covers
  • Saving the running process's registers and PC, loading the next one's, and switching the page table pointer.
  • Direct cost: about a microsecond of kernel work.
  • Indirect cost, the bigger one: caches and TLB are full of the old process's data, so the new one misses heavily at first.
  • Thread switches within a process are cheaper because the address space doesn't change.

Follow-up: A program does a system call that returns immediately. Was there a context switch? (No. Two mode switches, same process throughout. Context switch means a different process or thread takes the CPU.)

Interview question

One core, two programs: a video encoder that always has work, and a text editor that mostly waits for keystrokes. How should the scheduler share the CPU, and why?

What a strong answer covers
  • The editor should win whenever it's ready: it needs the CPU for a moment and then blocks again, so giving it priority costs the encoder almost nothing.
  • The encoder soaks up whatever is left. It's CPU-bound; a little latency is invisible.
  • Mechanism: preemption with a short enough slice, plus favoring processes that sleep a lot (which is what Linux's scheduler does).
  • Pure first come, first served would make the editor unusable.

Follow-up: What's the danger in always favoring interactive processes? (Starvation: a CPU-bound job never runs if interactive ones keep waking. Real schedulers guarantee a minimum share.)

Interview question

Describe the states a process can be in and what moves it between them.

What a strong answer covers
  • Running, ready, blocked (plus created and terminated, and Linux's zombie).
  • Running to ready: slice expired or a higher-priority process woke (preemption).
  • Running to blocked: it asked for something slow (I/O, a lock, sleep).
  • Blocked to ready: the thing arrived, usually via an interrupt handler marking it runnable.
  • Ready to running: the scheduler picked it.

Follow-up: Can a process go from blocked straight to running? (No. It becomes ready first; the scheduler still has to choose it, though it may do so immediately.)

Threads and concurrency

A thread is one path of execution inside a process. It has its own stack, its own registers, its own program counter, so the scheduler can run it independently, but it shares the process's address space with its sibling threads: the same heap, the same globals, the same code, the same open files. A process starts with one thread. It can create more.

Why threads

Two reasons. Parallelism: on a multicore machine, four threads can run on four cores at once. And overlap: a thread that blocks waiting for the network doesn't stop the others, so a web server can handle many requests with one thread each. The price is the shared memory that makes threads convenient.

The race

counter += 1 is not one operation. It's three: load the value into a register, add one, store it back. If two threads do this at the same time on the same variable, their steps can interleave: both load 5, both add, both store 6, and one increment is lost. That's a race condition: the result depends on timing you don't control. It might work a million times and then not. The piece of code that must not be interleaved is a critical section.

The fix, and the new problem

A mutex (mutual exclusion lock) is an object only one thread can hold at a time. Take it before the critical section, release it after; a second thread that tries to take it blocks until the first releases. The updates can no longer interleave. The cost is that the threads now take turns through that section, and if they spend most of their time there, you've serialized your parallel program.

Locks introduce their own failure. Thread 1 holds lock A and waits for lock B. Thread 2 holds lock B and waits for lock A. Neither will ever release what the other needs. That's deadlock, and the program simply stops, using no CPU, forever. The standard prevention: every thread acquires locks in the same global order, so the cycle can't form. Other tools exist (semaphores for counting, condition variables for waiting on a state, atomic instructions for single-variable updates), but mutex, race, and deadlock are the three words the interview wants.

Python, since you write it. CPython has a global interpreter lock, the GIL: only one thread runs Python bytecode at a time. Threads still help when they spend their time waiting on I/O, because the waiting thread releases the GIL. They don't help a CPU-bound loop; for that you use multiprocessing, or a library that does the heavy work outside Python. And the GIL does not save you from races: counter += 1 can still be interrupted between its bytecodes.

Interview question

Process versus thread: what's the difference, and when would you choose each?

What a strong answer covers
  • A process has its own address space; threads share one. Threads have their own stack, registers, and PC.
  • Threads: cheap to create and switch, trivial to share data, one crash kills all. Processes: isolated, heavier, communicate through pipes, sockets, or shared memory.
  • Threads for parallel work on shared data or overlapping I/O in one program. Processes for isolation and robustness (browser tabs, separate services).
  • Bonus: in Python the GIL pushes CPU-bound parallelism toward processes.

Follow-up: Why does a browser use a process per tab instead of a thread per tab? (Isolation: one tab crashing or being exploited can't read or take down the others.)

Interview question

Two threads each increment a shared counter a million times. The final value is less than two million. What happened, and how do you fix it?

What a strong answer covers
  • Increment is load, add, store. Interleaved between threads, two loads can happen before either store, and one increment is lost. A race condition.
  • Fix: make the increment a critical section with a mutex, or use an atomic increment instruction, or give each thread its own counter and sum at the end.
  • Trade-off: the mutex serializes the increments; the per-thread counters avoid contention entirely.
  • Strong answers can name the exact interleaving that loses an update.

Follow-up: Would the bug show up in a test that runs it once? (Maybe not. Races are timing-dependent; it can pass a thousand times. That's what makes them dangerous.)

Interview question

What is a deadlock? Give a concrete example and two ways to prevent it.

What a strong answer covers
  • Two or more threads each waiting for a resource another holds, in a cycle, so none can proceed. The program hangs using no CPU.
  • Example: thread 1 locks A then B; thread 2 locks B then A; each gets its first lock and waits forever for the second.
  • Prevent: a global lock ordering so cycles can't form; or hold only one lock at a time; or try-lock with timeout and back off; or a single coarse lock.
  • Detect: a stuck program with 0 percent CPU and threads all in a waiting state.

Follow-up: Can you deadlock with a single lock? (Yes, if a thread tries to take a lock it already holds and the lock isn't re-entrant. It waits for itself.)

Interrupts and I/O

Devices are slow and they don't run on the CPU's clock. A keypress comes when the human presses it; a packet arrives when the network delivers it; a disk read finishes milliseconds after it was asked for. The CPU could sit and check, over and over, whether the thing has happened yet. That's polling, and it wastes the CPU. Instead, devices raise interrupts.

What an interrupt does

A device pulls a wire. Between two instructions, the CPU notices, saves where it was, flips to kernel mode, and jumps to the kernel's interrupt handler for that device, exactly the way a trap does for a system call. The handler does the minimum: acknowledge the device, move or note the data, mark any process that was waiting for it as ready. Then the CPU restores what it was doing and continues. Whatever program was running never knows it was paused; a few microseconds vanished.

The timer is a device too. Its interrupt every few milliseconds is how the scheduler gets control back from a running process. Without it, preemption would be impossible.

DMA

Copying bytes from a device into RAM would eat the CPU if the CPU did it. So devices do it themselves: DMA, direct memory access, lets a network card or disk controller write straight into RAM at an address the kernel gave it, and raise an interrupt when the whole transfer is done. The CPU is involved at the start and the end, not for every byte.

Blocking and not blocking

The default is blocking I/O: your recv puts the process to sleep until data exists, and the interrupt handler that delivers the data is what wakes it. Simple, and fine when one thread handles one connection. A server with ten thousand idle connections can't afford ten thousand sleeping threads, so it uses non-blocking I/O plus a call like epoll that says "put me to sleep until any of these sockets has something," then handles whichever woke up. One thread, ten thousand sockets. That's how nginx and Node.js work, and it's worth one sentence in an interview.

Out loud, one to two minutes each. The second one is the big one.

Interview question

What is an interrupt, and how is it different from a system call?

What a strong answer covers
  • Both enter kernel mode through a trap and run a kernel handler.
  • A system call is synchronous and requested by the running program. An interrupt is asynchronous and forced by hardware (a device or the timer); the running program is just interrupted.
  • Interrupt handlers do the minimum and return; the timer interrupt is how preemption works.
  • Bonus: a page fault is a third kind of entry, a synchronous fault caused by the program without asking.

Follow-up: Why should an interrupt handler be short? (Other interrupts and the running process are stalled while it runs; heavy work is deferred to later kernel work or to the woken process.)

Interview question

Walk me through what happens from a packet arriving at the network card to recv() returning in my program.

What a strong answer covers
  • The program is blocked in recv; the scheduler is running something else.
  • The NIC matches the destination MAC, DMA-writes the frame into a kernel buffer in RAM, raises an interrupt.
  • Kernel mode: the driver hands the frame to the stack. Ethernet header says IPv4; IP says it's for me and TCP; TCP finds the socket by the four-tuple, checks the sequence number, queues the data in the socket's receive buffer, schedules an ACK.
  • The handler marks the blocked process runnable. Later the scheduler switches to it; the kernel copies from the socket buffer to the user buffer; recv returns the byte count in user mode.
  • Layers named at each step: hardware, kernel network stack, scheduler, user program.

Follow-up: How many times were the bytes copied? (Roughly twice: DMA into the kernel buffer, then kernel to user buffer. Zero-copy techniques exist to avoid the second.)

Interview question

A web server has ten thousand connections open, most of them idle. One thread per connection or something else? Why?

What a strong answer covers
  • Ten thousand blocked threads means ten thousand stacks and heavy scheduling overhead, mostly for threads doing nothing.
  • Instead: non-blocking sockets plus epoll (or kqueue, or IOCP). One thread sleeps until any socket is ready, then handles the ready ones.
  • This is the event loop model: nginx, Node.js, Python asyncio.
  • Trade-off: CPU-heavy requests block the loop, so you pair it with a small pool of worker threads.

Follow-up: How does the kernel know which sockets are ready without the thread polling them? (The same interrupt path: packet arrives, TCP queues data, and the socket is flagged; epoll returns the flagged ones.)

GPUs versus CPUs

Everything so far has been about one kind of processor. A GPU is a different kind, built on a different bet, and since Meta's data centers are increasingly built around them, interviewers ask. The good news is that the whole difference fits in one sentence: a CPU is built to finish one thing as fast as possible; a GPU is built to finish an enormous number of identical things per second. Latency versus throughput, again.

What a CPU spends its transistors on

Look back at session 1. Branch predictors, out-of-order execution, deep pipelines, three levels of cache: nearly all of a CPU core is machinery for making a single instruction stream fast and for hiding memory latency from it. The actual arithmetic units are a small corner of the chip. That's the right design for code that's branchy, serial, and unpredictable, which is most code.

What a GPU spends them on

A GPU throws that machinery away and spends the silicon on arithmetic. A modern GPU has thousands of small, simple cores, each far slower and dumber than a CPU core: little cache, no branch prediction, in-order. It makes that work with two tricks.

  • Lockstep execution. Cores are grouped (NVIDIA calls a group of 32 a warp), and every core in the group executes the same instruction at the same time on different data. One instruction fetch, one decode, 32 results. That model is called SIMT: single instruction, multiple threads.
  • Latency hiding by volume. When a warp waits on memory, the GPU doesn't stall; it switches to one of the thousands of other warps that are ready. It hides latency with sheer parallelism instead of caches. That only works if there are thousands of independent threads to switch between.

The price of lockstep: if threads in a warp want different branches, the warp runs both paths one after the other, with the threads that didn't take each path switched off. That's divergence, and it's why branchy code runs badly on a GPU.

Memory is the other half

A GPU has its own memory, VRAM (HBM on data center parts), with staggering bandwidth: 1 to 3 TB/s, against about 100 GB/s for a CPU's RAM. It needs it, because thousands of cores are hungry. But that memory is on the card. Data in the computer's RAM has to be copied across PCIe (or NVLink on high-end systems) before the GPU can touch it, at tens of GB/s, and the results copied back. That copy is often the whole story: for a small job, moving the data takes longer than the CPU would take to just do the work. The first rule of GPU programming is keep the data on the GPU.

How a program uses one

The CPU is the host; the GPU is the device. The host copies data over, launches a kernel (the GPU word for a function run by thousands of threads at once, one per element), waits, and copies results back. To the OS, the GPU is a device like any other from tab 5: a driver talks to it, DMA moves the data, and the OS does not schedule the GPU's threads; the GPU has its own hardware scheduler. Frameworks like PyTorch hide all of this, which is exactly why people are surprised when a tiny model runs slower on the GPU than on the CPU.

Amdahl's law, in one line

No amount of parallel hardware speeds up the part of a job that's serial. If 10 percent of a job can't be parallelized, the best possible speedup is 10x, no matter how many GPUs you add. This is Amdahl's law, and it's the reason "just throw GPUs at it" has a ceiling.

speedup = 1 / (serial fraction + parallel fraction / number of processors)
example: 10% serial, 1,000 processors: 1 / (0.10 + 0.90 / 1000) = 9.9x

Why the network team cares. Training a large model doesn't fit on one GPU, so it runs on thousands at once, and after every step they have to exchange and combine their results before the next step can start. Every GPU waits for the slowest exchange. That makes the network between them the bottleneck of the whole job, which is why AI data centers use dedicated high-bandwidth, low-latency fabrics (InfiniBand or RoCE, with RDMA so data moves GPU to GPU without the CPU copying it) and why a lost packet is a much bigger deal there than on a web server network. You don't need the protocol details this month. You need the sentence: the GPUs spend a lot of their time waiting on the network, so the network's latency and loss directly set training speed.

Interview questions

Out loud, one to two minutes each.

Interview question

Explain the difference between a CPU and a GPU. Why not use GPUs for everything?

What a strong answer covers
  • CPU: a few fast cores optimized for the latency of one instruction stream, with big caches, branch prediction, out-of-order execution. GPU: thousands of simple cores optimized for throughput, running the same instruction across many data elements in lockstep.
  • GPUs hide memory latency by switching between warps rather than with caches, so they need massive parallelism to be efficient.
  • Why not everything: most code is serial and branchy, small problems can't cover the transfer and launch cost, divergence wastes the lockstep, and the GPU can't run the operating system or handle I/O.
  • Strong answers say "latency versus throughput" and mention data transfer.

Follow-up: What kind of code would run terribly on a GPU even though it's parallel? (Parallel but branchy or pointer-chasing: each thread doing different work, or walking linked structures. The warps diverge and the memory accesses scatter.)

Interview question

My matrix multiply is slower on the GPU than the CPU for 100 by 100 matrices but fifty times faster at 10,000 by 10,000. Explain.

What a strong answer covers
  • Fixed costs: copying the matrices to the GPU over PCIe, launching the kernel, copying the result back. Tens of microseconds minimum, regardless of size.
  • At 100 by 100 there's so little arithmetic that the CPU finishes before the GPU has the data. At 10,000 by 10,000 the arithmetic is a trillion operations and dwarfs the transfer.
  • Also: a tiny problem can't keep thousands of cores busy, so the GPU runs mostly empty.
  • Practical fix for the small case: keep the data on the GPU across many operations, or just use the CPU.

Follow-up: In the widget, why does the plain array add never favor the GPU when the data has to be copied, and what changes that? (One operation per twelve bytes moved: the copy alone costs more than the CPU's work. Doing more arithmetic per element, or keeping the data resident on the GPU, flips it. Matrix multiply does thousands of operations per element moved.)

Interview question

Why would a network engineering team at a company like Meta care about GPUs at all?

What a strong answer covers
  • Large models train across thousands of GPUs, and after each step every GPU has to exchange results with the others before continuing.
  • That synchronization makes the network the critical path: every GPU waits for the slowest transfer, so latency, bandwidth, and packet loss directly set how fast training runs, and how much of a very expensive cluster sits idle.
  • So AI clusters get dedicated fabrics with very high bandwidth and low latency (InfiniBand or RoCE), RDMA so data moves between GPU memories without the CPU copying, and lossless configurations, because a retransmit stalls the whole job.
  • Strong answers connect it to session 1 of networking: same envelopes, same switches, but the traffic pattern is all-to-all bursts instead of many small independent flows.

Follow-up: Why is a dropped packet worse on a training network than on a web serving network? (On the web, one user waits a few milliseconds. In training, thousands of GPUs wait for that one retransmission before anyone can proceed.)

The state column

R running or runnable. S sleeping, waiting for something interruptible (most processes, most of the time). D uninterruptible sleep, almost always waiting on disk; a machine full of D states has a storage problem. Z zombie. T stopped. The load average counts R and D, which is why disk trouble shows up as high load with idle CPUs.

Memory columns

VIRT is everything the process has mapped, including files and reserved-but-untouched space. It's usually huge and usually meaningless. RES (or RSS) is what's actually resident in RAM. That's the one you watch. SHR is the part shared with other processes, mostly libraries. In free, "free" is misleading: the kernel uses spare RAM for the page cache, which it gives back instantly. Read available instead.

The playbook

  1. Load versus cores. Load above core count means queuing. Then ask: for CPU or for disk?
  2. CPU line. High us means user programs computing. High sy means kernel work, often I/O or a syscall storm. High wa means everyone's waiting for disk.
  3. Memory. available near zero and swap climbing means you're heading for thrashing. Find the process with the biggest RES.
  4. Processes. Sort by %CPU or %MEM. Look for D states, Z states, or one process with N times 100 percent.
  5. Then narrow. strace or /proc on the suspect; iostat for disks; ss for sockets.

Interview questions

Out loud, one to two minutes each.

Interview question

A production server is slow. What are the first five commands you run, and what are you looking for in each?

What a strong answer covers
  • uptime or top: load average versus core count. Queuing or not?
  • top's CPU line: us versus sy versus wa. Compute-bound, kernel-bound, or disk-bound?
  • free -h: available and swap used. Heading for thrashing?
  • top sorted by CPU and by memory, plus the state column: one hog, a leak, D states, zombies.
  • Then a targeted tool: strace on the suspect, iostat for disks, ss for sockets, dmesg for hardware errors.

Follow-up: Load is 30 on 8 cores, CPU is 10 percent busy. What is it? (Disk. Processes in D state count toward load. Check wa and iostat.)

Interview question

In top, what's the difference between VIRT and RES, and which one tells you a process is using too much memory?

What a strong answer covers
  • VIRT is the size of the virtual address space: every mapping, including files mapped but not read and memory reserved but never touched.
  • RES is the resident set: pages actually in RAM right now. That's the real footprint.
  • SHR is the shared part of RES, mostly libraries, counted once per process even though it's one copy in RAM.
  • Watch RES over time: growth that never comes back is a leak.

Follow-up: Why can VIRT be far bigger than the machine's RAM? (Virtual memory: mappings don't need frames until touched. A process can map terabytes and use megabytes.)

Interview question

You see three zombie processes in top. Is the machine in trouble? What do you do?

What a strong answer covers
  • Three zombies cost three PID slots and nothing else. Not trouble by themselves.
  • They mean a parent isn't calling wait. Find it: the zombies' PPID.
  • kill on the zombie does nothing; it's already dead. Fix or restart the parent; if the parent dies, PID 1 reaps them.
  • Thousands of zombies, or a growing count, is a bug worth escalating: PIDs are finite.

Follow-up: Could you ever have a zombie whose parent is PID 1? (Only briefly; PID 1 reaps continuously. A lingering one means PID 1 itself is stuck, which is a real emergency.)

Practice

Out loud first, then open the answer.

1. What does the kernel do, in three sentences?

It's the one program allowed to touch the hardware, and it shares that hardware among all the others. It gives each process its own memory and its turns on the CPU, moves data to and from devices, and enforces who may do what. Programs reach it only by asking, through system calls.

2. fork, exec, wait: one sentence each, then how a shell uses them.

fork clones the process; exec replaces its program; wait collects a finished child. The shell forks, the child execs the command, the shell waits for it to exit.

3. Why does the OS need a timer interrupt?

Without it, a running process keeps the CPU until it voluntarily blocks or exits, so one infinite loop freezes the machine. The timer forces control back into the kernel every few milliseconds so the scheduler can preempt.

4. Explain a race condition with the counter example, and name the fix.

counter += 1 is load, add, store. Two threads can both load the old value before either stores, so one increment vanishes. Wrap it in a mutex so only one thread runs those three steps at a time, or use an atomic increment.

5. Interrupt versus system call versus page fault.

All three enter kernel mode. A system call is the program asking, on purpose. A page fault is the program stumbling into something the kernel has to fix, without asking. An interrupt is a device or the timer forcing its way in, unrelated to what's running.

6. Load average is 16 on a 4-core box and the CPUs are 20 percent busy. Explain.

Load counts processes in disk wait too. The CPUs are idle because the processes are all blocked on storage. Expect high wa in top and many D states. It's a disk problem wearing a CPU costume.

7. CPU versus GPU in three sentences, and why the network matters for GPUs.

A CPU has a few fast cores built to finish one instruction stream quickly; a GPU has thousands of slow cores that run the same instruction across many data elements at once. GPUs win on huge uniform arithmetic and lose on serial, branchy, or small work, partly because data has to be copied to them first. Training runs on thousands of GPUs that exchange results every step, so the network between them sets the pace of the whole job.

Paper problems

a. One core. A needs 5 ticks of CPU, B needs 3, C needs 2, all ready at tick 0. Round robin, slice 2. Draw the schedule and give each completion time.

A A B B C C A A B A. C finishes at 6, B at 9, A at 10. Average turnaround (10 + 9 + 6) / 3 = 8.3. First come, first served would be A A A A A B B B C C: A 5, B 8, C 10, average 7.7. FCFS has a better average here, but C waited 8 ticks to run at all; round robin got it done in 6. Check it in the scheduler widget with "Three plain CPU jobs."

b. Two threads each increment a shared counter 5 times, three steps per increment, no lock, and the scheduler alternates strictly one step at a time. Final value?

5. Each pair of increments interleaves as load, load, add, add, store, store, so the two stores write the same value and one increment is lost every time. Ten increments, five survive. Check it in the race widget.

c. A loop calls getpid() 1,000 times. How many mode switches? How many context switches?

2,000 mode switches (into the kernel and back, each call). Zero context switches: the same process ran the whole time; nothing blocked.

d. Thread 1 locks A then B. Thread 2 locks B then A. Both start at once. What happens, and what's the one-line fix?

Thread 1 gets A, thread 2 gets B, then each waits for the other's lock forever: deadlock. Fix: make thread 2 lock A then B too. With a global order, the cycle can't form.

e. A shell runs "sort big.txt > out.txt". List the system calls in order, roughly.

fork. In the child: open out.txt, dup2 it onto file descriptor 1, exec sort. sort then: open big.txt, read repeatedly, write repeatedly to fd 1 (which is out.txt), exit. In the parent: wait.

g. A job is 10 percent serial. Speedup with 10 processors? With 1,000? With infinitely many?

1 / (0.1 + 0.9/10) = 1 / 0.19 = 5.3x. With 1,000: 1 / (0.1 + 0.0009) = 9.9x. Infinite: 1 / 0.1 = 10x. The last 990 processors bought less than 2x. That's Amdahl.

h. You copy 1 GB to the GPU over PCIe at 32 GB/s, run a kernel that takes 5 ms, and copy 1 GB back. What fraction of the time was compute? What if you keep the data on the GPU for 100 kernels in a row?

Each copy is 1 GB / 32 GB/s = 31 ms, so 62 ms of transfer around 5 ms of compute: compute is about 7 percent of the time. Keeping the data resident for 100 kernels: 62 ms of transfer once, 500 ms of compute, so compute is about 89 percent. That's why "keep the data on the GPU" is rule one.

f. top shows a process at 397 percent CPU. How many cores is it using, and is that a problem?

About four cores' worth: %CPU is per core, so 400 means four cores fully busy, presumably four threads. It's only a problem if that process isn't supposed to be doing that. Check with top -H to see its threads.

Narration one: what happens when you run ./program (the OS half)

You told the machine half last session. Now the whole thing, from the shell prompt to exit. A complete answer touches all of these.

  • The shell reads the command and calls fork; the child is a copy of the shell.
  • The child calls exec on ./program: the kernel throws away the shell's address space and maps the new binary's code and data.
  • The loader maps shared libraries and sets up the stack; the program counter is set to the entry point.
  • Pages load on demand: the first instruction fetch page-faults the code in.
  • The process runs in user mode; every file, network, or memory request is a system call into the kernel.
  • The timer interrupt lets the scheduler preempt it and run other processes; it keeps running when picked again.
  • If it blocks (reading input, waiting on the network), it sleeps until an interrupt handler wakes it.
  • It calls exit: memory and file descriptors are released; it becomes a zombie until the shell's wait collects the exit status.
  • The shell prints the next prompt.
  • You named which side each step belongs to: hardware, kernel, or user program.

Narration two: a packet arrives

The one that ties both weeks together. Ninety seconds, out loud.

  • The program is blocked in recv on a TCP socket; the scheduler is running something else.
  • The frame arrives; the network card checks the destination MAC and the checksum and keeps it.
  • DMA writes the frame into a kernel buffer in RAM; no CPU involved.
  • The card raises an interrupt; the CPU saves state, enters kernel mode, runs the driver's handler.
  • The Ethernet header says IPv4; the IP header says it's for this host and carries TCP.
  • TCP finds the socket by source and destination address and port, checks the sequence number, queues the data in the receive buffer, and arranges an ACK.
  • The handler marks the blocked process runnable and returns; the interrupted process resumes.
  • The scheduler later switches to our process; the kernel copies the data to the user buffer.
  • recv returns the byte count, back in user mode.
  • You named the layer at every step: hardware, kernel network stack, scheduler, user program.

The usual confusions. Threads share stacks (they don't). fork creates a thread (no, a process). A system call is an interrupt (related mechanism, different cause). Zombies use resources (only a PID). kill -9 first (TERM first). Load average is CPU percentage (it's queue length). Blocking means the CPU is stuck (the CPU moves on; the process sleeps).

GPU widget answers. Warp: all threads on the same branch gives 5 cycles (if) or 4 (else) at 100 percent useful; any split gives 6 cycles, and a 4/4 split is 75 percent useful. Race: with one operation per element and a copy, the GPU never wins at any size or core count (arithmetic intensity too low). Keep the data resident and the GPU wins past about 250,000 elements with 8 CPU cores (30,000 with 1 core, a million with 32). With a hundred operations per element and a copy, the GPU wins past about 2,800 elements with 8 cores (300 with 1, 16,000 with 32). The serial chain never favors the GPU. These are the toy model's numbers; the proportions are what matter.

Widget answers. Scheduler, "Three plain CPU jobs," round robin slice 2: A A B B C C A A B A, completions C 6, B 9, A 10, 5 context switches. FCFS: A 5, B 8, C 10, 2 switches. The mixed workload with round robin and slice 2 finishes at tick 15 with 7 switches; B's two I/O waits show as ticks 3 to 5 and 10 to 12. Race, four increments each, strict alternation, no lock: final 4 (four lost). Whole increments or mutex: 8. Deadlock mode with opposite order: stops after four steps with both waiting. Same order: completes.

Python checks. Race demo: unlocked results typically between 1.2 and 1.9 million, varying per run; locked gives 2,000,000 and takes noticeably longer. If her unlocked run gives exactly 2,000,000 every time, have her increase the count or add a tiny sleep inside the loop; on some CPython versions the switch interval hides it.
