How a packet is built and delivered

By the end of this session you can take one message, wrap it in real headers, hand it to a switch, and explain every decision along the way out loud. That narration is the thing Meta actually grades.

Start here

You already know how to write software. This week you learn what happens to the bytes after send() returns. Nothing here is hard. It is just a set of moving parts you have never had to look at, and the interview will ask you to look at them under pressure.

The one idea to carry through the whole week: a packet is a nested set of headers, and each header carries exactly one field that tells the receiver which layer to hand the rest to. Everything else is detail.

Layers

Networking is layered for the same reason your code is. Each layer has one job, a contract with the layer above it, and a contract with the layer below it. Swap Wi-Fi for Ethernet and TCP does not notice. Swap TCP for UDP and Ethernet does not notice. That independence is the entire point.

Two models, one stack

The OSI model has seven layers and shows up on every whiteboard. The TCP/IP model has four and is what real systems actually implement. Learn both names, but think in TCP/IP.

The three questions

Three of these layers carry an address, and each address answers a different question:

  • Layer 2, MAC address: which machine on this wire? Only meaningful within one network segment. Rewritten at every router.
  • Layer 3, IP address: which machine anywhere? Stays the same from source to destination across the whole internet.
  • Layer 4, port: which program on that machine? 80 means the web server, 22 means SSH, 51234 means some browser tab.

When you're debugging, the first move is always to place the symptom on a layer. "Ping works but curl doesn't" is a layer 4 or higher problem. "Ping fails but ARP resolves" is layer 3. "ARP never gets an answer" is layer 2 or 1. Nobody at Meta cares whether you can recite layers 5 and 6. They care that you do this sorting fast.

The programmer's translation

Encapsulation is nested structs. A routing table is a longest-prefix-match lookup, which you would implement as a trie. A switch's MAC table is a hash map from address to port. Every time a networking concept feels foreign, ask what data structure it is, and it usually stops being foreign.

Encapsulation

Your program hands the network stack some bytes. On the way down, each layer prepends its own header. On the way up at the other end, each layer reads its header, uses one field to decide who gets the rest, strips the header, and passes the payload up. That's all encapsulation is.

The demultiplexing field

Notice the pattern when you unwrap. Every header has exactly one field whose job is to say what's inside:

  • Ethernet: EtherType. 0x0800 means IPv4, 0x0806 means ARP, 0x86DD means IPv6.
  • IP: Protocol. 6 means TCP, 17 means UDP, 1 means ICMP.
  • TCP or UDP: Destination port. 80 means hand it to whatever process bound port 80.

If you remember nothing else about headers, remember those three fields. They are the reason a single NIC can carry a thousand different conversations and every byte ends up at the right program.

Same-subnet delivery

IP gives you the destination's address. It does not give you the destination's MAC, and a frame cannot leave the NIC without one. Bridging that gap is ARP, and the device in the middle that gets the frame to the right cable is a switch. Both are dumber than people expect, which is exactly why they're fast.

The decision every host makes first

Before a host sends anything, it answers one question: is the destination on my subnet? It ANDs the destination IP with its own subnet mask and compares the result to its own network address. If they match, the destination is local and the host sends to it directly. If not, it sends to its default gateway instead. Today everything is local. Session 2 is about the other branch.

ARP

ARP maps an IP address to a MAC address on the local segment. The host broadcasts a request to ff:ff:ff:ff:ff:ff: "who has 192.168.1.20? Tell 192.168.1.10." Every host on the segment receives it. Only the owner answers, with a unicast reply straight back: "192.168.1.20 is at 02:00:00:00:00:0b." Both sides cache the result for a while (Linux defaults to about a minute of reachability before it re-checks) so the next packet skips the whole exchange.

One detail people miss: the target also caches the requester's mapping, because the request already contained it. That's why in the lab you'll see B reply to A without ever sending its own ARP request.

What a switch actually does

A switch has one table: MAC address to port. It fills that table by reading the source MAC of every frame that arrives. It forwards by looking up the destination MAC. Three cases:

  • Destination MAC is in the table: send the frame out that one port only.
  • Destination MAC is not in the table: flood the frame out every port except the one it came in on.
  • Destination is the broadcast address: flood.

That's it. A switch does not look at IP addresses, does not change a single byte of the frame, and has no idea what ARP is. It just learned who lives where.

TCP

IP delivers packets on a best-effort basis: they can arrive out of order, duplicated, or not at all. TCP sits on top and turns that into a reliable, ordered byte stream. It does that with three tools: a handshake to agree on starting numbers, sequence numbers on every byte, and acknowledgments that say "I have everything up to here."

The handshake

Three messages. The client sends SYN with a random initial sequence number. The server answers SYN-ACK: its own random sequence number, plus an ack of the client's number plus one. The client sends ACK. Both sides now know each other's starting point and the connection is established. Random starting numbers, not zero, so that a late packet from an old connection can't be mistaken for a new one.

Reading the numbers

  • The ack number is cumulative. If I ack 1000, I have every byte below 1000. One lost segment holds the ack in place until it's retransmitted.
  • SYN and FIN each consume one sequence number even though they carry no data. That's why the SYN-ACK acks x+1.
  • Wireshark shows relative numbers by default, starting at 0, so the math is readable. tcpdump does the same after the handshake unless you pass -S. The real numbers are 32-bit and random.
  • A lost SYN-ACK looks like a client sending the same SYN again and again, at roughly 0, 1, 3, and 7 seconds. The gaps double each time. That's exponential backoff and you will see it in captures.
  • RST means "no connection here, stop." A closed port answers a SYN with RST-ACK immediately. A firewall that drops silently produces no reply at all, which is why "connection refused" and "connection timed out" are different symptoms.

One packet, one journey

Now put it all together. This is the answer to "walk me through what happens when a host sends a request," and it is also the skeleton of every troubleshooting question you'll get: trace the packet, find the step where it dies.

Step through it with a cold ARP cache first. Then warm. Then flip to the different-subnet preview and pay attention to exactly which fields change at the router. Session 2 covers that path in depth; today you just need to see it once.

Packet journey

The observation that carries the whole course: across the switch, not one byte changed. Across the router, both MAC addresses changed, the TTL dropped by one, the IP checksum was recomputed, and the IP addresses and ports did not move. Layer 2 is hop by hop. Layer 3 is end to end. Everything else in networking is a footnote to that sentence.

The narration, in order

This is the shape of a complete answer. Learn the order, not the words. In the interview you say it slowly, you name the layer at each step, and you say what you would check if that step failed.

  1. Application hands data to a socket: destination IP and port are known.
  2. Transport adds the TCP header: source port picked, destination port set. If TCP, the handshake happens before any data.
  3. Network adds the IP header: source and destination IP, TTL, protocol.
  4. Host decides local or remote by ANDing the destination with its mask.
  5. Host resolves the next hop's MAC with ARP, from cache or by asking.
  6. Link adds the Ethernet header and the frame goes on the wire.
  7. Switch learns the source MAC, looks up the destination MAC, forwards or floods. Changes nothing.
  8. (Remote only) Router accepts the frame, looks up the destination in its routing table, decrements TTL, rewrites both MACs, sends on the next link.
  9. Destination NIC accepts on MAC match, EtherType picks IP, protocol picks TCP, destination port picks the socket.
  10. Data arrives in the application's recv().

Lab 1: two hosts, one wire, every packet

Linux network namespaces give you a complete, separate network stack: its own interfaces, routing table, ARP cache. Two namespaces joined by a virtual cable is two computers as far as the packets are concerned, and it costs nothing. This is how you prove every claim on this page.

Run every command yourself. Don't paste the whole block. Read each line and say what it does before you hit enter.

Part 1: build the network

sudo ip netns add hostA
sudo ip netns add hostB
sudo ip link add vethA type veth peer name vethB
sudo ip link set vethA netns hostA
sudo ip link set vethB netns hostB
sudo ip -n hostA addr add 192.168.1.10/24 dev vethA
sudo ip -n hostB addr add 192.168.1.20/24 dev vethB
sudo ip -n hostA link set vethA up
sudo ip -n hostB link set vethB up
sudo ip -n hostA link set lo up
sudo ip -n hostB link set lo up

What you built: two namespaces, a veth pair (a virtual Ethernet cable with an interface at each end), one end moved into each namespace, an address on each, everything brought up. Check it:

sudo ip -n hostA addr show vethA
sudo ip -n hostB addr show vethB

Write down both MAC addresses (the link/ether line). You'll need them to read the capture.

Part 2: capture a ping

Open two terminals. In the first, start listening inside hostB:

sudo ip netns exec hostB tcpdump -i vethB -e -n

-e prints the Ethernet header (the MACs), -n skips name lookups so you see raw addresses. In the second terminal, ping from hostA:

sudo ip netns exec hostA ping -c 3 192.168.1.20

Expected output in the tcpdump terminal, with your MACs in place of these:

02:.. > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 192.168.1.20 tell 192.168.1.10, length 28
02:.. > 02:.., ethertype ARP (0x0806), length 42: Reply 192.168.1.20 is-at 02:.., length 28
02:.. > 02:.., ethertype IPv4 (0x0800), length 98: 192.168.1.10 > 192.168.1.20: ICMP echo request, id 4213, seq 1, length 64
02:.. > 02:.., ethertype IPv4 (0x0800), length 98: 192.168.1.20 > 192.168.1.10: ICMP echo reply, id 4213, seq 1, length 64
...

What to look for

  • The ARP request goes to the broadcast MAC. The reply comes back unicast. Confirm both against your written-down MACs.
  • EtherType flips from 0x0806 to 0x0800 between ARP and ICMP. That is the demux field doing its job.
  • Frame length 98. Explain it: 14 Ethernet + 20 IP + 8 ICMP + 56 bytes of ping payload. The length 64 at the end is the ICMP part alone.
  • Now look at the ARP caches on both sides. B has an entry for A even though B never asked:
sudo ip -n hostA neigh
sudo ip -n hostB neigh
  • Run the ping again. No ARP this time. Then flush A's cache and ping once more, and ARP is back:
sudo ip -n hostA neigh flush all
sudo ip netns exec hostA ping -c 1 192.168.1.20

Part 3: capture a real TCP handshake

Start a web server inside hostB, then fetch from hostA while capturing. This time save the capture to a file too.

sudo ip netns exec hostB python3 -m http.server 8080 --bind 192.168.1.20

Second terminal, capture to a file (and to the screen with -v if you like):

sudo ip netns exec hostB tcpdump -i vethB -n -w lab1.pcap

Third terminal:

sudo ip netns exec hostA curl -s http://192.168.1.20:8080/ | head -3

Stop tcpdump with Ctrl-C, then read the file. -S shows absolute sequence numbers; drop it to see relative ones like Wireshark.

tcpdump -r lab1.pcap -n -S | head -12

Find the three handshake lines: Flags [S], then Flags [S.], then Flags [.]. Check that the SYN-ACK's ack equals the SYN's seq plus one. Find the [P.] segment that carries the GET, then the FINs at the end. If you have Wireshark, wireshark lab1.pcap and expand the first SYN to see the exact header layout you decoded in the widget.

Clean up

sudo ip netns del hostA
sudo ip netns del hostB

Deleting a namespace deletes everything inside it, including its end of the veth pair, which deletes the other end too.

WSL2 notes: everything here works on the stock WSL2 kernel. If tcpdump complains about permissions, you forgot sudo. If wireshark won't open a window, copy the pcap to your Windows side with cp lab1.pcap /mnt/c/Users/<you>/Desktop/ and open it there.

Practice

Work each one on paper or out loud before opening the solution. Interview answers are spoken, so say them, don't just think them.

1. A host sends a 120-byte HTTP request over TCP over IPv4 over Ethernet, no options anywhere. How many bytes go on the wire? What does the IP total length field say?

Show solution

On the wire: 14 + 20 + 20 + 120 + 4 (FCS) = 178 bytes. tcpdump reports 174 because it usually doesn't see the FCS; the NIC strips it.

IP total length = 20 + 20 + 120 = 160. It counts from the IP header on and knows nothing about Ethernet.

2. A frame arrives with EtherType 0x0806. What's inside? Does it have an IP header? Does it have a TCP header?

Show solution

0x0806 is ARP. ARP is its own protocol sitting directly on Ethernet. There is no IP header and no TCP header. That's why ARP can't cross a router: there's no IP address on the packet for a router to route.

3. In the lab, host B ended up with A's MAC in its ARP cache even though B never sent an ARP request. Explain.

Show solution

A's ARP request contained A's own IP and MAC in the sender fields. B needed A's MAC to send the reply, so it cached the mapping from the request. Free information, so it kept it.

4. A capture shows a client sending a SYN, then the identical SYN one second later, then again two seconds after that. What happened and what would you check?

Show solution

No SYN-ACK came back inside the retransmission timer, so the client retried with exponential backoff. Either the SYN never reached the server, or the SYN-ACK never made it back, or the server silently dropped it (a firewall that drops rather than rejects). Check: can the server see the SYN arrive (tcpdump on the server side)? Is anything listening on that port (ss -ltn)? Is there a firewall rule dropping it? A closed port with no firewall would have answered RST instead of staying silent.

5. tcpdump on B shows ICMP requests and replies between A and B, but no ARP traffic at all. Is something wrong?

Show solution

No. Both caches were already warm from an earlier exchange, so no ARP was needed. To see it again, flush A's neighbor table and repeat.

6. A switch's table says host A is on port 1. A frame arrives on port 3 with A's MAC as the source. What does the switch do?

Show solution

It updates the entry: A is now on port 3. The switch trusts source MACs unconditionally, which is why a laptop can be unplugged and moved to another port and keep working. It's also why MAC spoofing is trivial on a plain switch.

7. Two symptoms: (a) ping to a server works but curl to port 8080 hangs for a minute then times out. (b) ping works and curl fails instantly with "connection refused." Place each on a layer and name the most likely cause.

Show solution

Both are transport layer or above, because IP delivery works in both directions (ping succeeded). (a) A timeout means the SYNs got no answer: usually a firewall dropping traffic to 8080. (b) Refused means the server answered with RST: the host is reachable but nothing is bound to 8080, or the service is bound only to localhost.

8. A and B share a subnet and a switch. A has a cold ARP cache. A runs curl http://B/ and the server replies with a small page. List every frame on the wire, in order, until the connection closes.

Show solution
  1. ARP request, A to broadcast: who has B?
  2. ARP reply, B to A: B is at its MAC.
  3. TCP SYN, A to B.
  4. TCP SYN-ACK, B to A.
  5. TCP ACK, A to B. Connection established.
  6. TCP PSH-ACK, A to B, carrying the GET.
  7. TCP ACK, B to A (often merged with the next one).
  8. TCP PSH-ACK, B to A, carrying the response.
  9. TCP ACK, A to B.
  10. FIN-ACK, ACK, FIN-ACK, ACK: four segments to close, two in each direction. Who closes first depends on the server and on HTTP keep-alive.

Compare with your lab1.pcap. The real one will have a few extra ACKs; the order of the big pieces is the same.

Common mistakes: forgetting ! (network byte order) in the struct format, so ports and lengths come out byte-swapped; slicing IP at a fixed 14 instead of using IHL; reading flags from the data-offset byte. If she got the IP checksum stretch, she zeroed bytes 24 and 25 before summing.

The pcap should show: one ARP request to broadcast, one unicast reply, ICMP frames of 98 bytes, a clean [S] / [S.] / [.] handshake with ack = seq + 1, a [P.] carrying GET / HTTP/1.1, and four FIN/ACK segments. If she flushed the cache before part 3, there will be a second ARP pair before the SYN. Ask her to explain 98.

Narration check. Use the ten-item rubric. The usual gaps: skipping the local-or-remote decision, saying the switch "routes" or "reads the IP," and never saying what to check on failure. If she hits eight or more, she's ahead of pace.

Pacing. If session 1 runs long, cut the TCP vs UDP table and the lost SYN-ACK scenario; both come back in week 3. Do not cut the journey widget or lab part 2.
