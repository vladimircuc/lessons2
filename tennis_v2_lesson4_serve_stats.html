This loop rebuilds everything so far: Elo, surface Elo, head-to-head, rest, and experience.

import pandas as pd
import numpy as np
from collections import defaultdict
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import accuracy_score

df = pd.read_csv("atp_2000_2024_model_ready.csv", low_memory=False)
df["tourney_date"] = pd.to_datetime(df["tourney_date"])
df = df.sort_values(["tourney_date", "match_num"]).reset_index(drop=True)
is_A = df["winner_is_A"].values.astype(bool)
cut = int(len(df) * 0.8)

def dynamic_k(n): return 250 / ((n + 5) ** 0.4)

elo = defaultdict(lambda: 1500.0); games = defaultdict(int)
selo = defaultdict(lambda: 1500.0); sgames = defaultdict(int)
h2h = defaultdict(int); last_date = {}; played = defaultdict(int)
ew=np.zeros(len(df)); el=np.zeros(len(df)); sew=np.zeros(len(df)); sel=np.zeros(len(df))
hw=np.zeros(len(df)); rw=np.zeros(len(df)); rl=np.zeros(len(df)); xw=np.zeros(len(df)); xl=np.zeros(len(df))

for i, row in enumerate(df.itertuples(index=False)):
    w, l, s, d = row.winner_id, row.loser_id, row.surface, row.tourney_date
    a, b = elo[w], elo[l]; ew[i]=a; el[i]=b
    sa, sb = selo[(w,s)], selo[(l,s)]; sew[i]=sa; sel[i]=sb
    hw[i] = h2h[(w,l)] - h2h[(l,w)]
    rw[i] = (d-last_date[w]).days if w in last_date else 30
    rl[i] = (d-last_date[l]).days if l in last_date else 30
    xw[i] = played[w]; xl[i] = played[l]
    e = 1/(1+10**((b-a)/400)); elo[w]=a+dynamic_k(games[w])*(1-e); elo[l]=b-dynamic_k(games[l])*(1-e); games[w]+=1; games[l]+=1
    se = 1/(1+10**((sb-sa)/400)); selo[(w,s)]=sa+dynamic_k(sgames[(w,s)])*(1-se); selo[(l,s)]=sb-dynamic_k(sgames[(l,s)])*(1-se); sgames[(w,s)]+=1; sgames[(l,s)]+=1
    h2h[(w,l)]+=1; last_date[w]=d; last_date[l]=d; played[w]+=1; played[l]+=1

df["elo_diff"]=np.where(is_A,ew-el,el-ew); df["surface_elo_diff"]=np.where(is_A,sew-sel,sel-sew)
df["h2h_diff"]=np.where(is_A,hw,-hw); df["rest_diff"]=np.where(is_A,rw-rl,rl-rw); df["exp_diff"]=np.where(is_A,xw-xl,xl-xw)

STACK = ["elo_diff","surface_elo_diff","h2h_diff","rest_diff","exp_diff"]
def acc(cols):
    tr, te = df.iloc[:cut], df.iloc[cut:]
    m = LogisticRegression(max_iter=1000).fit(tr[cols], tr["target"])
    return round(accuracy_score(te["target"], m.predict(te[cols])), 4)
print("stack so far:", acc(STACK))

Your Week-3 stack sits at about 0.650. That is the bar serve stats have to clear.

The hypothesis

Serving dominates tennis. Let's state the claim precisely and set up a fair test.

The claim. A player's serve is one of the biggest weapons in tennis. Big servers hold serve almost for free and win tiebreaks. So the hypothesis is: adding each player's career serve quality (how well they serve, historically) will improve the model beyond skill, surface, and context. It sounds obviously true. This week you test it instead of assuming it.

What we'll measure per player

Three career serve rates, each computed from all of a player's matches before the current one:

  • Ace rate: aces per service point. Pure serving power.
  • First-serve win rate: points won when the first serve lands. Serve effectiveness.
  • Break-point-save rate: break points saved out of faced. Serving under pressure.
The leakage trap, sharper than ever. Your data has this match's serve stats (aces hit in this match), but using those would be catastrophic leakage, they are a result of the match you are predicting. You must use only each player's career serve stats coming in, accumulated from past matches. So the loop reads the running totals first, then adds this match's serve numbers after. Read first, update after, exactly as always.
Practice

1.In a markdown cell, explain why using this match's ace count as a feature would be leakage, but a player's career ace rate coming in is fine. write it

Example answer

This match's ace count is produced during the match we are trying to predict, so it already contains information about how the match went, which is leakage. A player's career ace rate coming in is computed only from their earlier matches, so it is known before this match starts and reflects their general serving ability rather than this match's outcome. The first cheats by peeking at the result; the second is a fair pre-match feature.

Running rates

A new technique: build a rate by accumulating totals, not by averaging per-match percentages.

The right way to build a career rate. To get a player's career ace rate, you do not average their per-match ace percentages. You keep running totals of aces and of service points, and divide at the end: total_aces / total_service_points. This weights every point equally, so a five-set marathon counts more than a quick straight-setter, which is correct. Averaging per-match rates would let a single short match swing the number.

You track a small array of running totals per player and read the rate before each match.

Cell · career serve rates (running totals)

# running totals per player: [aces, service_points, 1st_won, 1st_in, bp_saved, bp_faced]
serve = defaultdict(lambda: np.zeros(6))

ace_w = np.zeros(len(df)); ace_l = np.zeros(len(df))
fsw_w = np.zeros(len(df)); fsw_l = np.zeros(len(df))
bps_w = np.zeros(len(df)); bps_l = np.zeros(len(df))

def serve_rates(t):
    if t[1] == 0:                       # no service points yet
        return 0.076, 0.712, 0.604      # tour-average defaults (placeholder for now)
    return t[0]/t[1], t[2]/max(t[3],1), t[4]/max(t[5],1)

for i, row in enumerate(df.itertuples(index=False)):
    w, l = row.winner_id, row.loser_id
    # READ career rates BEFORE this match
    ace_w[i], fsw_w[i], bps_w[i] = serve_rates(serve[w])
    ace_l[i], fsw_l[i], bps_l[i] = serve_rates(serve[l])
    # UPDATE totals with THIS match (skip rows missing serve stats)
    wv = [row.w_ace, row.w_svpt, row.w_1stWon, row.w_1stIn, row.w_bpSaved, row.w_bpFaced]
    lv = [row.l_ace, row.l_svpt, row.l_1stWon, row.l_1stIn, row.l_bpSaved, row.l_bpFaced]
    if not any(pd.isna(wv)): serve[w] += np.array(wv, float)
    if not any(pd.isna(lv)): serve[l] += np.array(lv, float)

df["ace_diff"] = np.where(is_A, ace_w - ace_l, ace_l - ace_w)
df["fsw_diff"] = np.where(is_A, fsw_w - fsw_l, fsw_l - fsw_w)
df["bps_diff"] = np.where(is_A, bps_w - bps_l, bps_l - bps_w)
Two details. About 7% of matches are missing serve stats (older or smaller events), so we skip updating on those rows with the pd.isna check. And max(t[3], 1) avoids dividing by zero before a player has any first serves recorded.

2.In a markdown cell, explain why a career rate should be built from running totals rather than by averaging each match's percentage. write it

Example answer

Building from running totals divides total aces by total service points, so every point counts the same and long matches contribute more than short ones, which reflects reality. Averaging each match's percentage gives every match equal weight regardless of length, so one short match with an unusual rate can distort the average. Totals give a more accurate and stable estimate of a player's true rate.

The small-sample guard

A rate from a handful of points is not trustworthy. Guard against it.

The problem. A player who has served 30 points and happened to hit 4 aces has a 13% ace rate, but that number is almost meaningless, it is far too little data. If you feed the model these shaky early rates, you add noise. The fix is a guard: until a player has enough history, use a neutral default (the tour average) instead of their unreliable personal rate.

With few points, the estimated rate bounces wildly around the true value. Once enough points accumulate, it settles. Below the threshold we use the tour average; above it we trust the player's own rate.

Cell · add the guard (require 200 career service points)

MIN_POINTS = 200
ACE_AVG, FSW_AVG, BPS_AVG = 0.076, 0.712, 0.604   # tour averages

def serve_rates(t):
    if t[1] < MIN_POINTS:                # not enough history yet
        return ACE_AVG, FSW_AVG, BPS_AVG
    return t[0]/t[1], t[2]/max(t[3],1), t[4]/max(t[5],1)

Rerun your serve loop with this guarded serve_rates, so early-career rates fall back to the tour average until there is enough data.

2.In a markdown cell, explain what the small-sample guard does and why feeding unreliable early rates to the model would hurt. write it

Example answer

The guard checks whether a player has enough serving history, and if not, it uses the tour-average rate instead of their own. Early rates computed from very few points swing wildly and do not reflect true ability, so using them would feed the model noise rather than signal. Falling back to a neutral average until there is enough data keeps those unreliable values from misleading the model.

Roughly: stack 0.650, and every serve version comes in at or slightly below it (about 0.647 to 0.649). Serve stats did not help. They slightly hurt.

The result, and why it is not a failure. The hypothesis was reasonable and the features are correct (the ace-rate sanity check proved that). But the data says serve quality adds nothing on top of what you already have. The reason is the same one that sank recent form: Elo already contains it. A great server wins more matches, so their Elo is already high. The serve rate is largely a repeat of information Elo has absorbed through results, and piling redundant, slightly noisy features onto the model can nudge accuracy down.
This is a real scientific result, and a strong one for your write-up. You proposed a sensible hypothesis, built the features rigorously, verified them, tested them, and reported honestly that they did not help, with a clear explanation of why. That is exactly how good science works, and it is more impressive than a lucky feature that happened to help. Your final model will use the features that earned their place; serve stats join recent form as "tested and dropped."

Example answer

This match's aces are generated during the match we are predicting, so they already reflect its outcome. Using them lets the model peek at the result, which is leakage and produces fake accuracy. Only serve stats accumulated from earlier matches are known before the match and are fair to use.

7.Why build a career rate from running totals instead of averaging match percentages? write it

Example answer

Running totals divide total successes by total attempts, so every point is weighted equally and longer matches count more, giving an accurate rate. Averaging per-match percentages weights every match the same regardless of length, so a short match with an odd rate can distort the result.
