The rule that governs this entire chapter: no leakage. A feature may only use information that existed before the match was played. When you build a feature from history, you must record its value before you update it with the match result. Get this backwards even once and your accuracy will look amazing and be completely fake, because the model would be peeking at the answer. Every loop we write follows the same safe order: read first, update after.

The chronological loop

Learn the one pattern behind every history feature, using the simplest possible example first.

The pattern, in plain words. Walk through the matches in date order. Keep a running record of each player's current state in a dictionary. For each match: (1) read both players' current values and store them as the feature for this match, then (2) update the record using who won. Because you read before you update, the feature never contains the result of the match it describes. That is the whole trick, and it is leakage-safe by construction.

Let's build the simplest feature there is to see the mechanism clearly: experience, how many matches each player has played so far.

Cell · experience (matches played before this match)

matches_played = defaultdict(int)          # running count per player, starts at 0
exp_w = np.zeros(len(df))                   # winner's count before the match
exp_l = np.zeros(len(df))                   # loser's count before the match

for i, row in enumerate(df.itertuples(index=False)):
    w, l = row.winner_id, row.loser_id
    # 1) READ: record each player's count BEFORE this match
    exp_w[i] = matches_played[w]
    exp_l[i] = matches_played[l]
    # 2) UPDATE: now that the match happened, add one to each
    matches_played[w] += 1
    matches_played[l] += 1
Two things worth knowing. defaultdict(int) is a dictionary that returns 0 for any player you have not seen yet, so you never have to check "is this a new player". And df.itertuples() walks the rows quickly; row.winner_id reads a column from the current row.

Turn it into a feature the model can use

Right now exp_w and exp_l are from the winner's and loser's side, which would leak (the model could guess the winner). So convert to A-vs-B, the same trick you used for rank_diff: A's value minus B's value.

is_A = df["winner_is_A"].values.astype(bool)
df["exp_diff"] = np.where(is_A, exp_w - exp_l, exp_l - exp_w)

Cell · does it help?

train, test = df.iloc[:cut], df.iloc[cut:]
m = LogisticRegression(max_iter=1000).fit(train[["exp_diff"]], train["target"])
print("experience only:", round(accuracy_score(test["target"], m.predict(test[["exp_diff"]])), 3))

2.In a markdown cell, explain why we record the feature value before updating it, and what would go wrong if we updated first. write it

Example answer

We record before updating because a feature is only allowed to use information from before the match. If we updated first, the value would already include the result of the current match, so the model would effectively see who won before predicting it. That is leakage, and it would make the accuracy look great in testing but fail completely on real future matches where the result is not yet known.

What Elo actually is

A skill rating that updates after every match. It is the single biggest upgrade over raw ranking, and it uses the exact loop you just learned.

The idea. Every player has a rating number (everyone starts at 1500). Before a match, the two ratings predict the result: the bigger the gap, the more likely the higher-rated player wins. After the match, both ratings update. Win against someone stronger and you gain a lot; lose to someone weaker and you drop a lot; expected results barely move the needle. Do this across 71,000 matches and the ratings settle into a genuine measure of skill, one that reacts to current form instead of lagging like the official points-based ranking.

Step 1: ratings predict the match (the expected score)

A rating gap converts to a win probability with this S-shaped curve:

Equal ratings mean a 50/50 match. The further your rating is above your opponent's, the closer your win chance gets to 100%. This is the "expected score", written expected = 1 / (1 + 10^((their_rating - your_rating) / 400)).

Step 2: the result updates both ratings

The winner gains and the loser drops by the same amount: K times the surprise. "Actual" is 1 for the winner and 0 for the loser. If a win was fully expected (expected near 1), the change is tiny; a big upset moves both ratings a lot. K is the step size, how fast ratings react.

Why this beats the official ranking: ATP ranking is a points system based on which tournaments you won over the last 52 weeks, so it lags and rewards showing up. Elo reacts to every single result against the specific quality of the opponent, so it tracks who is actually playing well right now.

1.In a markdown cell, explain the phrase K × (actual - expected) in your own words: what "actual" and "expected" are, and why an upset changes the ratings more than an expected result. write it

Example answer

"Actual" is what happened, 1 if the player won and 0 if they lost. "Expected" is the win chance the ratings predicted before the match, between 0 and 1. The rating changes by K times the difference between them. If a heavy favorite wins, expected was near 1 and actual is 1, so the difference is tiny and the rating barely moves. If an underdog wins, expected was low but actual is 1, so the difference is large and both ratings move a lot, which is the model quickly correcting its estimate of their skill.

Build Elo on the match history

The same read-then-update loop, now with the Elo formulas inside it.

Everyone starts at 1500. For each match, in date order: read both ratings (that is the pre-match feature), compute the expected score, then update both ratings by K × (actual - expected).

Cell · overall Elo, fixed step size

elo = defaultdict(lambda: 1500.0)          # every player starts at 1500
elo_w = np.zeros(len(df))                   # winner's rating BEFORE the match
elo_l = np.zeros(len(df))                   # loser's rating BEFORE the match
K = 32                                      # step size (fixed for now)

for i, row in enumerate(df.itertuples(index=False)):
    w, l = row.winner_id, row.loser_id
    a, b = elo[w], elo[l]
    # 1) READ: pre-match ratings are the feature
    elo_w[i] = a
    elo_l[i] = b
    # 2) UPDATE: expected score for the winner, then move both ratings
    expected_w = 1 / (1 + 10 ** ((b - a) / 400))
    elo[w] = a + K * (1 - expected_w)       # winner: actual = 1
    elo[l] = b - K * (1 - expected_w)       # loser drops by the same amount

# turn into an A-vs-B feature
df["elo_diff"] = np.where(is_A, elo_w - elo_l, elo_l - elo_w)

Same shape as the experience loop, just more math in the update step. It runs over all 71,000 matches in about a second.

Dynamic K: better ratings for new players

One upgrade that makes Elo noticeably sharper, straight from professional sports-rating systems.

The problem with a fixed step size. A brand-new player starts at 1500, but their true skill is unknown. With a small fixed K, their rating crawls toward reality over dozens of matches, so it is wrong for a long time. With a large fixed K, established stars bounce around too much after a single loss. You cannot win with one fixed number. The fix: make K large when a player is new (so their rating finds its level fast) and small once they are established (so it stays stable).

A simple, battle-tested formula does exactly that. K starts high and shrinks as a player plays more matches:

def dynamic_k(matches_played):
    return 250 / ((matches_played + 5) ** 0.4)

A player's first match uses K near 130 (moves fast); after 100 matches, K is down around 35 (steady). You track each player's match count as you go, the same counter from the experience feature, and feed it in.

Cell · Elo with a dynamic step size

elo = defaultdict(lambda: 1500.0)
games = defaultdict(int)                     # matches played so far, per player
elo_w = np.zeros(len(df)); elo_l = np.zeros(len(df))

def dynamic_k(n):
    return 250 / ((n + 5) ** 0.4)

for i, row in enumerate(df.itertuples(index=False)):
    w, l = row.winner_id, row.loser_id
    a, b = elo[w], elo[l]
    elo_w[i] = a; elo_l[i] = b               # READ first
    expected_w = 1 / (1 + 10 ** ((b - a) / 400))
    elo[w] = a + dynamic_k(games[w]) * (1 - expected_w)   # each player's own K
    elo[l] = b - dynamic_k(games[l]) * (1 - expected_w)
    games[w] += 1; games[l] += 1             # UPDATE the counts after

df["elo_diff"] = np.where(is_A, elo_w - elo_l, elo_l - elo_w)   # overwrite with the better version

Notice each player uses their own K based on how many matches they have played. This is the version of elo_diff you keep going forward.

Why + 5 and ** 0.4? The + 5 stops the very first match from using an enormous K, and the 0.4 power controls how quickly K shrinks. These are tuned constants from established rating systems; you do not need to derive them, just understand that they make K start high and taper.

Example answer
