How computers send each other messages

Envelopes, addresses, and a phone call. That's most of what's in this session, and it's the foundation for everything else we'll do.

Start here

You already write software. This session is about what happens after your program hands off some data: how it gets across a cable or Wi-Fi to another computer and lands in the right program on the other side.

None of this needs math or memorizing. It's a small number of ideas that happen to have intimidating names. We'll do the idea first and attach the name after, every time.

The one idea for today. A message gets put inside envelopes, one per job. Each envelope has just enough written on it for its one job. That's it. Everything else is detail on top of that.

Messages travel in small pieces

A network is two or more computers that can pass messages to each other, over a cable or over Wi-Fi.

A message doesn't travel as one big blob. It gets chopped into small pieces, and each piece is called a packet. A packet is usually about 1,500 bytes, and a byte is one character of text, so think "one paragraph per packet." A photo is thousands of packets. A single letter of text is one small packet.

Each packet travels on its own. Packets can arrive out of order, and now and then one gets lost. So every packet carries its number, and the receiving computer uses the numbers to put the pieces back together.

Why bother chopping? Because the cable is shared. If one computer could grab it for a whole 4 GB movie, nobody else could send anything until it finished. Small packets mean everyone takes turns.

Three kinds of address

For a packet to arrive, it needs an address. Computers use three, and each one answers a different question. This is the part most people rush past, and it's the part that makes everything else make sense, so go slowly here.

The three, in plain words

  • A MAC address belongs to the network card, the chip in your laptop that does Wi-Fi or plugs into a cable. It's set at the factory and never changes. Think of it as the serial number on the device. It's only used to reach a computer on the same local network, like the same Wi-Fi or the same office switch.
  • An IP address is given to your laptop when it joins a network. It's the mailing address: it depends on where you are, it changes when you move to another network, and it's what computers anywhere on the internet use to find you.
  • A port is a number that says which program on the computer a packet is for. One computer runs many programs at once. The web server listens on port 80, SSH on 22. Your browser picks a random high number for itself, like 51234, so replies know where to come back to. Think apartment number inside the building.

Interview favorite: why do we need both a MAC and an IP? Because they do different jobs. The MAC only works on the local network and never changes. The IP works everywhere and changes with location. A packet crossing the internet needs the IP to find the right building and, on the last stretch, the MAC to find the right machine in the room. You'll see this in action in the "Same network" tab.

Envelopes inside envelopes

The software that handles networking is split into layers. Each layer does one job and doesn't know or care about the others. The easiest way to picture it: your message is a letter, and each layer puts it in its own envelope with its own "To" and "From."

The letterApplication layer. What your program actually says: a web request, an email, a chat message. Written by the program.
TCP envelopeTransport layer. Which program this is for, which program sent it, and the packet number. Written by TCP (or its lighter cousin UDP).
IP envelopeInternet layer. Which computer this is for and which sent it, using IP addresses. Works across the whole internet.
Ethernet envelopeLink layer. Which network card on this cable or Wi-Fi should pick it up, using MAC addresses. Only has to get across one link.

Two words you'll hear for this. The writing on an envelope is called a header. The fully wrapped thing that actually goes onto the cable, all envelopes included, is called a frame. And a protocol is just an agreed format for what gets written where, so that any two computers can read each other's envelopes. TCP, IP, and Ethernet are all protocols.

About "the OSI model"

You'll hear about the OSI model, which slices the same stack into seven layers instead of four. Same idea, finer slices. Interviewers use its numbers as shorthand, so learn three of them: layer 2 is the Ethernet envelope, layer 3 is the IP envelope, layer 4 is the TCP envelope. The rest rarely comes up.

Delivering on the same network

Today we deliver inside one local network only: laptops on the same Wi-Fi, or plugged into the same box in an office. Sending to a computer on a different network, across the internet, is next session.

The box in the middle

The box the cables plug into is a switch. It's not smart, and that's a good thing. It does exactly one job: it remembers which cable each MAC address lives on, and it sends each frame down the right cable. How does it learn who's where? By reading the "From" line on the Ethernet envelope of every frame that passes through. If it hasn't seen a MAC yet, it just sends the frame down every cable and lets the right computer keep it.

Finding the MAC you need

Here's a snag. Your program knows the destination by IP address (that's what you type or look up). But the Ethernet envelope needs the destination's MAC. How does A find out B's MAC?

It asks the whole room. A sends a frame to everyone at once (that's called a broadcast) saying "who has 192.168.1.20?" Only B answers: "that's me, here's my MAC." A writes the answer in a small list so it doesn't have to ask again. This asking protocol is called ARP. You will be asked about it. The whole thing is: ARP turns an IP address into a MAC address, by asking.

TCP is a phone call. UDP is postcards.

The IP envelope gets a packet to the right computer, but IP makes no promises. Packets can arrive out of order, arrive twice, or disappear. Something has to turn that mess into a reliable conversation, and that's TCP.

TCP behaves like a phone call. Before you say anything, you make sure the other side is there and listening. Everything you say gets a "got it" back. If a "got it" doesn't come, you repeat yourself. And packets are numbered, so the other side can put them in order.

The call setup has a name you must know: the three-way handshake. Three messages. "Hello, can you hear me?" then "Yes, can you hear me?" then "Yes." In protocol terms those are SYN, SYN-ACK, and ACK. Only after the third one does any actual data move.

UDP is the other option, and it's postcards. You just send them. No handshake, no "got it," no resending. It's faster and lighter, and it's the right choice when late data is useless anyway: a video call, a game, a voice chat. A frame of video from half a second ago isn't worth stopping the whole call to recover.

Practice

Answer each one out loud, as if explaining to a friend who writes code but has never thought about networks. Then open the model answer and compare. Yours doesn't have to match. It has to be right and clear.

1. Why does a computer need both a MAC address and an IP address?

They do different jobs. The MAC is fixed to the hardware and only works for reaching machines on the same local network. The IP is assigned when you join a network and works across the whole internet. A packet uses the IP to find the right network and the MAC to reach the right machine on that network.

2. What does a switch do, in one sentence?

It learns which MAC address is on which cable by reading the "From" line of frames passing through, then sends each frame down only the cable its destination MAC is on.

3. What is ARP for, and how does it work?

It finds a MAC address when you only know the IP. The computer broadcasts "who has this IP?" to everyone on the local network, the owner replies with its MAC, and the asker saves the answer so it doesn't have to ask again.

4. Explain the three-way handshake, first as a phone call, then with the real names.

"Hello, can you hear me?" "Yes, can you hear me?" "Yes." The client sends SYN, the server answers SYN-ACK, the client sends ACK. Now both sides know the other is listening, and data can start.

5. When would you pick UDP over TCP?

When late data is useless, so waiting to resend it would only hurt: video calls, voice, games. UDP skips the handshake and the acknowledgments, which makes it faster, at the cost of never knowing if something got lost.

6. Tell the whole trip: your browser on A asks the web server on B for a page. Same network.
  1. The browser writes the request (the letter).
  2. TCP puts it in an envelope: for port 80, from port 51234, packet number 1. (The handshake already happened.)
  3. IP puts that in an envelope: to 192.168.1.20, from 192.168.1.10.
  4. A needs B's MAC for the outer envelope. If it doesn't have it, it asks with ARP and B answers.
  5. Ethernet puts everything in the outer envelope: to B's MAC, from A's MAC. The frame goes onto the cable.
  6. The switch reads the destination MAC and sends the frame down B's cable only.
  7. B's network card sees its own MAC and keeps the frame. It opens Ethernet, then IP, then TCP, and hands the letter to the web server on port 80.
  8. The server writes a reply and the same thing happens in reverse.

Pacing for 90 minutes. Start 5, Packets 10, Addresses 15, Envelopes 20, Same network 15, TCP and UDP 15, Whole trip 10. Envelopes is the one to protect. If short on time, skip the OSI table and the UDP half of the widget; both return in week 3.

What "good" looks like in her trip story. The four envelopes in the right order, ARP mentioned before the Ethernet envelope gets addressed, the switch reading the MAC only, and the receiver opening outside in. Anything about routers or TTL is fine but not expected yet.

The usual confusions. Thinking the switch reads IP addresses. Thinking ARP finds an IP (it finds a MAC). Thinking the handshake carries the first data. Thinking a port is a physical socket. Each one is worth a two-minute detour when it shows up.
