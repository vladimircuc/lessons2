Systems prep. Session 1 of 2: the machine.

How a program actually runs

The CPU, the memory it reads from, and the trick that lets every program believe it has the whole computer to itself. Session 2 adds the operating system on top.

Start here

Networking is paused for a week. These two sessions are about the machine itself: how the code you write turns into something a chip can run, why memory is organized in layers, and how the operating system shares one computer among many programs without any of them noticing. It's the material behind interview questions like "what's a cache line," "explain virtual memory," and "what happens on a page fault."

You've probably met most of this in a class. The goal here is different from learning it: it's being able to explain it out loud, cleanly, in two minutes, with a concrete example for each idea. That's what the interview questions at the end of every tab are for.

The story this session tells

  1. A program is a list of instructions. The CPU runs them in a loop: fetch, decode, execute.
  2. To go faster, the CPU works on several instructions at once and guesses which way branches go.
  3. The CPU is far faster than memory, so small fast caches sit in between, betting that you'll reuse what you just touched.
  4. Every program sees its own private memory starting at address zero. That's an illusion the hardware and the OS build together, called virtual memory.
  5. When a program touches memory that isn't actually in RAM, the OS quietly fetches it. When it touches memory it has no right to, the OS kills it.

The one idea for today. Every layer of a computer lies to the layer above it, and the lies are what make it fast and safe. The cache lies about how fast memory is. Virtual memory lies about how much memory there is and where it lives. Pipelining lies about doing one thing at a time. Learn the lies and you understand the machine.

The CPU

A program is a list of instructions. The code you write gets translated into them by a compiler, and the result is machine code: numbers, where each number means something like "add these two registers" or "load the value at this address." The CPU can run machine code and nothing else. Python doesn't break that rule: the Python interpreter is itself a compiled program, and when you run a script, the interpreter's machine code is what the CPU executes, on your script's behalf.

Three kinds of instruction

Every instruction has an opcode (what to do) and operands (what to do it to). Almost every instruction in existence falls into one of three families:

  • Move data. Load a value from memory into a register, or store a register back to memory.
  • Compute. Add, subtract, compare, shift, AND, OR. Always on registers, never directly on memory.
  • Change what runs next. Jump to another instruction, sometimes only if a condition holds. Loops and if-statements are made of these.

Registers and the program counter

A register is a tiny storage slot inside the CPU, a few bytes wide. There are only a few dozen of them, and they're the only place arithmetic can happen. Anything in memory has to be loaded into a register first, worked on, and stored back. One register is special: the program counter (PC) holds the address of the next instruction to run.

The loop

The CPU does the same three things forever:

  1. Fetch. Read the instruction at the address in the PC. Move the PC to the next one.
  2. Decode. Work out what the instruction is and which registers or addresses it involves.
  3. Execute. Do it. If it's a jump, overwrite the PC.

A clock paces this. "3 GHz" means three billion ticks per second, and each step takes one or more ticks, called cycles. A core is one complete CPU, with its own registers and its own PC, running its own stream of instructions. An eight-core chip is eight of these side by side.

Memory, meanwhile, is just a huge array of bytes with addresses. Both the instructions and the data live in it, which is why a program is also just data on disk until something loads it and points a PC at it.

Interview question

Explain the fetch-decode-execute cycle. What's the role of the program counter?

What a strong answer covers
  • Fetch: read the instruction at the address in the PC from memory, advance the PC.
  • Decode: figure out the opcode and operands, which registers or memory it needs.
  • Execute: perform it, possibly reading or writing memory; a jump overwrites the PC.
  • The PC is what makes it a sequence: it's the only state that decides what happens next, and control flow is just writing to it.
  • A concrete example: walk through one ADD and one JNZ from the widget.

Follow-up: What happens to this loop when the program has an if-statement? (It compiles to a compare and a conditional jump; the jump writes the PC only if the condition held.)

Interview question

From the CPU's point of view, what's the difference between a register, RAM, and disk?

What a strong answer covers
  • Registers: inside the CPU, a few dozen, a few bytes each, accessible in one cycle, the only place computation happens.
  • RAM: outside the CPU, gigabytes, hundreds of cycles away, holds the running program and its data, loses content on power off.
  • Disk: terabytes, millions of cycles away, permanent, the CPU can't touch it directly; the OS copies data between disk and RAM.
  • The theme: each step out is bigger, slower, and cheaper per byte. That gap is the reason caches exist (next tabs).

Follow-up: If a program's variable lives in RAM, what has to happen before the CPU can add one to it? (Load into a register, add, store back. Three instructions, at least one slow memory round trip.)

Interview question

What does a compiler do? And if the CPU only understands machine code, how does a Python script run?

What a strong answer covers
  • A compiler translates source code into machine code for a specific CPU family, ahead of time. The output is a file of instructions.
  • Python is interpreted: the interpreter is a compiled program. The CPU runs the interpreter's machine code, and the interpreter reads your script and decides what to do.
  • That indirection is why Python is slower than C for tight loops and why it's portable: the same script runs anywhere the interpreter runs.
  • Bonus: many languages sit in between (bytecode plus a virtual machine, or just-in-time compilation).

Follow-up: Why can't you take a compiled program from a Mac with an Apple chip and run it on an Intel PC? (Different instruction sets: the machine code numbers mean different things.)

Faster CPUs

Doing one instruction completely before starting the next wastes most of the chip. While the decode circuitry is busy, the fetch circuitry sits idle, and so on. Two ideas fix that, and both come up in interviews.

Pipelining: the assembly line

Split the work into stages and have different instructions in different stages at the same time. A classic five-stage pipeline: fetch, decode, execute, memory access, write back. Each instruction still passes through all five, but once the pipe is full, one instruction finishes every cycle, the way a car wash finishes one car per minute even though each car spends five minutes inside.

Pipelining doesn't make any single instruction faster. It raises throughput: instructions completed per second. Ten instructions in a five-stage pipeline take 14 cycles instead of 50.

Branch prediction: guessing the future

The pipeline has a problem with jumps. When a conditional jump enters the pipe, the CPU won't know which way it goes until the execute stage, but it needs to fetch the next instruction now. So it guesses. A branch predictor tracks how each jump behaved before and bets it'll do the same again. Loops make this easy: the jump back went the same way the last thousand times.

When the guess is wrong, the instructions fetched down the wrong path are thrown away and fetching restarts on the right one. That's the misprediction penalty, a few cycles in the toy here, closer to 15 to 20 on a real chip. Modern predictors are right well over 95 percent of the time, which is why unpredictable branches (sorting random data, for example) are measurably slower than predictable ones.

Why not just a faster clock?

Clock speeds climbed for decades and then stalled around 3 to 5 GHz, because power and heat grow much faster than speed. So chips went sideways instead: more cores. A program only benefits from that if it has work that can run in parallel, which means multiple threads, which is session 2. One core can also pretend to be two with hyperthreading (Intel's name; the generic term is SMT): it keeps two instruction streams in flight and fills each one's idle slots with the other's work. That's why a laptop says "8 cores, 16 threads." The 16 are not 16 cores; they're 8 cores each holding two queues.

One more trick worth a sentence: out-of-order execution. If an instruction is waiting on slow memory, the CPU runs later independent instructions in the meantime and puts the results back in program order. You don't need the details, just the fact that the CPU reorders your instructions behind your back and hides it.

Interview question

What is pipelining, and why does it make a CPU faster if every instruction still takes the same number of stages?

What a strong answer covers
  • Instruction execution is split into stages; different instructions occupy different stages in the same cycle.
  • Latency per instruction is unchanged; throughput goes to roughly one instruction per cycle once the pipe is full.
  • The car wash or assembly line analogy, with numbers: N instructions in S stages take about N + S - 1 cycles instead of N times S.
  • What breaks it: dependencies between adjacent instructions (stalls) and branches (guessing).

Follow-up: An instruction needs the result of the one right before it. What happens in the pipeline? (It waits, a stall or bubble, unless the CPU forwards the result directly from the execute stage; either way the dependency limits how much can overlap.)

Interview question

What is branch prediction, and why does the CPU need it at all?

What a strong answer covers
  • In a pipeline the next instruction must be fetched before a conditional jump has been decided, so the CPU has to guess.
  • The predictor uses history: this branch went this way last time, so probably again. Loops are almost perfectly predictable.
  • On a wrong guess the wrong-path instructions are flushed and fetching restarts; the cost is the misprediction penalty, tens of cycles on real hardware.
  • Consequence a programmer can see: code with unpredictable branches (a condition on random data) runs slower than the same code on sorted data.

Follow-up: How could you rewrite an if-statement in a hot loop to avoid a branch entirely? (Compute both outcomes and select with arithmetic or a conditional-move; compilers do this when they can.)

Interview question

My laptop says "8 cores, 16 threads." What does that mean? Does a single-threaded program run any faster on it than on a 1-core machine with the same clock?

What a strong answer covers
  • 8 physical cores, each able to hold two instruction streams (hyperthreading), so the OS sees 16 logical CPUs.
  • A single-threaded program uses one core and runs at essentially the same speed; more cores only help work that's split into threads.
  • The other 15 logical CPUs are still useful: everything else on the machine runs there without stealing from your program.
  • Hyperthreading gives maybe 10 to 30 percent extra throughput per core, not double, because the two streams share the core's execution units.

Follow-up: Give one reason a program with 16 threads might run no faster on this machine than with 8. (Only 8 real cores; the extra threads share execution units, or the work is limited by memory rather than compute, or the threads spend time waiting on each other.)

The memory ladder

Here's the problem that shapes the rest of the session. A core can finish an addition in a fraction of a nanosecond. Fetching one value from RAM takes about 100 nanoseconds. If the CPU had to wait for RAM on every load, it would spend over 99 percent of its time idle.

Fast memory is expensive and can't be built big. Big memory is slow. Nobody has found a way around that, so computers use a ladder: a tiny amount of the fastest memory closest to the CPU, then bigger and slower layers stepping outward, each holding a copy of the most-used parts of the layer below.

Interview question

Why do CPUs have caches? Why not just use faster RAM?

What a strong answer covers
  • The CPU is hundreds of times faster than RAM; without something in between it would idle on every load.
  • Fast memory is small and expensive; you can't make gigabytes of it or put it close enough to the core.
  • Caches hold recently and nearby used data, which works because programs have locality (next tab).

Follow-up: Who decides what goes in the cache? (The hardware, automatically, on every access. The programmer can only influence it by how they lay out and traverse data.)

Interview question

Rank these by how long they take, with rough numbers: a register read, an L1 hit, a RAM access, an SSD read, and a round trip to another server in the same data center.

What a strong answer covers
  • Register: about a cycle. L1: about 1 ns, a few cycles. RAM: about 100 ns, hundreds of cycles. SSD: about 100 microseconds. Network round trip in a data center: about half a millisecond.
  • Orders of magnitude matter more than exact digits; each step is roughly 10 to 1,000 times the last.
  • The practical point: a network call costs a million instructions, so you batch them; a RAM miss costs a few hundred, so you keep hot data contiguous.

Follow-up: Where would a spinning hard disk seek go on that list? (After SSD and after the data center round trip: about 10 milliseconds, roughly a hundred times slower than an SSD read.)

Caches up close

A cache only helps if the thing you need is already in it. It usually is, because of two habits nearly every program has, together called locality:

  • Temporal locality: if you used an address recently, you'll probably use it again soon. Loop counters, the current function's variables, hot data structures.
  • Spatial locality: if you used an address, you'll probably use the ones next to it soon. Arrays walked in order, the next instruction after this one, the fields of a struct.

Cache lines

The cache doesn't move single bytes. It moves fixed chunks called cache lines, 64 bytes on nearly every modern CPU, which is 16 four-byte integers. Touch one integer and its whole line comes along. That's spatial locality turned into hardware: walk an array in order and you get one miss followed by fifteen hits per line, for free.

What a miss costs

A hit takes a few cycles. A miss to RAM takes a few hundred. So the average cost of a memory access is dominated by the miss rate:

average time = hit rate x hit time + miss rate x miss time
example: 0.95 x 4 + 0.05 x 300 = 3.8 + 15 = 18.8 cycles

Notice what that says: a 5 percent miss rate makes memory access almost five times slower than the all-hits case. Going from 95 to 99 percent hits roughly halves the average. Small changes in hit rate are large changes in speed.

Where a line goes

The simplest design is direct-mapped: each memory address has exactly one slot in the cache it can go to, chosen by a few bits of the address, like a hash table with no chaining. Two lines that map to the same slot evict each other even if the rest of the cache is empty. Real caches are set-associative: each address gets a small set of candidate slots (typically 4 to 16), which cuts those collisions. You don't need the wiring; you need the idea that an address decides where its line can live.

The example every interviewer knows

A 2D array in C, Java, or NumPy is stored row-major: row 0's elements are next to each other in memory, then row 1's, and so on. Summing it row by row walks memory in order and rides the cache lines: 75 percent hits in the widget, over 90 percent on a real machine. Summing it column by column jumps a whole row between accesses, so nearly every access is a new line, and with a small cache the lines evict each other before they're reused. Same arithmetic, same number of operations, often five to ten times slower. Try both patterns in the widget, then try the column pattern with 1 word per line and see the lines stop mattering.

Two more sentences for completeness. Writes go to the cache too and are written back to RAM later, so a cache also hides write latency. And on a multi-core chip each core has its own L1 and L2, so the hardware keeps them consistent behind the scenes; two cores repeatedly writing to the same line ping-pong it between them, which is why "false sharing" is a real performance bug in threaded code. Interview question

What is a cache line, and why should I care about it when I write a loop?

What a strong answer covers
  • The unit the cache moves: 64 bytes, so 16 ints or 8 doubles come in together.
  • A loop that touches consecutive elements pays one miss per line and gets the rest as hits; a loop that strides across memory pays a miss per element.
  • It also means data layout matters: keep things you use together next to each other (arrays of structs vs structs of arrays is the classic debate).
  • Bonus: the row-major example, and false sharing when two threads write the same line.

Follow-up: You have a linked list and an array with the same million integers. Which sums faster and why? (The array, by a lot: consecutive lines. Each list node is a separate allocation, so nearly every next-pointer is a miss.)

Interview question

Explain temporal and spatial locality, with a concrete example of each from real code.

What a strong answer covers
  • Temporal: the same address used again soon. Example: a loop counter, or a hash map that's looked up on every request.
  • Spatial: neighboring addresses used soon. Example: iterating an array, reading the fields of one object, the instruction after the current one.
  • Caches exploit temporal locality by keeping recently used lines, and spatial by loading whole lines.
  • Code that has neither (random access into a huge table) runs at RAM speed no matter how good the cache is.

Follow-up: Name a data structure with poor spatial locality and say what you'd do about it. (Linked lists, trees of individually allocated nodes. Fix: store nodes in a contiguous array, or use a B-tree style layout with many keys per node.)

Interview question

Two versions of a function sum a large 2D array: one loops rows-then-columns, the other columns-then-rows. Identical arithmetic. One is several times faster. Explain, and say what "several times" depends on.

What a strong answer covers
  • Row-major layout puts a row's elements consecutively. Row-first walks memory in order: one miss per line, then hits.
  • Column-first jumps a whole row each step: a different line every access, and with more rows than cache lines, lines are evicted before they're reused.
  • The ratio depends on the line size, the array's width versus the cache size, and how bad a miss is on that machine.
  • Strong answers mention the hardware prefetcher helps the sequential case even more, and that this shows up in real numeric code constantly.

Follow-up: The array is tiny, 4 by 4. Does the order still matter? (Barely. The whole thing fits in a couple of lines, so after the first pass everything hits either way.)

Virtual memory

Three problems show up the moment a computer runs more than one program. Every program was compiled to use addresses starting near zero, so they'd all want the same memory. A bug in one program could scribble over another's data. And a program shouldn't need to know or care where in RAM it happens to land this time.

One mechanism solves all three. Every process gets its own private virtual address space: the illusion of a full range of memory starting at zero that belongs only to it. The addresses a program uses are virtual addresses. On every single memory access, a piece of hardware in the CPU called the MMU translates the virtual address into a physical address, the real location in RAM, using a lookup table the operating system built for that process.

Pages and frames

Translating every byte individually would need a table as big as memory. Instead, the address space is cut into fixed chunks called pages, 4 KB each, and RAM is cut into 4 KB frames. The page table maps page numbers to frame numbers. A virtual address is a page number plus an offset inside the page. Only the page number gets translated; the offset is copied through unchanged.

With 4 KB pages the offset is the low 12 bits of the address (2 to the 12th is 4,096). Everything above those 12 bits is the page number. In the widget the addresses are 16 bits wide to keep them readable: 4 bits of page number, 16 pages, 12 bits of offset.

What you get for it

  • Isolation. A process can only reach frames its own table points to. There's no address it can form that lands in another process's memory.
  • Relocation. The program uses the same addresses every run; the OS puts it in whatever frames are free.
  • Sharing. Two processes can map the same frame. That's how one copy of a shared library in RAM serves every program using it.
  • Lying about size. A page doesn't have to be in RAM at all. It can be on disk, or not exist yet. The table just says so. That's the next tab.

The TLB

Walking the page table costs memory accesses of its own, on every load and store. So the MMU keeps a small cache of recent translations, the TLB (translation lookaside buffer): "page 3 is in frame 6." A TLB hit makes translation nearly free. A miss means a page table walk, then the result is cached. It's the same locality bet as the data cache, applied to translations. When the OS switches to a different process, the TLB has to be flushed or tagged, because the same page numbers now mean different frames.

The layout of one address space

On Linux, a process's virtual space has a conventional shape, and the widget's process A follows it: code at the bottom, then global data, then the heap growing upward as you allocate, shared libraries somewhere in the middle, and the stack at the top growing downward. Huge gaps of unmapped addresses sit between them. Touching one of those gaps is what a segmentation fault is: not "bad memory," but "no mapping here."

Interview question

What is virtual memory, and what problems does it solve?

What a strong answer covers
  • Each process gets a private address space; the hardware translates every access through a per-process page table the OS maintains.
  • Isolation: no process can address another's memory. Relocation: programs use fixed addresses and land anywhere in RAM. Sharing: one frame mapped into many processes.
  • And the size lie: pages can live on disk or not exist yet, so a process can use more memory than is physically present, and memory is allocated lazily.
  • Strong answers name pages, frames, page tables, and the TLB, and say translation happens in hardware.

Follow-up: What's the cost? (Every access needs a translation, so you need a TLB; page tables use memory; a page fault to disk is enormously slow.)

Interview question

Walk me through translating a virtual address to a physical one, step by step.

What a strong answer covers
  • Split the virtual address into page number (high bits) and offset (low 12 bits for 4 KB pages).
  • Check the TLB for the page number. Hit: you have the frame. Miss: walk the page table in memory and cache the result.
  • Check the entry's bits: valid? present in RAM? permission allows this access?
  • Physical address = frame number with the offset appended. Then go to the cache or RAM with that.
  • If not present: page fault, OS loads it. If not valid: segmentation fault.

Follow-up: With 4 KB pages and a 32-bit address, how many pages are there and how big is the offset? (Offset 12 bits, 20 bits of page number, so about a million pages. Which is why real page tables are multi-level.)

Interview question

Process A and process B each have a pointer holding the same value. Can one read the other's data through it? Why not, mechanically?

What a strong answer covers
  • No. The pointer is a virtual address, and each process has its own page table; the same page number maps to different frames.
  • A can only reach frames present in A's table. There's no virtual address in A that translates to B's frames unless the OS deliberately maps one (shared memory).
  • The check happens in hardware on every access, so it can't be bypassed by user code.
  • Bonus: this is exactly what a shared library or explicit shared memory relies on, in reverse: the OS maps the same frame into both tables on purpose.

Follow-up: Then how does a debugger read another process's memory? (It asks the OS, which has access to every table, through a system call such as ptrace.)

Page faults and swap

The page table entry has more than a frame number. It has flags: is this page valid at all, is it currently in RAM, can it be written, can it be executed. The interesting cases are when the MMU can't complete a translation.

The page fault

When a program touches a page whose entry says "valid, but not in RAM," the MMU stops the instruction and hands control to the operating system. That's a page fault. It is not an error. It's how memory gets loaded at all. The OS then:

  1. Finds a free frame. If none is free, picks a victim page to evict and, if it has been modified, writes it out to disk first.
  2. Fills the frame: reads the page from disk (the program file, or the swap area), or just zeroes it if this is fresh memory the program asked for and never touched.
  3. Updates the page table entry to point at the frame and mark it present.
  4. Restarts the instruction that faulted. The program never knows it happened, except that it was slow.

This is demand paging: nothing is loaded until it's touched. A program that maps a 2 GB file and reads 3 pages of it costs 3 page faults, not 2 GB of reading.

The other outcome

If the entry says "not valid" (no mapping at all), or the access breaks a permission (writing to read-only code), the OS doesn't fix anything. It sends the process a signal, and by default the process dies. That's a segmentation fault. Same hardware trap, opposite meaning: a page fault is "not here yet," a segfault is "you were never allowed here."

Swap and thrashing

When RAM is full, evicted pages go to swap space on disk, so the total memory in use can exceed physical RAM. The OS picks victims roughly by LRU, least recently used, on the same locality bet as the cache: what you haven't touched in a while you probably won't touch soon.

It works as long as the set of pages a program is actively using, its working set, fits in RAM. When it doesn't, every fault evicts a page that's needed again a moment later, which faults, which evicts another. The machine spends its time moving pages to and from disk and no real work happens. That's thrashing, and it's why a computer that runs out of RAM doesn't slow down gracefully: it falls off a cliff. Each disk fault costs millions of cycles, so even a small fault rate dominates everything.

  • The MMU can't translate (present bit clear), so it traps to the OS: a page fault.
  • The OS checks the entry is valid, finds a free frame or evicts a victim (writing it to swap if dirty), and reads the page from disk or zero-fills it.
  • It updates the page table (and the TLB gets the new entry on retry), then restarts the faulting instruction.
  • The program is unaware except for the delay: microseconds if the page was in the page cache, milliseconds if it came from disk.

Follow-up: Why is this called demand paging, and what does it buy you? (Pages load only when touched. Fast startup, and a process can map far more than it uses.)

Interview question

What's the difference between a page fault and a segmentation fault?

What a strong answer covers
  • Both start as the MMU failing to translate and trapping to the OS.
  • Page fault: the entry is valid but the page isn't in RAM. The OS loads it and the program continues. Normal, frequent, invisible.
  • Segfault: no valid mapping, or a permission violation. The OS can't fix it and kills the process with a signal.
  • Strong answers connect it to real bugs: dereferencing null or a freed pointer lands in an unmapped region, hence segfault.

Follow-up: Can you get a segfault on an address that's inside your program's memory range? (Yes: writing to a read-only page, such as your own code or a string literal, is a permission fault and also a segfault.)

Interview question

A server has idle CPU and is suddenly crawling; the disk activity light is solid. What do you suspect, and how would you confirm it?

What a strong answer covers
  • Suspect thrashing: the working set no longer fits in RAM, so the machine is swapping constantly. Idle CPU plus busy disk is the signature.
  • Confirm: check memory and swap usage (free, top), and swap-in and swap-out rates (vmstat's si and so columns); a high fault rate with low CPU seals it.
  • Fix: find the process that grew (top sorted by memory), kill or restart it, add RAM, or fix the leak.
  • Strong answers say why it's a cliff: each disk fault is millions of cycles, so a small fault rate dominates.

Follow-up: Would adding a faster SSD for swap solve it? (It softens the cliff, but the real fix is making the working set fit in RAM. Swap is a safety net, not a memory extension.)

Practice

Out loud first, then open the answer. Same rules as always.

1. Explain the fetch-decode-execute loop to someone who's never programmed.

The CPU has a bookmark (the program counter) pointing at the next instruction in memory. It reads that instruction, works out what it says, does it, and moves the bookmark forward. A jump instruction just moves the bookmark somewhere else. Billions of times a second.

2. Why do caches exist, and why more than one level?

The CPU is hundreds of times faster than RAM, so it needs something closer. Fast memory has to be small, so you keep a tiny fast one (L1) for what you're using right now, a bigger slower one (L2) behind it, and a bigger shared one (L3) behind that. Each level catches what the one in front missed.

3. What's a cache line, and why does a loop's order matter?

The cache moves 64-byte chunks. A loop through consecutive elements pays one miss per chunk and gets the rest free. A loop that jumps around pays a miss per element. Row-major arrays summed row by row versus column by column are the standard example.

4. What does virtual memory give you?

Every process gets its own private address space starting at zero. Isolation: no process can address another's memory. Relocation: programs use fixed addresses and land anywhere in RAM. Sharing: one frame mapped into many processes. And the size lie: pages can live on disk or not exist yet.

5. Walk through translating one address.

Split into page number and offset. Check the TLB; on a miss, look up the page table. Check the flags. Frame number plus offset is the physical address. Not present: page fault, load it, retry. Not valid: segfault.

6. Page fault versus segfault, in two sentences.

A page fault is "valid page, not in RAM yet": the OS loads it and the program never notices. A segfault is "no mapping here" or "not allowed": the OS kills the process.

Paper problems

Do these by hand. Answers under each.

a. Hit rate 96 percent, hit 4 cycles, miss 250 cycles. Average access time?

0.96 x 4 + 0.04 x 250 = 3.84 + 10 = 13.84 cycles. Four percent misses more than triple the average.

b. Direct-mapped cache, 8 lines, 4 words per line. Accesses to words 0, 4, 8, 32, 0. Hits and misses?

Word 0: line block 0, slot 0, miss. Word 4: block 1, slot 1, miss. Word 8: block 2, slot 2, miss. Word 32: block 8, slot 8 mod 8 = 0, miss, and it evicts block 0. Word 0 again: slot 0 now holds block 8, miss. Five misses, zero hits. The last one is a conflict miss: the cache had room, but blocks 0 and 8 fight over the same slot.

c. 4 KB pages. Virtual address 0x3A7C. Page 3 maps to frame 9. Physical address?

Offset is the low 12 bits: 0xA7C. Page number is 3. Frame 9 starts at 9 x 0x1000 = 0x9000. Physical = 0x9000 + 0xA7C = 0x9A7C.

d. 16-bit virtual addresses and 4 KB pages. How many pages, and how many bits of offset?

4 KB is 2 to the 12th, so 12 bits of offset. 16 minus 12 is 4 bits of page number: 16 pages. (A real 64-bit machine has 48 usable address bits, so 36 bits of page number, which is why page tables are multi-level trees.)

e. 3 frames, LRU, reference string 1, 2, 3, 1, 4, 2. Faults?

1 fault [1]. 2 fault [1 2]. 3 fault [1 2 3]. 1 hit (1 is now most recent). 4 fault, evict the LRU which is 2: [3 1 4]. 2 fault, evict 3: [1 4 2]. Five faults, one hit.

f. Ten instructions on a five-stage pipeline with one mispredicted branch costing 2 cycles. Total cycles?

Ideal: 10 + 4 = 14. Plus the penalty: 16. Without a pipeline: 50.

Narration rubric: what happens when you run ./program (machine side)

The OS half of this story comes next session. For now, tell the machine's half. A complete answer touches all of these.

  • The program is machine code in a file; it has to be mapped into memory before anything runs.
  • The OS gives it a virtual address space and sets the program counter to its first instruction.
  • The first fetch page-faults: the code page isn't in RAM yet, so the OS loads it and retries.
  • The CPU runs fetch, decode, execute, with the pipeline keeping several instructions in flight.
  • Early loads miss the cache and pull lines from RAM; the loop's locality then makes most accesses hit.
  • The branch predictor learns the loop's jump after a couple of iterations.
  • Every address the program uses is virtual; the MMU translates each one, mostly via the TLB.
  • Data the program allocates but hasn't touched costs nothing until it's touched (demand paging).
  • If it dereferences a bad pointer, the translation fails with no mapping: segfault.
  • You named the layer at each step: hardware (CPU, cache, MMU) versus OS (page table, fault handler).
